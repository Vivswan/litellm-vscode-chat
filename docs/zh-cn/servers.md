# 服务器

[English](../servers.md) | 简体中文 | [繁體中文](../zh-tw/servers.md)

扩展可以同时连接任意数量的 LiteLLM 服务器, 并把它们的模型聚合进同一个选择器列表。本页覆盖关于服务器的一切: 声明它、向它进行身份验证、塑造它的模型、它在 VS Code 中的生命周期, 以及它的密钥如何存储。

## 服务器如何工作

三个概念承载其余一切:

- **条目** - `litellm-vscode-chat.servers` 设置中的一个对象: 关于服务器的声明式真相。[仪表板](dashboard.md)的添加/编辑表单写入的是同一个设置, 因此 JSON 编辑和表单始终一致。
- **提供程序组** - VS Code 自己为每个服务器持有的东西 (位于 `<profile>/User/chatLanguageModels.json`, 即「模型文件」)。扩展会在激活时以及设置每次变化时, 自动把条目同步为组。
- **标识** - 条目的 `label` 加 `baseUrl`。组以标签命名, 这就是重命名和删除会出现[下文](#生命周期-重命名删除与隐藏的组)所述生命周期怪癖的原因。

`servers` 设置是机器作用域的: 它只存在于你的用户设置中, 工作区无法覆盖它 (克隆下来的仓库永远无法把你的服务器重新指向另一台主机), Settings Sync 也不携带它 - 服务器和凭据留在你录入它们的那台机器上。要把它们搬到另一台机器, 用 ["LiteLLM: Export Settings..."](settings.md#导出与导入), 它也能携带密钥存储中的值。

来自旧版本的条目 (扁平的 `apiKey`、`oauth*`、`virtualKey*`、`modelParameters` 等字段) 会由一次性迁移自动重构。已在密钥存储中的密钥不受影响 - 重构只改动设置文本, 无需重新输入任何东西。

## 快速开始

最小形式 - 无需身份验证的本地代理:

```jsonc
"litellm-vscode-chat.servers": [
  { "label": "Local", "baseUrl": "http://localhost:4000" }
]
```

典型形式 - 托管网关, 密钥不放进设置文件:

```jsonc
"litellm-vscode-chat.servers": [
  { "label": "prod", "baseUrl": "https://litellm.example.com" }
]
// 然后: 仪表板 -> 编辑 "prod" -> API 密钥 -> 「安全存储」,
// 或命令面板 -> "LiteLLM: Set Server Secret"
```

保存后, 服务器的模型片刻之内就会出现在模型选择器中。仪表板的**测试连接**按钮会按当前输入原样探测草稿 - 包括未保存的编辑, 已存储的密钥从其存放处读取 - 发出一次发现调用, 报告模型数量或确切错误, 当失败看起来是设置问题时, 附上指向匹配的[故障排除](troubleshooting.md#常见问题)小节的链接。它不保存也不同步任何内容。

密钥晚于条目时要知道的一条时序规则: 提供程序组在条目第一次同步的那一刻从条目创建, 凭据也包含在内, 而 VS Code 无法更新现有的组 - 第一次同步之后才存储的密钥, 要等组被重新创建后才能到达请求, 服务器行会显示确切步骤 ([生命周期](#生命周期-重命名删除与隐藏的组))。仪表板的添加表单避开了这一点: 它在条目第一次同步之前就把密钥存好。

## 条目参考

条目能携带的每个属性:

| 属性 | 类型 | 作用 |
|---|---|---|
| `label` | 字符串, 必填 | 在模型选择器中为服务器命名; 条目标识的一半 |
| `baseUrl` | 字符串, 必填 | 服务器的根 URL。扩展会自行追加 `/v1`; 若 URL 已以 `/v1` 或 `/v2` 这样的版本段结尾, 则按原样使用; `apiVersion` 字段可覆盖两者 |
| `apiVersion` | 字符串 | 追加到基础 URL 的内容。未设置 = 自动 (`/v1`, 或 URL 中已有的版本段); `""` = 不追加任何内容; `"v2"` = 追加 `/v2`。与所有每条目字段一样, 只通过匹配条目标签和基础 URL 的提供程序组生效; 过期组会回退到自动规则, 仪表板会在该服务器行的下方说明 |
| `auth` | 对象 | `apiKey`、`oauth`、`virtualKey` 恰取一种形式, 可选择带级别更低的伴随凭据 ([下文](#身份验证))。服务器不需要凭据时整个省略。含混不清的形态会被报告, 条目按配置错误处理 |
| `headers` | 对象 | 发往此服务器的每个请求上的自定义 HTTP 标头 ([下文](#自定义标头)); 冲突时扩展管理的身份验证标头胜出 |
| `models.parameters` | 记录 | 只针对此服务器模型的请求参数; 与全局设置相同的[匹配键](models.md#模型匹配), 逐字段应用在它之上 ([详情](models.md#参数)) |
| `models.capabilities` | 记录 | 只针对此服务器模型的能力覆盖; 机制相同 ([详情](models.md#能力)) |
| `discovery.declared` | 字符串数组 | 即使发现列不出也要注册的精确模型 ID ([下文](#声明的模型)) |
| `discovery.expectedFailures` | 字符串数组 | 此服务器预期失败的发现终结点: `"modelListing"` (`/v1/models`)、`"modelInfo"` (`/v1/model/info`)。各只尝试一次, 记一条 info 级日志而非红色错误 ([下文](#发现与预期失败)) |
| `budget` | 数字 | 用于[用量警报](usage.md#预算)的手动预算 (美元)。优先于密钥自身的 `max_budget`; 仪表板两者都显示 |

一个完整的条目:

```jsonc
{
  "label": "prod",
  "baseUrl": "https://gateway.internal",
  "auth": { "apiKey": "sk-..." },
  "headers": { "x-routing-env": "prod" },
  "models": {
    "parameters":   { "gpt-5*": { "temperature": 0.2 } },
    "capabilities": { "deepseek-r1": { "supports_reasoning": true, "context_length": 131072 } }
  },
  "discovery": {
    "expectedFailures": ["modelListing", "modelInfo"],
    "declared": ["deepseek-r1"]
  },
  "budget": 50
}
```

表格展示不了的边界情况:

- 标签在条目之间唯一: 重复使用先前条目标签的条目会被跳过并报告 - 第一个条目胜出。要把两个条目指向同一主机, 给它们不同的标签; 它们随即成为端到端的两个服务器 - 两个选择器组、模型分别列在各自组下, 每个条目的身份验证、标头和 `models` 记录只应用于自己的组。
- 空的或只有空白的 `label` 或 `baseUrl` 让条目不可用: 跳过并报告。JavaScript 保留名 `__proto__`、`constructor` 和 `prototype` 会被拒绝作为标签。
- 基础 URL 可以带路径 (`https://intranet.example.com/litellm`, 挂载在某路径下的网关); `/v1` 追加在其后, 除非路径已以 `/v1` 或 `/v2` 这样的版本段结尾 (按原样使用) - `apiVersion` 字段可覆盖两者 (空字符串 = 什么都不追加)。尾部斜杠无害 - 比较或使用 URL 之前会将其去掉。
- 纯 `http` 可以用, 而且是本地代理的常规选择; 但在网络上它会明文携带你的凭据, 因此任何远程服务器都请优先用 `https`。
- `budget` 必须是大于 0 的数字 ([用量 - 预算](usage.md#预算))。
- 短暂损坏的条目 (比如编辑到一半的 settings.json) 会被跳过并报告, 但绝不会被误认为删除: 它的提供程序组不会被隐藏。[删除](#生命周期-重命名删除与隐藏的组)只在标签本身从设置中消失时发生。

## 身份验证

选择与你的网关期望相匹配的形式。每个条目恰好一种形式, 形式按 `oauth` > `apiKey` > `virtualKey` 分级: 一种形式可以携带级别更低的*伴随凭据*, 供要求在第二个标头中提供第二个凭据的网关使用 - `oauth` 可带 `apiKey` 和/或 `virtualKey` 伴随凭据 (放在 `oauth` 对象内部), `apiKey` 可带一个 `virtualKey` 伴随凭据 (与它并排), 而级别最低的 `virtualKey` 不带任何伴随凭据。

| 你的网关期望 | 配置 |
|---|---|
| 密钥作为 bearer 令牌 (最常见, LiteLLM 虚拟密钥也在内) | `auth.apiKey` |
| 密钥放在自定义标头中 (例如 `x-litellm-api-key`) | `auth.virtualKey` |
| bearer 密钥**加**自定义标头中的密钥 | `auth.apiKey` + 与它并排的 `virtualKey` 伴随凭据 |
| OAuth2 客户端凭据令牌 | `auth.oauth` |
| OAuth 令牌**加**旁边一个 LiteLLM 密钥 | `auth.oauth` + 其 `apiKey` 或 `virtualKey` 伴随凭据 |

两个边界情况:

- 缺少必要部分的身份验证形式 (`oauth` 缺 `tokenUrl` 或 `clientId`) 是和设置两种形式一样的配置错误: 报告, 且条目在修复之前不被使用。而只是*在等它的密钥*的形式 (`virtualKey` 标头有了但值还没设置, `apiKey` 还没有存放在任何地方) 则不同: 条目照常工作, 请求只是不携带凭据, 服务器的 401 会告诉你缺什么 - 这是添加条目和运行 "LiteLLM: Set Server Secret" 之间的正常状态。

- **完全没有 `auth`** 意味着不发送凭据标头 - 除非该条目的[已存储密钥](#密钥与密钥存储)另有说法; 存储也算形态的一部分。没有单独的「免密钥」模式可选: 结果需要密钥的服务器会回答 401 (「身份验证失败」), 把密钥加到条目上就是修复。
- **含混不清的 `auth` 形态**绝不会让扩展在凭据之间乱猜: `oauth` 与任何其他东西并列在 `auth` 顶层 (它的伴随凭据属于 `oauth` 对象*内部*), 或者 `auth` 内出现扩展不认识的键 (否则一个笔误会悄悄变成「没有凭据」), 都是配置错误 - 仪表板的服务器行和其「配置」诊断会点名出问题的键 - 条目在修复之前不被使用。其他条目不受影响。`apiKey` 与 `virtualKey` 并排*不*算含混: 按级别读, 那是 API 密钥形式加一个虚拟密钥伴随凭据。

### API 密钥

```jsonc
"auth": { "apiKey": "sk-..." }   // 或存放在密钥存储中; 见下文「密钥」
```

以 `Authorization: Bearer` 标头发送, 并附一份 `X-API-Key` 副本 (有的网关读前者, 有的读后者)。

同时检查 bearer **和**自定义标头中密钥的网关, 把第二个凭据作为伴随凭据放在密钥旁边:

```jsonc
"auth": {
  "apiKey": "sk-...",
  "virtualKey": { "header": "x-litellm-api-key", "value": "sk-..." }  // 可选伴随凭据: 额外标头
}
```

把 `Authorization` 或 `X-API-Key` 命名为标头的伴随凭据, 会从 API 密钥手中接管那一个标头。

### 自定义标头中的虚拟密钥

虚拟密钥是 LiteLLM 代理自己签发的密钥, 限定到某个预算、团队或一组模型 ([LiteLLM 的文档](https://docs.litellm.ai/docs/proxy/virtual_keys))。大多数网关把它当作普通 bearer 令牌接收 - 那种情况用 `auth.apiKey`。这种形式给期望它出现在自定义标头中的网关:

```jsonc
"auth": {
  "virtualKey": {
    "header": "x-litellm-api-key",
    "value": "sk-..."            // 或存放在密钥存储中
  }
}
```

把 `Authorization` 命名为标头会把整个该标头交给虚拟密钥。`header` 是必填项, 是普通的设置文本; `value` 是可作密钥的那一半, 因此只带标头的条目就是[密钥存储形态](#密钥与密钥存储) - 值从其存放处读取。

### OAuth 客户端凭据

给位于身份提供方之后、拒绝静态密钥的网关:

```jsonc
"auth": {
  "oauth": {
    "tokenUrl": "https://idp.example.com/oauth2/token",
    "clientId": "my-client-id",
    "clientSecret": "...",       // 公共客户端省略; 可存放在密钥存储中
    "scopes": "read write"       // 可选, 以空格分隔
  }
}
```

扩展用凭据换取一个短期 bearer 令牌, 在发往该服务器的每个请求上作为 `Authorization` 发送, 并在其过期前不久刷新。交换在每个请求上都受 `discovery.timeout` 约束 - 它是身份验证管道, 不是聊天调用, 所以身份提供方缓慢时要调高的是 `discovery.timeout`, 而不是 `chat.timeout`; 在聊天请求上, 交换同时也计入 `chat.timeout` 的整体预算。被拒绝的令牌会被丢弃, 下一个请求会获取新令牌。

**伴随凭据** - 有些企业网关同时检查两个凭据: OAuth bearer 向身份提供方证明你的身份, 而第二个标头中的 LiteLLM 密钥告诉代理该向哪个预算或团队计费。由于 `Authorization` 已被 bearer 占用, 第二个凭据走自己的标头:

```jsonc
"auth": {
  "oauth": {
    "tokenUrl": "https://idp.example.com/oauth2/token",
    "clientId": "my-client-id",
    "apiKey": "sk-...",          // 可选: 一并发送, 仅作为 X-API-Key
    "virtualKey": { "header": "x-litellm-api-key", "value": "sk-..." }  // 可选: 额外标头
  }
}
```

把 `Authorization` 命名为标头的伴随 `virtualKey` 会接管该标头, 并完全跳过 OAuth 交换。

## 自定义标头

条目的 `headers` 对象为发往此服务器的每个请求 - 发现和聊天都算 - 附加额外的 HTTP 标头。它的职责是网关管道: 路由标签、跟踪标头、额外的网关密钥。

```jsonc
{
  "label": "prod",
  "baseUrl": "https://gateway.internal",
  "auth": { "apiKey": "sk-..." },
  "headers": { "x-routing-env": "prod", "x-trace-source": "vscode" }
}
```

- 冲突时扩展管理的身份验证标头胜出: 这里的自定义标头会输给条目的 `auth` 形式发送的任何标头 - `Authorization`、`X-API-Key`, 或虚拟密钥命名的标头, 伴随凭据也算。名称按 HTTP 标头惯例不区分大小写比较, 所以写 `authorization` 不会改变任何事。
- 和每个条目级字段一样, 标头只通过与条目的标签和基础 URL 都匹配的提供程序组生效: 过时的组 (重命名的遗留, 或早于条目标签的组) 发出的请求不带它们 ([故障排除](troubleshooting.md#每服务器模型参数未生效))。
- 因为标头存放在条目上, 它们是机器作用域的, 从不随 Settings Sync 传播 - 类似凭据的值留在这台机器上。(有意不提供全局标头设置, 正是出于这个原因。)
- 只有大小写不同的两个标头名是同一个标头 (HTTP 标头名不区分大小写): 对象中的第一个胜出, 冲突作为配置诊断报告。
- 标头值是普通设置文本, 不是密钥。真正保密的值属于[`auth` 形式](#身份验证), 后者可以存放在密钥存储中。

## 每服务器模型配置

条目的 `models` 对象塑造此服务器的模型是什么样、如何被调用。两个字段都镜像全局 `models.*` 设置 - 学一次记录形态, 两处都能用。

### 参数与能力

- `models.parameters` 针对请求: 它使用与全局 `models.parameters` 相同的[匹配键](models.md#模型匹配), 逐字段应用在其**之上**。条目记录是服务器专属配置的唯一去处 - 全局键只是模型匹配器, 没有服务器限定。
- `models.capabilities` 针对注册: token 限制、视觉、工具调用、推理 - 纠正或补全发现报告的内容。能力与来源无关: 无论模型是被发现的还是[声明的](#声明的模型), 应用方式完全相同。

仪表板的编辑表单对两者都有对应的「此服务器的...」区块, 带逐行验证, 以及与全局编辑器相同的生效值检查器。

### 声明的模型

当发现列不出某个模型时 - 没有 `/v1/models` 的网关、被网关隐藏的模型 - 声明它, 它照样注册:

```jsonc
"discovery": { "declared": ["deepseek-r1", "qwen2.5-vl-72b"] }
```

- ID 是精确的 (没有匹配器): 声明说的是「这个模型在这里存在」。空的 `declared` 列表等于没有列表。
- 声明的模型只在发现尚未列出它时创建; 一旦服务器开始列出它, 声明转为休眠, 服务器的数据接管。
- 唯一的判据是该 ID 是否被列出 - 而不是它为什么缺失。无论终结点是预期缺失、发现整轮失败 (服务器行仍会报告那次失败), 还是服务器列出了其他模型却隐藏了这个, 声明的模型都会注册。
- 休眠与激活之间的切换发生在发现轮次上: 会话中途开始 (或停止) 列出某个已声明 ID 的服务器, 在下一次刷新之前什么都不会变 - 发现的列表有缓存 ([`discovery.cacheTtl`](settings.md#参考)) - 想立即看到就运行 "LiteLLM: Sync Models Now"。
- 两个条目可以声明同一个 ID: 各自在自己的服务器下注册自己的副本, 和两个服务器都提供的模型一模一样。
- 声明模型和描述模型是两个独立步骤: 声明模型的能力来自 `models.capabilities`、OpenRouter 目录和内置默认值, 和其他任何模型完全一样。
- 声明始终是按服务器的。对于通过 VS Code 自己的模型管理添加的服务器 (没有条目), 先[采用它](#外部服务器与采用)。
- 和每个条目级字段一样, 声明通过条目的标签加基础 URL 匹配来解析: 服务该服务器的过时组 (重命名的遗留, 或早于条目标签的组) 不会注册任何声明的模型。修复方法与[未生效的每服务器参数](troubleshooting.md#每服务器模型参数未生效)相同。

### 发现与预期失败

发现先尝试 `/v1/model/info` (丰富的元数据), 再回退到 `/v1/models` (纯列表)。请求是幂等的, 瞬时失败会在 `discovery.timeout` 之内重试。

如果你的网关就是不提供其中一个或两个终结点, 说出来, 扩展就不再把它当作故障:

```jsonc
"discovery": { "expectedFailures": ["modelListing", "modelInfo"] }
```

- 每个被点名的终结点只尝试一次 (不重试), 记一条 info 级日志而非红色错误; 服务器不计为不可达。
- 「预期」标记的是失败不足为奇, 而不是终结点被禁用: 被点名却有应答的终结点照常使用 - 它的数据照常胜出, 它列出的任何[声明的](#声明的模型) ID 转为休眠。无论成败, 只尝试一次是唯一持续的效果。
- 列表中的未知值 (`"modelListing"` 和 `"modelInfo"` 之外的任何东西) 被忽略并报告。
- 与 `discovery.declared` 组合, 就是完全没有发现能力的网关的配方: 声明模型, 预期两种失败, 服务器表现得像一等公民 - 状态栏、仪表板和「测试连接」都报告声明的模型而不是错误。

## 密钥与密钥存储

可作密钥的字段 - `auth.apiKey`、`auth.oauth.clientSecret`、`auth.virtualKey.value`, 以及伴随凭据的密钥/值 (OAuth 的或 API 密钥形式的) - 每个都提供按条目的选择:

- **内联**在 settings.json 中, 当该文件中出现明文值可以接受时。
- **VS Code 密钥存储** (加密, 按机器), 通过仪表板表单的「安全存储」选项或 "LiteLLM: Set Server Secret"。条目随即干脆省略该字段。
- 内联值优先于存储的值。

存储的值在 settings.json 中没有任何标记, 所以形态与存储共同起作用: 只要条目的形态没有另作说明, 已存储的 `apiKey` 就会激活 bearer - 在完全没有 `auth` 的条目上、在 API 密钥形式上, 或与已声明的 `virtualKey` 并存时 (按级别读, 那是 API 密钥形式加伴随凭据)。在 `oauth` 之下它保持为伴随凭据: `Authorization` 属于 OAuth bearer, 已存储的密钥只以 `X-API-Key` 发出。要停止发送已存储的密钥, 请删除存储的值本身 (下文的复选框) - 只删除设置文本够不到它。

哪些会回显到仪表板: 存储的值从不回显 - 表单显示值存放在哪里, 不显示值是什么。内联值会预填到编辑表单中 (遮盖在「显示」开关之后), 因为它们本来就以明文存在于你的 settings.json 中。

一个字段可能同时有两份副本 - 先安全存储了一个值, 后来又内联粘贴了一个。请求使用内联那份, 存储的那份原地不动: 清空内联字段会回退到存储的值, 而不是清除它。要摆脱存储的副本, 用编辑表单下方的「删除已存储的...」复选框。

编辑已保存的条目时:

- 清空的密钥字段保留已存储的值; 它不会清除密钥。
- 删除已存储的密钥是显式选择: 编辑表单在每个有值的密钥字段下方显示「删除已存储的...」复选框。

设置或轮换已存储的密钥等同于更改条目的凭据: 已同步的组无法接收它, 请求继续使用组创建时的凭据, 服务器行会显示重新创建的步骤 ([生命周期](#生命周期-重命名删除与隐藏的组))。

当扩展需要为凭据保留一个非机密标识时 (让同步状态保持一致的变更检测器), 它存储的是以随机的每安装密钥为键的指纹, 而不是简单哈希 - 那些记录不会向能读取扩展状态但读不到密钥存储的任何东西泄露关于凭据的任何信息, 哪怕是一个短到可猜的密钥。而当 VS Code 的密钥存储本身不可用时 (比如没有钥匙环服务的 Linux 桌面), 同步会在这一轮跳过该条目, 服务器行会说明 - 见[故障排除](troubleshooting.md#密钥存储不可用)。

已存储的密钥只属于条目的标签 - 基础 URL 不参与。两个后果:

- 直接在 settings.json 中重命名会把值留在旧标签下: 在你重新设置它们或从仪表板重新保存之前, 重命名后的条目一直不带凭据地运行; 通过仪表板的编辑表单重命名, 则会替你把已存储的密钥搬到新名称下。
- 把熟悉的标签重新指向另一台主机, 仍会拾取该标签已存储的值并发送给它。要把退役的标签重新用于不应看到旧凭据的服务器, 请先删除存储的值 (编辑表单的「删除已存储的...」复选框)。

删除条目不会删除它存储的密钥: 重新添加同标签的条目会再次找到它们。卸载前删除所有密钥的方法见[故障排除](troubleshooting.md#卸载与清理)。

## 生命周期: 重命名、删除与隐藏的组

一个 VS Code 限制解释了整个小节: **宿主 API 可以创建提供程序组, 但永远无法更新或删除它们。**扩展诚实地绕过它, 而不是假装没有。

| 你做什么 | 发生什么 |
|---|---|
| 添加条目 | 创建一个提供程序组; 模型出现在选择器中 |
| 更改条目的 URL 或凭据 | 现有的组无法更新。服务器行显示错误和修复方法: 从模型文件删除该组的对象、重新加载、运行 "LiteLLM: Sync Models Now" - 组会从条目重新创建。在那之前, 请求继续使用组创建时的凭据 - 轮换后的密钥尚未生效 |
| 重命名条目 (`label`) | 在新名称下创建新组; 旧组留在原处。扩展的通知会点名它并打开模型文件, 以便删除它的对象; 仪表板把遗留行标记为「外部」, 徽章提示中注明这次重命名。直接在 settings.json 中重命名不会搬动该标签已存储的密钥 - 它们留在旧名称下 ([密钥](#密钥与密钥存储)); 通过仪表板重命名会把它们带过去 |
| 删除条目 | 组无法被删除, 所以扩展*隐藏*它: 记住这次删除, 用空模型列表应答该组 (模型离开选择器), 把该行折叠进仪表板的「隐藏的组」一行并提供「取消隐藏」操作。删除通知点名该组并打开模型文件以便永久删除 |
| 重新添加标签和基础 URL 相同的条目 | 它隐藏的组自行回归 |

模型文件是 `<profile>/User/chatLanguageModels.json` - 一个有文档说明、用户可编辑的 JSON 文件。VS Code 在启动时读取它并驻留内存, 因此编辑后请退出或重新加载窗口; 运行中的窗口可能覆盖外部编辑。

## 外部服务器与采用

组是在本扩展之外添加的服务器 (VS Code 自己的模型管理界面 - 模型选择器中的 "Manage LiteLLM Provider" 流程 - 或其他工具) 仍然可用; 由于没有设置条目, 仪表板把它们标记为「外部」。当扩展知道来历时, 徽章的悬停提示会说明该行来自哪里 - 已删除条目的遗留 (注明名称), 或重命名的遗留 (注明新旧标签)。

外部行提供两个操作:

- **删除**会隐藏该组, 与删除声明条目相同; 后续通知会打开模型文件以便永久删除。
- **编辑**会把该组采用进设置:

1. 在外部行上单击「编辑」- 那就是采用操作。
2. 选择条目的标签。表单会预填该组当前的标签, 但通常值得重命名: 名称仍被某个现有组占用的条目, 在该组的对象从模型文件中删除之前无法同步。
3. 选择每个密钥的存放位置 (密钥存储或内联)。凭据值在扩展内部复制, 从不经过仪表板页面。
4. 保存: 该组的连接详情成为一个新的 `servers` 条目, 像任何声明的条目一样可编辑。
5. 从模型文件中删除原组的对象并重新加载 (采用无法删除它); 在那之前它的模型会出现两次 - 采用之后仪表板会提醒你。

## 多台机器与 Settings Sync

- `servers` 设置是机器作用域的; Settings Sync 从不携带它。密钥存储中的值同样不同步。在第二台机器上, 重新添加服务器及其密钥。
- 其他每个 `litellm-vscode-chat.*` 设置都正常同步 - 包括 `models.parameters` 和 `models.capabilities`, 所以你的模型配置会跟着你走。在服务器尚未重新添加的机器上, 这些同步来的记录只是没有模型可匹配 - 它们静静待命, 服务器一到位就立即生效。任何绑定服务器的东西 (凭据、自定义标头、预算) 都存放在条目上, 按设计留在原地。
