# 用量与预算

[English](../usage.md) | 简体中文 | [繁體中文](../zh-tw/usage.md)

当 LiteLLM 服务器跟踪支出时, 扩展会把它呈现出来: 你的密钥相对其预算花了多少、预算耗尽前的警报、一个不碍事但关键时刻会出现的状态栏项, 以及一个展示全貌的仪表板面板。这里的一切都是只读的 - 扩展从你的服务器读取支出数据, 从不更改预算、密钥或服务器侧的任何东西。支出数据也从不写入扩展的日志或 Bug 报告; 它只存在于你和你的服务器之间。

四个设置驱动全部, 每个都在下文的上下文中详述:

| 设置 | 默认值 | 一句话 |
|---|---|---|
| [`usage.pollInterval`](settings.md#参考) | `300000` 毫秒 | 后台多久获取一次支出; `0` = 关闭 ([轮询](#轮询)) |
| [`usage.alertThresholds`](settings.md#参考) | `[0.8, 0.95]` | 触发通知的预算比例 ([警报](#警报)) |
| [`usage.statusBar`](settings.md#参考) | `"always"` | `always` / `alerts-only` / `off` ([状态栏](#状态栏)) |
| 条目的 [`budget`](servers.md#条目参考) | 未设置 | 按服务器的手动预算 (美元) ([预算](#预算)) |

## 要求

用量功能需要带数据库运行的 LiteLLM 服务器 - 支出跟踪和[虚拟密钥](https://docs.litellm.ai/docs/proxy/virtual_keys)的标准配置。扩展最多读取三个终结点, 始终只查询自己的密钥 (服务器条目用来做身份验证的那把), 以及在密钥归属于某用户时该用户自己的汇总 - 从不枚举其他密钥或用户:

| 终结点 | 扩展读取什么 |
|---|---|
| `/key/info` | 调用密钥的支出、`max_budget` 和 `budget_reset_at` |
| `/user/daily/activity` | 最近 30 天的请求数、成功率和缓存读取 token 计数 |
| `/user/info` | 所属用户的支出、`max_budget` 和 `budget_reset_at` - 仅当 `/key/info` 报告密钥归属于某用户时才读取 |

在没有数据库的服务器上, 这些终结点不存在。扩展检测一次后就为该服务器静默隐藏所有用量界面: 没有仪表板区块、没有状态栏项、没有警报、没有错误噪音、没有需要配置的东西。可用性按服务器判断, 所以混合部署也没问题 - 用量恰好出现在数据存在的地方。

这个检测结果会一直沿用: 后台轮询不会重新检查已判定缺失的终结点。之后补上数据库时, 运行 "LiteLLM: Refresh Usage Now" - 或编辑该服务器的条目 - 扩展就会重新探测可用性。

被服务器拒绝的密钥是另一种情况。当 `/key/info` 或 `/user/daily/activity` 回答 401 或 403 (无权读取用量数据的密钥) 时, 扩展同样把它当作永久状态 - 但权限是你能修复的, 所以当这种拒绝让一个服务器完全没有可读的用量数据时, 该服务器不会被隐藏: [用量面板](#用量面板)保留它的行, 标注「用量访问被拒绝」, 展开后点名被拒绝的端点和 HTTP 状态码。这一行没有数字可显示 - 没有支出计量条, 该服务器也永远不会触发警报; 密钥权限调整后, 运行 "LiteLLM: Refresh Usage Now" (或编辑该条目) 重新探测。只在一个端点被拒绝而另一个端点正常应答的密钥仍得到常规行, 被拒绝的部分写在它所阻断的那条事实上。下面的 curl 测试能区分两种形态: 缺数据库回答的是路由错误, 受限密钥回答的是 401 或 403 - 此时的修复是一把允许读取自己用量的密钥, 而不是数据库。

要检查服务器支持什么, 问它扩展问的同一个问题:

```bash
curl -s -H "Authorization: Bearer $YOUR_LITELLM_KEY" https://litellm.example.com/key/info
```

有数据库支撑的服务器回答带 `spend` 和 `max_budget` 字段的 JSON; 没有数据库的服务器回答错误, 因为没有数据库时该路由不提供。如果 curl 成功但扩展什么都不显示, 检查条目的密钥是不是你测试用的那把 - 数据是按密钥的。而且那是密钥在服务器侧的总数: 通过那把密钥消费的每个客户端都计入其中, 不只是 VS Code。

可用性除了按服务器, 还按终结点: 一个服务器 (或你的密钥在它上面) 可能回答 `/key/info` 但不回答 `/user/daily/activity`。此时[用量面板](#用量面板)显示支出和预算, 但没有请求统计 - 这在某些配置上是正常形态, 不是错误。

## 预算

预算可以来自两个地方:

- **密钥报告**: LiteLLM 存放在密钥本身上的 `max_budget`, 创建密钥时在服务器侧设置。`/key/info` 连同当前支出一起报告它。
- **条目的 `budget` 字段**: [服务器条目](servers.md#条目参考)上的手动数字 (美元, 大于 0):

```jsonc
"litellm-vscode-chat.servers": [
  {
    "label": "prod",
    "baseUrl": "https://litellm.example.com",
    "auth": { "apiKey": "sk-..." },
    "budget": 50
  }
]
```

两者都存在时, 条目的值是**生效预算**: 百分比和[警报](#警报)都相对它计算, 而每个显示预算的界面都会两者并列 (`预算 $50 - 密钥报告 $100`), 服务器侧的上限永不从视野中消失。条目字段为两种情况而存在: 服务器没有给 `max_budget` 的密钥, 以及设在服务器硬上限之下的个人警戒线。

有支出数据但两个来源都没有预算的服务器, 显示支出而不显示百分比, 也永不警报 - 没有可计算比例的东西。

预算旁显示的重置日期是密钥的 `budget_reset_at`: LiteLLM 将在何时为下一周期把支出归零。重置后, 支出回落, 已触发的[警报](#警报)自行重新武装。回落在下一次获取时才可见 - 后台轮询、打开仪表板, 或 "LiteLLM: Refresh Usage Now" - 而不是重置瞬间; 没有重置计划的密钥就不显示重置日期。

值得知道的边界情况:

- **条目的 `budget` 需要支出数据来衡量。**在不提供用量数据的服务器上它不改变任何事 - 用量界面照样隐藏。
- **高于密钥上限的条目 `budget` 会让警报失效。**条目的值无条件胜出, 所以在上限 $100 的密钥上设 `budget` 为 $200, 每个百分比都相对 $200 计算 - 服务器在 $100 就切断密钥, 第一条警告还没来得及触发。扩展无法调高服务器侧的 `max_budget`: 想在上限之前被提醒, 请把条目的值保持在上限或其之下, 或干脆不设, 让密钥自己的数字驱动。
- **支出可以越过预算。**扩展是只读的, 从不拦截请求; 密钥越过 `max_budget` 后服务器是否继续服务, 是 LiteLLM 的策略, 不是扩展的。每个阈值都不超过 1, 所以越过预算的支出位于最高阈值之上: 错误背景, 所有警报都已触发。
- **数据跟着密钥走, 不跟条目。**轮换条目的凭据会把它的数字切到新密钥的支出和预算。用同一把密钥做身份验证的两个条目各自显示那把密钥的支出 - 由于[状态栏](#状态栏)取最大值而非求和, 共享的支出不会在那里被重复计算。

## 轮询

`usage.pollInterval` (毫秒, 默认 `300000` - 5 分钟) 驱动一个后台轮询器, 让警报和状态栏在仪表板关闭时也工作。负值钳制为 `0`; 低于 `30000` (30 秒) 的非零值向上钳制到它, 所以最快的节奏是每个服务器每 30 秒获取一次。

单次获取失败照常在下一次轮询重试, 但持续失败的终结点 - 不再应答的服务器, 或从来不是 LiteLLM 代理的地址 - 会被越来越少地重试, 等待时间逐次翻倍, 最多到轮询间隔的 16 倍。第一次成功自行恢复正常节奏, "LiteLLM: Refresh Usage Now" 或编辑该服务器的条目则立即重试。

`0` 完全关闭后台轮询:

- 不发出后台请求, 不触发警报。
- 仪表板每次打开时仍会获取新数据。
- "LiteLLM: Refresh Usage Now" 仍会在你运行它时立即获取。

**新鲜度。**服务器的用量数据在最近一次获取成功且距今不足两个轮询间隔时算*新鲜*; 轮询关闭时, 按需获取的数据保鲜十分钟 (默认间隔的两倍), 而 "LiteLLM: Refresh Usage Now" 总是产生新鲜数据。数据一旦过期 - 服务器不再应答, 或窗口期用完 - 扩展在[用量面板](#用量面板)继续显示最后已知的值, 标注其年龄: 展开行的「上次更新」一栏对单纯变旧的数据读作「25 分钟前 - 可能已过时」, 原因已知时则点名原因 (「上次刷新失败」, 或密钥失去权限时的「用量访问被拒绝」)。消费数据从未加载成功的行则显示「此服务器的消费数据尚未加载。」而不是年龄。[状态栏](#状态栏)会把过期的服务器从聚合中剔除, 而不是把旧数字当作当前值展示。

同一规则覆盖离线或休眠过的机器: 睡眠期间没有轮询, 所以醒来时超过两个间隔的数据都算过期 - 面板带年龄地继续显示, 状态栏项则保持隐藏, 直到下一次成功获取替换它。

- 报告 `max_budget: 0` 的密钥算作没有预算 (LiteLLM 的「零即无限」惯例); 服务器条目的 `budget` 必须是正数 - 零或负值作为配置诊断报告并忽略。

## 警报

`usage.alertThresholds` 是生效预算的比例列表, 每个大于 0 且不超过 1; 达到阈值就算越过 (在 80.0% 时 0.8 的警报触发, `[1.0]` 阈值在支出等于预算时触发)。超出范围的值被丢弃并作为配置诊断报告。默认的 `[0.8, 0.95]` 在 80% 警告一次, 95% 再警告一次。列表会替你去重和排序; 空列表关闭警报。

- 越过阈值时, 每个服务器每个阈值只显示**一条**通知 - 每五分钟轮询一次不等于每五分钟弹一次。当一次轮询一举越过多个阈值时, 只有最高的触发。所有预算通知使用同一严重级别; 逐级升色的故事在[状态栏](#状态栏)。
- 已触发的阈值在支出回落到其下方时重新武装: 新的计费周期、调高的预算, 警报就再次待命。
- 警报在每次获取时评估 - 后台轮询和手动刷新一视同仁; 揭示出越线的 "LiteLLM: Refresh Usage Now" 会立即弹出通知。每服务器每阈值一次的规则依然适用。

在 $50 生效预算和默认值下, 你会在 $40 和 $47.50 收到扩展的消息 - 然后直到预算重置前不再打扰。

更短的列表工作方式相同, 只在[状态栏](#状态栏)上有一处细节: 那里的严重程度以*配置的最高*阈值为顶, 所以像 `[0.5]` 这样只有一项的列表, 那一个阈值就是警报器 - 越过它直接进入错误背景。另一端, `[1.0]` 让扩展在预算几乎耗尽之前保持沉默。

## 状态栏

`usage.statusBar` 控制一个刻意精简的状态栏项, 坐在 [LiteLLM 连接项](dashboard.md#状态栏项)旁边:

| 值 | 行为 |
|---|---|
| `"always"` (默认) | 只要有东西可显示就可见 |
| `"alerts-only"` | 阈值触发前隐藏, 触发期间可见 |
| `"off"` | 从不显示 |

该项的文本只有一样东西: **最差新鲜服务器**的支出百分比 - 在有[新鲜数据](#轮询)且有预算的服务器中, 支出对生效预算比率最高的那个。其余一切都在工具提示里。

| 情况 | 该项显示 |
|---|---|
| 每个新鲜服务器都在阈值之下 (`"always"`) | 最差百分比, 普通样式 - 例如 `42%` |
| 任何新鲜服务器越过最低阈值 | 警告背景上的百分比 |
| 任何新鲜服务器越过最高阈值 | 错误背景上的百分比 |
| `"alerts-only"`, 没有越过阈值的 | 什么都不显示 |
| 没有服务器有预算, 或 `"off"` | 什么都不显示 |
| 完全没有新鲜数据 | 什么都不显示 |

使用自定义阈值列表时, 严重程度刻度以配置的最高阈值为顶: 越过最高的得到错误背景, 越过任何更低的得到警告背景 - 所以单阈值列表被越过时直接进入错误背景; 它就是警报器。

超过 100% 时, 该项显示字面数字 (`112%`) - 面板的计量条只是填满, 真实百分比在它旁边, 超支金额写在该行上 (「超出预算 $3.00」)。

最后一行是新鲜度规则在履职: 该项从不把过期数字当作当前值显示。过期的服务器被排除在聚合之外并在工具提示中注明; 当*没有*服务器有新鲜数据时, 该项整个隐藏 - 连接项已经在讲故障的故事, 第二个红色的东西不会增加任何信息。

工具提示携带完整的按服务器明细: 支出、两个预算、百分比、重置日期、还有多少*其他*服务器越过阈值, 以及数据上次更新时间。单击该项打开[用量面板](#用量面板)。

上述规则隐含的边界情况, 明说出来:

- **数字可能在两次更新之间跳变。**最差服务器在每次轮询时重算, 所以百分比可能切到*另一个*服务器的比率, 而不只是沿一个服务器的支出上下移动; 工具提示的明细显示当前数字背后是哪个服务器。
- **百分比从不相加。**该项是跨服务器的最大值: 两个各花一半的预算显示为两者中较大者, 而不是 100%。
- **`"alerts-only"` 同样遵循新鲜度。**当唯一越线服务器的数据过期时, 该项隐藏, 尽管预算多半仍然是花掉的状态 - 等新鲜数据确认了状态它才回来, 无论确认成哪边。面板期间继续显示最后已知的值。
- **`"off"` 只隐藏该项, 别的什么都不动。**警报照常触发, 用量面板照常工作; 该设置只控制一个状态栏项。

## 用量面板

仪表板的[用量区块](dashboard.md#用量区块)是全貌所在。每个有用量数据的服务器是**一行**: 标签、支出对生效预算、一条支出计量条、百分比, 以及此刻在该服务器上最要紧的那件事 - 请求数, 或要处理的问题 (「用量访问被拒绝」「上次刷新失败」「可能已过时」「超出预算 $3.00」)。区块标题统计列表并说明多少行需要处理, 它的**立即刷新**按钮立即获取, 获取进行中自我禁用。

展开一行会列出扩展所知关于该服务器的一切, 每行一条带标签的事实: 基础 URL、支出、**预算**及其来处 (条目还是密钥, 两者不同时还有密钥自己的数字)、**下次重置** (`budget_reset_at`)、当服务器提供 `/user/daily/activity` 时最近 30 天 (UTC 日历日, 含今天) 的**请求数、成功率和缓存命中率**, 以及数字的**上次更新**时间。

服务器没有报告的字段呈现为一个暗淡的短横线**加就地写明的原因** - 「密钥未报告重置日期」「此服务器不提供 /user/daily/activity (在某些部署中属正常情况)」- 从不是零, 因为零是一次测量, 而这里没有测量发生。扩展因密钥被拒而完全读不到用量的服务器保留它的行, 展开时说明阻断: 发生了什么、什么能解除, 以及被拒绝的端点和 HTTP 状态码 - 没有数字 (见[要求](#要求))。

打开仪表板会获取新数据, 即使[轮询](#轮询)已关闭。当服务器的数据过期时, 它最后已知的值留在屏幕上, 该行标注「可能已过时」- 你仍能读到的历史, 清楚地标成历史; 过期原因已知时, 标注会改为点名原因 (「上次刷新失败」「用量访问被拒绝」), 展开行内还有一行点名终结点和状态码的紧凑技术信息。

## 命令

| 命令 | 作用 |
|---|---|
| LiteLLM: Refresh Usage Now | 立即获取每个服务器的支出数据, 不受 `usage.pollInterval` 约束, 并重新检查每个服务器的用量可用性 |
| LiteLLM: Open Dashboard | 打开仪表板; 用量区块一步之遥 (或经状态栏项直达) |
