# 故障排除

[English](../troubleshooting.md) | 简体中文 | [繁體中文](../zh-tw/troubleshooting.md)

本页按症状索引: 找到你正在看到的现象, 每个条目会说它意味着什么、如何修复, 以及完整故事在哪里。扩展把状态放在你看得见的地方 - 连接一个状态栏项、用量一个、细节在仪表板的诊断区块、完整日志在输出通道 - 下文没有匹配项时就从那里开始。

## 状态栏

两个项坐在右下角。左边是**连接项** - 它回答「我现在能聊天吗?」:

| 项 | 状态 | 含义 |
|------|--------|---------|
| `$(warning) LiteLLM` | 未配置 | 没有配置服务器 - 单击进行设置 |
| `$(loading~spin) LiteLLM` | 正在加载 | 正在从服务器获取模型 |
| `$(check) LiteLLM` | 已连接 | 所有服务器可达; 工具提示携带模型数量 |
| `$(warning) LiteLLM` | 已降级 | 部分服务器不可达; 工具提示说明可达的服务器提供多少模型 |
| `$(error) LiteLLM` | 错误 | 所有服务器都失败了 - 诊断区块有每个服务器的错误 |

单击它打开[仪表板](dashboard.md); 诊断区块有每服务器的细节。

它旁边的**用量项**回答「我离预算还有多近?」- 最差服务器的支出百分比:

| 它显示 | 含义 |
|----------|---------|
| 普通百分比, 例如 `42%` | 每个服务器都在其警报阈值之下 |
| 警告背景上的百分比 | 某服务器越过了最低阈值 (默认 80%) |
| 错误背景上的百分比 | 某服务器越过了最高阈值 (默认 95%) |
| 什么都不显示 | 没有新鲜的预算数据 (故障由连接项负责提示)、用量功能不适用于你的服务器, 或 `usage.statusBar` 隐藏了它 |

单击它打开仪表板的[用量区块](dashboard.md#用量区块)。预算、阈值和轮询如何配合, 在[用量](usage.md#状态栏)页面。(只配置了一个阈值时, 它既是最低也是最高, 所以越过它直接进入错误背景。)

所以: **左边红**意味着请求过不去 - 按下面的[常见问题](#常见问题)排查。**右边红**意味着请求畅通但预算快花完了 - 见[用量: 警报](usage.md#警报)。

## 诊断工具

| 工具 | 它给你什么 |
|------|-------------------|
| "LiteLLM: Test Connection" (命令面板) | 端到端验证服务器: 连接、报告找到的模型数量、失败时显示详细错误消息, 并更新状态栏。仪表板的「测试连接」按钮对保存前的草稿条目做同样的事 |
| "LiteLLM: Show Diagnostics" | 把仪表板打开到诊断区块: 整体状态、已配置服务器数量、上次检查时间戳, 以及每个服务器一行结果及其 URL |
| 「LiteLLM」输出通道 | 完整日志: 配置变化、模型获取尝试及结果、带完整细节的错误。打开输出面板 (`Ctrl+Shift+U` / `Cmd+Shift+U`), 从下拉列表选择 "LiteLLM" |
| 仪表板的检查器 | 按模型显示哪个来源设置了每个参数和能力字段 - 「这个值为什么是这个」问题的专用工具 ([模型: 检查器](models.md#检查器)) |
| "LiteLLM: Help & Feedback" | 报告 Bug、请求功能或打开文档的快捷入口 |

## 常见问题

### 「聊天界面或 "Manage Models..." 不见了」

本扩展接入的是 GitHub Copilot Chat; 没有它就没有聊天视图, 也没有模型选择器。

- 安装 GitHub Copilot Chat 扩展, 登录 GitHub, 并确保它已启用。
- VS Code 较旧时请更新: 扩展需要 1.129.0 或更高版本。
- 在处于受限模式的窗口中 (不受信任的文件夹), VS Code 会整个禁用本扩展: LiteLLM 命令、状态栏项和已注册的模型全部消失, 直到你信任该工作区。

### 「连接错误: 无法连接」

基础 URL 上没有任何东西应答。

- 核实基础 URL 正确 (例如 `http://localhost:4000`), 且你的 LiteLLM 代理正在运行。
- 以 `/v1` 结尾的 URL 没有问题: 只有当 URL 尚未以 `/v1` 或 `/v2` 这样的版本段结尾时, 扩展才会追加 `/v1`; 每服务器的 `apiVersion` 字段可覆盖两者 (空字符串 = 什么都不追加)。
- 检查 VS Code 与服务器之间的防火墙、VPN 或代理设置。

[条目参考](servers.md#条目参考)记录了基础 URL 规则。

### 「SSL 证书错误」

VS Code 无法与基础 URL 建立可信的 HTTPS 连接; 扩展没有绕过证书验证的设置。

- 「... 的 SSL 证书已过期」: 请你的 LiteLLM 服务器管理员续期证书。
- 其他任何证书问题会显示「无法验证服务器的 SSL 证书, 连接已被阻止」, 下方的详细信息行 (`SSL certificate error for ...`) 点名服务器和 TLS 失败 - 自签名或内部 CA 证书, 在企业部署上很常见: 把 CA 加入操作系统的信任存储, 或用指向 CA 证书包的 `NODE_EXTRA_CA_CERTS` 启动 VS Code。信任决定属于 VS Code 的运行时, 不属于本扩展。

### 「身份验证失败」

两种 401 消息点名的是不同的凭据:

- 单纯的**「身份验证失败: 你的 LiteLLM 服务器需要 API 密钥」**意味着代理拒绝了扩展的凭据。编辑该服务器 (仪表板, 或 `servers` 设置) 并更新它; 对照你的 LiteLLM 代理配置核实密钥。对于没有条目的[外部组](servers.md#外部服务器与采用), 凭据归 VS Code 所有 - 通过模型选择器的 "Manage LiteLLM Provider" 流程更新它, 或采用该组。
- **「上游身份验证失败」**意味着代理接受了你的密钥, 但无法向模型的上游提供方进行身份验证; 更新扩展的密钥帮不上忙。请在 LiteLLM 服务器上修复那个提供方的凭据, 或请服务器运营者修复。

两个设置错误看起来像身份验证失败:

- `auth` 对象带有含混不清形态的条目 (比如 `apiKey` 和 `oauth` 并排) 按配置错误处理, 仪表板的服务器行会指出; 不会在凭据之间乱猜。恰好保留一种形式 - 真正同时检查两个凭据的网关, 需要的是级别更低的伴随凭据 (`auth.oauth` 内部, 或 `auth.apiKey` 旁边的 `virtualKey`)。见[服务器: 身份验证](servers.md#身份验证)。
- 期望密钥出现在自定义标头中的网关 (例如 `x-litellm-api-key`) 会拒绝标准 bearer 形式; 用 `auth.virtualKey` 配上它想要的标头名。

### 「服务器无法识别此请求」/「回答了 404 - 它有应答, 但不提供 LiteLLM API」

那个地址上有东西应答, 但不是 LiteLLM 代理 - 或者没有这个模型。聊天请求上的错误显示上面的标题, 下方的详细信息行 (`详细信息: LiteLLM 404 ...`) 引用服务器的应答。

- 检查那里实际在监听什么 - 一个网页服务器、别的服务, 或错误的端口 (LiteLLM 代理默认是 4000)。
- 以 `/v1` 或 `/v2` 这样的版本段结尾的基础 URL 按原样使用; 否则扩展会追加 `/v1`。因此 404 意味着地址在别的方面不对: 路径前缀不同、端口错误, 或服务器根本不提供 LiteLLM API。每服务器的 `apiVersion` 字段可强制指定版本段 (空字符串 = 什么都不追加)。
- 先前正常的服务器在聊天请求上返回 404, 通常意味着该模型已从代理移除: 运行 "LiteLLM: Sync Models Now" 刷新模型列表。如果每个请求都以 404 失败, 按上文检查基础 URL。

### 指向 Ollama、vLLM 或普通 OpenAI 兼容服务器

本扩展为 LiteLLM 代理而建, 所以发现会先请求 LiteLLM 的 `/v1/model/info` (能力、定价), 再回退到普通 OpenAI 的 `/v1/models` 列表。只提供其中一部分接口的服务器也能正常工作 - 只需把缺失的终结点声明出来, 让该失败不再算作问题。被声明的终结点每次同步仍会探测一次 (挂起的终结点会等满一次 `discovery.timeout`), 所以如果同步太慢, 也请调低该设置。三种模式:

- **没有 `/v1/model/info` (Ollama、vLLM、LM Studio 及多数 OpenAI 兼容服务器)。** 模型仍会经回退出现, 但每轮新的发现都要先为注定失败的模型信息探测买单 - 在 Ollama 上该请求会挂起直到发现超时, 所以调大 `discovery.timeout` 只会更糟。仪表板的服务器行会说明:「可以提供其模型, 但其模型信息探测永远不会应答, 每次同步都要等满发现超时。将该失败声明为预期, 即可把它标记为此服务器的正常情况。」(当服务器以 404/405 应答而非挂起时, 提示会点名缺失的终结点); 它的「声明预期失败」按钮会写入该声明, 也可以手动添加:

```jsonc
"litellm-vscode-chat.servers": [
  {
    "label": "Ollama",
    "baseUrl": "http://localhost:11434",
    "discovery": { "expectedFailures": ["modelInfo"] }
  }
]
```

- **连 `/v1/models` 也没有, 或完全无法列出模型。** 当列表失败而服务器在其他方面有应答时, 错误会建议对称的声明 -「模型列表获取失败, 但此服务器有响应。如果它从不提供模型列表, 请在 ... 条目上声明」- 服务器行也提供同样的一键「声明预期失败」。声明 `"modelListing"` (或两个类别都声明), 并在 `discovery.declared` 中自行列出模型; 完整配方见[服务器: 发现与预期失败](servers.md#发现与预期失败):

```jsonc
{
  "label": "my-gateway",
  "baseUrl": "https://gateway.example.com",
  "discovery": {
    "expectedFailures": ["modelListing", "modelInfo"],
    "declared": ["gpt-5", "deepseek-r1"]
  }
}
```

- **两个终结点都没有应答。** 错误显示为「位于 ... 的两个发现终结点都没有应答 - 该地址看起来不是 LiteLLM 或 OpenAI 兼容的 API。」这里没有任何声明能帮上忙: 请检查基础 URL 和端口 (LiteLLM 代理默认为 4000, Ollama 为 11434), URL 的解析规则见上文的 404 条目。

声明到底改变了什么: 被点名的终结点每轮只尝试一次 (不重试), 其失败按预期记录而不再报警 - 对模型列表来说, 失败也不再算作故障; 模型信息探测的失败本来就不致命 (发现总会回退), 声明主要是让日志安静下来并撤下仪表板的提示。除此之外什么都不变。而没有 `/v1/model/info` 时失去的是元数据, 不是聊天: 能力与定价字段不会到达, 所以重要的字段请通过 [`models.capabilities`](models.md#能力) 补上 (知名模型 ID 由 OpenRouter 目录自动回填)。想恢复完整元数据 - 以及多提供方路由 - 的替代方案是在该服务器前架设一个 LiteLLM 代理并把扩展指向它; [LiteLLM 自己的文档](https://docs.litellm.ai/docs/providers/ollama)介绍了如何前置 Ollama 等服务器。

### 模型选择器中没有出现任何模型

先看状态栏 - 它点名故障类别。

- 连接项显示错误或降级状态: 发现在失败; 运行 "LiteLLM: Test Connection" 读取确切错误, 然后与上面的条目对照。
- 一切显示已连接, 但最近添加的模型不见了: 发现的列表有缓存 (`discovery.cacheTtl`, 默认 1 小时)。运行 "LiteLLM: Sync Models Now" 绕过缓存。
- 网关根本无法列出模型 (没有 `/v1/models`): 用 `discovery.declared` 在条目上声明它们, 并在旁边加上 `discovery.expectedFailures`, 让缺失的终结点不再算作故障。配方: [服务器: 声明的模型](servers.md#声明的模型)。
- 你之前确实见过的模型上有警告图标, 意味着后台刷新失败, 扩展正在提供标记为过期的最后已知列表 - 见[超时与重试](#超时与重试)。
- 一切显示已连接, 你服务器的标签下却什么都没有, 而你的 Copilot 席位来自组织 (Copilot Business 或 Enterprise): 组织的「Bring your own language model key」策略被禁用了。隐藏发生在 Copilot 内部, 所以扩展自己的诊断全都报告成功; 请你的 Copilot 管理员启用该策略, 然后重新加载 VS Code。

### 「服务器返回了 0 个模型」

你的 LiteLLM 代理在运行, 但没有配置任何模型。

- 检查你的 LiteLLM 代理配置 (`litellm_config.yaml`)。
- 运行 `litellm --config your_config.yaml`, 带着模型启动代理。

### 「我的嵌入或图像生成模型没有出现在选择器中」

LiteLLM `model_info.mode` 指向非聊天终结点 (`embedding`、`image_generation`、`audio_speech`、`audio_transcription`、`rerank`、`moderation`) 的模型被有意排除在聊天选择器之外, 因为对它们的聊天请求只会失败; 未声明 mode 的模型始终注册。代理已暂停的部署 (`model_info.blocked`) 同样被跳过。见[模型: 模型如何出现](models.md#模型如何出现)。

### 「模型不接受图像, 或从不使用工具」

能力门控提供什么和发送什么: 图像只发给声明视觉支持的模型, 使用工具的请求只发给声明工具调用的模型。当有能力的模型在服务器侧的声明缺失或错误时, 覆盖它:

```jsonc
"litellm-vscode-chat.models.capabilities": {
  "qwen2.5-vl-72b": { "supports_vision": true }
}
```

在没有视觉支持的模型上, 文本照常通过, 图像被丢弃, 「LiteLLM」输出通道记一条说明。对知名的模型 ID, OpenRouter 目录经常自动填补这些空缺。见[模型: 能力](models.md#能力)。

### 「此对话对于该模型来说似乎过长」

当扩展自己的 token 估计超过模型的输入预算时, 它在发送前拒绝请求; 标题下方的详细信息行为「详细信息: 发送前已超出 token 限制: 本地估计 N 个 token (消息 + 工具), 输入限制 M」。计数是本地估计 (文本约四字符一个 token, 图像、PDF 或音频剪辑按固定数字计), 所以可能与服务器实际计费不同。

- 精简对话或去掉附件, 或者
- 当真实模型能接受的比限制 `M` 说的更多时, 调高预算。限制来自模型声明的输入限制 (服务器报告、目录, 或你的覆盖); 在 `models.capabilities` 中纠正它:

```jsonc
"litellm-vscode-chat.models.capabilities": {
  "my-model": { "max_input_tokens": 100000 }   // 或修正 context_length
}
```

键是精确匹配的; 用 `"*"` 为每个模型设置底线。(旧版本为此提供 `defaultContextLength` / `defaultMaxInputTokens` / `defaultMaxOutputTokens` 设置; 它们没有了, 已自动迁移进一个 `"*"` 记录。) 见[模型: 能力](models.md#能力)。

### 「我配置的参数没有生效」

不要猜 - 打开仪表板的模型页面, 查看该模型的参数[检查器](models.md#检查器): 它显示每个生效字段以及究竟是哪个来源设置了它。它通常揭示的是:

- **键匹配不上。**键默认精确: `"gpt-5"` 只匹配 `gpt-5`, 不匹配 `gpt-5-turbo`。家族键需要尾部的 `*`。见[模型匹配](models.md#模型匹配)。
- **正则键锚定整个 ID。**`"/gpt-5/"` 只匹配字面 ID `gpt-5`, 不匹配 `my-gpt-5-deployment` - 斜杠包裹的模式必须匹配整个模型 ID, 而不是它的子串。要做包含匹配, 写 `"/.*gpt-5.*/"`。无效的模式 (或 `i` 之外的任何标志) 会在仪表板中报告, 该键被忽略。
- **更宽的键没有流入。**默认情况下最具体的匹配记录整体胜出 - `"*"` 或 `"gpt-5*"` 的值只有在标记了 `_inheritable` (且中间没有 `_inherit_from: false` 屏障) 时才到达更具体的匹配; 服务器条目的记录逐字段胜过全局设置。查看诊断区块的继承树, 然后见[模型 - 匹配](models.md#哪条记录生效)。
- **运行时选项排在你前面。**请求时传入的选项 (Copilot 或聊天工具) 和[选择器的每模型配置](models.md#选择器)胜过配置的记录。要不管不顾地钉住一个字段, 标记为强制: `"gpt-5*": { "_force": ["temperature"], "temperature": 1 }`。见[模型: 参数](models.md#参数)。
- **就算被强制的字段, 也需要它的记录参与。**`_force` 只有在携带它的记录参与该模型的解析时才胜过运行时选项: 当更具体的记录胜出且不继承被强制的字段时, 强制永远到不了请求 - 诊断树会显示它停在哪里。而提供程序拥有的键 (`model`、`messages`、`stream` 等) 根本不能强制; 那样的 `_force` 会被报告并忽略。
- **条目的记录可能未生效。**如果服务器在仪表板中的行说条目的按服务器配置可能未应用, 见[下文](#每服务器模型参数未生效)。

### 「模型只产生了推理输出, 而此版本的 VS Code 无法显示它」

你的 VS Code 构建缺少 thinking-part API, 所以流式推理被丢弃 (输出通道有说明), 只包含推理的回复以此错误失败。把 VS Code 更新到支持 thinking part 的版本, 或换用返回最终文本的模型。

## 用量功能缺失

仪表板没有某服务器的用量区块、不显示支出百分比、也没有警报触发。按可能性排序:

- **服务器没有数据库。**LiteLLM 只在有数据库支撑时提供支出数据 (`/key/info`); 没有它, 扩展检测一次后为该服务器隐藏所有用量功能 - 属于设计, 无需配置。从终端核实: `curl -H "Authorization: Bearer sk-..." https://your-gateway/key/info` - 回答错误页而非 JSON 即可确认。之后补上数据库时, 后台轮询不会自己注意到: 运行 "LiteLLM: Refresh Usage Now" 重新检查。
- **密钥读不了用量数据。**在用量终结点上回答 401 或 403 的数据库支撑服务器不显示数字, 但不会被隐藏: 它的行留在用量区块, 标注「用量访问被拒绝」, 展开后写着「用量不可用: 此密钥无权读取其用量数据。」, 并附一行点名终结点和状态码的详细信息。此时上面的 curl 返回的是 401 或 403 而不是错误页; 请密钥的签发者允许它读取自己的 `/key/info`, 然后用「立即刷新」- 扩展不会自己重新检查。
- **轮询关了。**`usage.pollInterval: 0` 禁用后台轮询; 仪表板打开时仍会获取, 没有警报触发, 状态栏项在一次获取后显示按需数据十分钟, 然后隐藏。运行 "LiteLLM: Refresh Usage Now" 立即获取 - 它总能重新点亮该项。
- **警报关了。**空的 `usage.alertThresholds` 列表意味着没有阈值, 所以永远不会触发任何东西, `"alerts-only"` 状态栏模式也永不显示。
- **该项被配置隐藏了。**`usage.statusBar: "off"` 隐藏该项; `"alerts-only"` 只在阈值被越过时显示。
- **哪里都没有预算。**百分比需要预算: 密钥自身的 LiteLLM `max_budget`, 或条目的 `budget` 字段。见[用量: 预算](usage.md#预算)。

一个相关的部分缺失情况: **支出显示了, 但没有请求计数**。行内的请求数、成功率和缓存命中率来自第二个终结点 (`/user/daily/activity`); 服务器不提供它 - 或对你的密钥拒绝它 - 时, 展开的行只显示支出和预算, 缺失数字的位置就地写明原因。可用性按终结点检测, 所以这在某些配置上是正常形态, 不是错误。

完整功能描述在[用量](usage.md#用量面板)页面; 设置及其默认值在[参考](settings.md#参考)。

## 超时与重试

两个超时设置约束什么, 什么会重试:

- **聊天补全从不重试。**补全可能有副作用 (支出、工具调用), 所以扩展呈现失败, 而不是悄悄为第二次尝试付费。因此 `chat.timeout` (默认 5 分钟) 是一个请求可占用的总时间, 含流式传输; 长推理运行被截断时调大它。
- **发现会重试。**模型发现请求是幂等的 GET, 瞬时失败最多重试两次, 整轮 - 含重试和任何 OAuth 令牌交换 - 受 `discovery.timeout` (默认 30 秒) 约束。为缓慢的网关基础设施调大它; 注意缓慢的 OAuth 身份提供方花的是同一份预算, 而且在聊天请求上交换同样受 `discovery.timeout` 约束。
- **预期失败不重试。**条目的 `discovery.expectedFailures` 点名的终结点只尝试一次, 记一条 info 级日志而非红色错误 ([服务器](servers.md#条目参考))。
- **最小值。**两个超时都钳制到至少 1000 毫秒。
- **过期列表宽限。**当后台刷新失败, 但最近一次成功发现仍在 `discovery.staleServeWindow` 之内 (默认十分钟) 时, 扩展继续提供最后已知的模型列表, 以警告图标标记为过期, 而不是在会话中途丢掉你的模型。服务器休眠更久就调大这个窗口; `0` 关闭宽限。

设置的默认值和单位在[参考](settings.md#参考)。

## 服务器缓慢或被打爆

VS Code 重新解析模型提供程序很频繁 - 有时一秒好几次 - 而 `discovery.cacheTtl` (默认 1 小时) 正是防止这变成对你网关的请求风暴的东西。如果你的服务器日志显示扩展在不停地打 `/v1/models`, 那是有人把 TTL 设成了 `0` (每次都新取); 调高它。缓存从不存储失败, 同时发生的刷新共享一个请求, "LiteLLM: Sync Models Now" 随时按需绕过, 所以长 TTL 的代价只是服务器侧模型变化后需要手动同步一次。

## Settings Sync 的意外之处

- **「我的服务器没有跟我到新机器。」**属于设计: `servers` 设置是机器作用域的, Settings Sync 从不携带它, 密钥存储也不同步 - 服务器和凭据留在你录入它们的那台机器上。在新机器上重新添加。见[服务器: 多台机器](servers.md#多台机器与-settings-sync)。
- **「新机器有我的模型设置, 却没有模型。」**同一规则的另一面: Settings Sync 送达每个全局设置 - `models.parameters`、`models.capabilities`、用量阈值 - 但不送 `servers`, 所以记录暂时没有可应用的对象。重新添加服务器, 同步来的记录会随匹配模型的注册自行生效。存放在条目上的一切 (凭据、每服务器记录、标头、`budget` 字段) 需要随之重新输入。
- **「工作区改不了我的服务器。」**同样属于设计: `servers` 只接受用户设置的值, 所以克隆下来的仓库永远无法把你的标签重新指向另一台主机。
- **「那凭据应该放在哪里?」**放在服务器条目里 - 而且只放那里。条目的 [`auth` 形式](servers.md#身份验证) (可用密钥存储) 和它的每条目 `headers` 对象都是机器作用域的, 所以密钥既不会通过 Settings Sync 复制, 也不会落进提交的 `.vscode/settings.json`。每个非服务器设置 (`models.parameters`、超时、用量阈值) 正常同步, 且不携带任何类似凭据的东西。

## 删除或重命名服务器后的遗留组

VS Code 的提供程序组 API 可以创建组, 但永远无法更新或删除它们, 所以删除 `servers` 条目会隐藏它的组 (模型立即离开选择器) 而不是删除它, 重命名条目会把旧组作为「外部」行留下。永久修复始终相同:

1. 打开模型文件 - 通知的按钮, 或手动打开 `<profile>/User/chatLanguageModels.json`。
2. 从 JSON 数组中删除该组的对象。手动编辑前先退出或重新加载 VS Code: 它把文件驻留在内存中, 可能覆盖外部编辑。
3. 重新加载窗口并运行 "LiteLLM: Sync Models Now"。

当你重新添加标签和基础 URL 相同的条目, 或通过仪表板隐藏组的「取消隐藏」操作时, 隐藏的组自行回归。在非英语语言的 VS Code 构建上, 扩展可能识别不出宿主的名称冲突应答: 服务器行随即显示的不是单条可操作的「提供程序组已占用此名称」状态, 而是每轮都重试的一般同步失败 - 修复方法还是同样三步。完整生命周期 - 每个操作留下什么、为什么 - 在[服务器: 生命周期](servers.md#生命周期-重命名删除与隐藏的组); 外部行与采用[也在那里](servers.md#外部服务器与采用)。

## 每服务器模型参数未生效

当服务器条目携带每条目 `models.parameters`, 但服务该服务器的 VS Code 提供程序组可能不携带条目的标签化标识时, 仪表板在该服务器行的下方放一条诊断行 -「可能未应用其按服务器的模型参数」。这发生在组早于条目标签, 或重命名、基础 URL 编辑留下了过期组时; 经过这种组的请求可能只得到全局 `models.parameters` 设置。同一条诊断行也会点名其他每个受影响的部分: 条目的 `models.capabilities`、`discovery.declared` 和 `discovery.expectedFailures`、它的自定义 `headers`, 以及它的 `apiVersion` 覆盖 (请求回退到自动规则); 修复全都相同。

两种修复方式:

- 从模型文件 (`<profile>/User/chatLanguageModels.json`) 删除该组的对象, 重新加载窗口, 运行 "LiteLLM: Sync Models Now"; 扩展会从条目重新创建组, 这次带上它的标识。
- 或者用新标签保存条目; 会为它创建新组。旧组留着, 直到你从模型文件删除它的对象。

## 密钥存储不可用

两条服务器行消息意味着问题出在 VS Code 的密钥存储, 而不是你的服务器:

- **"Reading this entry's stored secrets failed, so it was not synced. Run Sync Models Now to retry."** 这一轮读取失败; 条目只是被跳过, 不是永久失败 - 下一轮 (或 "LiteLLM: Sync Models Now") 会再次读取。
- **"VS Code secret storage could not be confirmed this session, so this entry was not synced. Syncing resumes on the next VS Code session."** 扩展无法确认它的同步状态能在本会话之后留存, 所以宁可什么都不同步, 也不去猜。

两种状态下条目都只是本轮被跳过: 它的活动提供程序组继续提供最近一次同步的模型, 什么都不会丢。常见原因是操作系统的钥匙串或钥匙环不可用 - 在 Linux 上, 没有钥匙环服务 (gnome-keyring、KWallet) 的桌面会话是最常见的情况。恢复钥匙环, 重启 VS Code, 然后运行 "LiteLLM: Sync Models Now"。

## 来自旧版本的设置

如果某个设置在升级后好像消失了, 那是它被重命名或重构了: 一次性迁移自动移动一切 - 设置名进入新区块 (`requestTimeout` 到 `chat.timeout`、`modelParameters` 到 `models.parameters` 等等)、扁平服务器条目进入 `auth`/`models`/`discovery` 形态、`default*` token 设置进入 `models.capabilities` 的 `"*"` 记录、`_declare` 指令进入条目的 `discovery.declared` 列表, 旧的全局 `headers` 设置进入每个条目自己的 `headers` 对象 (无条目可接收的副本留在原地休眠, 附仪表板提示)。无需重新输入任何东西; [重命名表](settings.md#重命名与移除的设置)把每个旧名称映射到新家。

匹配器不再匹配时值得知道的两个迁移效果:

- 记录键以前是隐式前缀; 迁移给每个既有键追加了 `*`, 所以旧键匹配它们以前匹配的东西。只有从现在起你新写的键默认精确 ([模型匹配](models.md#模型匹配))。
- 全局记录中的服务器 URL 限定键移入了匹配的服务器条目。URL 匹配不到任何条目的限定键留在原地 - 休眠, 因为它永远匹配不到模型 ID - 仪表板会标记它并提示移入服务器条目。

## 报告问题

「报告问题」操作会打开预填了诊断信息的 GitHub Issue:

- 扩展和 VS Code 版本、平台和连接状态
- 是否配置了 API 密钥和基础 URL: 是、否, 或当凭据由 VS Code 管理时为未知; 从不包含值本身
- 最近的错误和近期日志行

扩展的日志记录的是所发生事件的分类, 从不记录源自服务器响应的文本, 因此预填的正文不可能泄露你的提示、补全或凭据; 即便如此, Issue 会在浏览器中打开, 供你在提交前审阅。当诊断信息对 URL 而言过大时, 全文改为进入你的剪贴板 (可能时还有一个本地文件), Issue 正文会说明省略了什么。

## 隐私与数据

你的提示、附件和补全只在 VS Code 与你配置的终结点之间传输:

- 聊天和模型发现请求发往你的 LiteLLM 服务器的基础 URL。
- OAuth 凭据只发往服务器条目上设置的令牌终结点。
- 一个默认开启的例外: 扩展约每周从 `https://openrouter.ai/api/v1/models` 刷新一次内置的 OpenRouter 模型目录 - 一个公开的、无需身份验证的模型列表; 该请求不携带提示、不携带用量, 也不携带任何关于你或你的服务器的信息。把 `litellm-vscode-chat.models.openRouterCatalog` 设为 `false` 可停止所有目录网络请求 ([模型: 能力](models.md#能力))。
- 用量轮询只调用你自己服务器的支出终结点, 用条目自己的凭据。
- 扩展没有遥测, 也没有自己的后端; 不向发布者发送任何内容。
- 唯一的另一个出站通道是[问题报告器](#报告问题), 它在本地准备一切, 携带环境细节和扩展自身的日志 (版本、平台、连接状态、错误分类和堆栈 - 从不含提示或响应文本, 从不含密钥值), 并在浏览器中打开, 供你在提交前审阅。

凭据存放在哪里、机器之间同步什么, 见[服务器](servers.md#密钥与密钥存储)。

## 卸载与清理

卸载扩展不会移除两样东西, 所以在意残留凭据的话请先清理:

- 你的 `litellm-vscode-chat.*` 设置留在 settings.json 中, 包括 `servers` 条目中的任何内联凭据 - [`auth` 对象](servers.md#身份验证)和任何每条目 `headers`。在设置编辑器中移除它们, 或从用户 settings.json 删除那些行。
- 服务器同步成的 VS Code 提供程序组归宿主所有, 保留自己那份凭据副本, 直到你移除它们: 从 `<profile>/User/chatLanguageModels.json` 删除它们的对象 (之后退出或重新加载 VS Code)。

存放在 VS Code 密钥存储中的密钥可以在扩展仍安装时移除, 通过编辑表单的「删除已存储的...」复选框 ([服务器](servers.md#密钥与密钥存储)); 卸载之后, 那份存储归 VS Code 的扩展数据处理管辖, 扩展自己的 UI 不再够得到它。
