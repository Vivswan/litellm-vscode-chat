三个概念承载整页。**能力**描述模型*能做什么* - 它们在注册时解析一次, 决定模型被提供来做什么。**参数**是请求*要求它做什么* - 逐请求解析, 随请求上线发出。**声明**是在发现看不见时宣布模型*存在*。三者从不混淆: 能力从不作为请求字段发送, 参数也从不改变模型注册成什么。

## 模型如何出现

### 发现

扩展询问每个已配置的服务器它提供什么 - 在激活时、设置变化时, 以及每当 VS Code 重新解析其模型提供程序时:

- 发现先读 `/v1/model/info` - 携带 token 限制、定价和能力标志的丰富终结点 - 当该调用失败、未返回数据数组, 或返回的条目没有一个可用时, 回退到纯 `/v1/models` 列表。格式良好的空列表注册零个模型, 不触发回退。
- 发现请求是幂等的 GET, 所以瞬时失败会重试; 整轮 - 含重试和任何 OAuth 令牌交换 - 受 `discovery.timeout` (默认 30 秒) 约束。重试规则详情: [故障排除](troubleshooting.md#超时与重试)。
- *预期*某终结点失败的服务器 (没有模型列表的网关) 在条目的 `discovery.expectedFailures` 里说明: 单次尝试、一条 info 级日志、没有错误噪音。见[服务器](servers.md#发现与预期失败)。
- 结果会复用 `discovery.cacheTtl` (默认 1 小时), 因为 VS Code 重新解析提供程序很频繁 - 有时一秒好几次。失败从不缓存, 同时发生的刷新共享一个请求, "LiteLLM: Sync Models Now" 在你需要立即拿到新列表时绕过缓存。
- 当后台刷新失败, 但最近一次成功发现距今不足十分钟时, 最后已知的模型保持可用, 标记为过期 (警告图标加悬停说明), 而不是在会话中途从选择器里消失。

### 声明的模型

发现不是唯一入口: 服务器条目的 `discovery.declared` 列出即使服务器列不出也要注册的精确模型 ID, 而发现开始列出某个 ID 后, 对应声明转为休眠。声明模型和描述模型是两个独立步骤 - 声明模型的[能力](#能力)与每个被发现模型一样, 从相同来源解析, 它在[仪表板的模型表格](dashboard.md#模型)中带「已声明」徽章。完整的故事, 包括无发现能力网关的单对象配方, 在[服务器 - 声明的模型](servers.md#声明的模型)。

### 哪些模型会注册

可达服务器报告的每个可聊天模型都会出现在选择器中。三条排除规则:

- `model_info.mode` 指向非聊天终结点 (`embedding`、`image_generation`、`audio_speech`、`audio_transcription`、`rerank`、`moderation`) 的模型被有意排除, 因为对它们的聊天请求只会失败。未声明 mode 的模型始终注册。
- 代理已暂停的部署 (`model_info.blocked`) 被跳过。
- 其他不做任何过滤: 完全没有能力数据的模型照样注册, 空缺由下文的[能力来源](#能力优先级)填补。

### 负载均衡池

当一个模型名由多个部署提供 (负载均衡池) 时, 它注册一次, 采用最严格贡献者的 token 限制, 这样请求绝不会超出实际服务它的那个部署。这次合并与 [`max_tokens` 例外](#max_tokens-例外)相关: 合并后的输出限制只有在每个部署都声明了输出限制时才算已声明。

同样保守的合并不止于 token 限制: 池只有在每个部署都声明某项能力时才对外宣布它 - 一个部署声明关闭工具调用, 池就失去它; 一种模态 (视觉、音频) 只有在所有部署都具备时才留存; 「思考力度」控件只在每个部署都声明推理时出现。定价只在每个部署逐字段声明完全一致的成本时显示 (不一致时, 请求实际花多少由代理的路由决定, 所以选择器宁可不显示, 也不显示错误数字); 选择器的提供方名称跟随第一个部署。被合并丢掉的能力可以用 [`models.capabilities` 覆盖](#能力)恢复。

### 提供方路由与聚合条目

带有 `providers` 路由数组的模型注册方式不同。两个发现终结点都可能携带这类条目; 常规 LiteLLM 代理通常不会, 对同一模型名做负载均衡的代理也不会产生这种形态 (那些部署合并进上面的单一条目)。

- 当至少一条路由支持工具时 (一条就够), 每条支持工具的路由注册自己的选择器条目 (命名为 `via <provider>`), 外加 `(cheapest)` 和 `(fastest)` 聚合条目, 让 LiteLLM 按请求挑选路由; 此时不注册无后缀的基础条目。
- 当没有路由支持工具时, 只注册一个基础条目, 没有聚合条目。
- 聚合条目对外宣布最严格的支持工具路由的 token 限制。

这些条目在自己的 ID 下注册 - `<id>:cheapest`、`<id>:fastest` 和 `<id>:<provider>` - [匹配键](#模型匹配)匹配的就是这个带后缀的 ID, 而不是服务器报告的基础 ID: 像 `gpt-4` 这样的精确键碰不到它们中的任何一个, 而通配键 (`gpt-4*`) 覆盖整个家族。[仪表板的模型表格](dashboard.md#模型)的复制操作给出的就是精确的带后缀 ID。

## 模型匹配

两个以模型为键的记录 - `models.parameters` 和 `models.capabilities`, 全局与每条目皆然 - 用相同的键语法选中模型。键匹配的是服务器报告的模型精确 ID (路由型模型的条目按其[带后缀的 ID](#提供方路由与聚合条目) 匹配), 而选择器不显示它; [仪表板的模型表格](dashboard.md#模型)在每行上提供复制它的操作。

**除非键自己说明, 否则按精确匹配处理:**

| 键 | 匹配 | 备注 |
|---|---|---|
| `"gpt-5"` | 只匹配 ID `gpt-5` | 不匹配 `gpt-5.7`, 也不匹配 `gpt-5-turbo` |
| `"gpt-5*"` | 以 `gpt-5` 开头的每个 ID | 通配 (glob); `*` 必须在末尾 |
| `"/gpt-[45].*/"` | 正则表达式匹配到的一切 | 以斜杠包裹, 对整个 ID 匹配; 在结尾斜杠后加 `i` 表示不区分大小写 (`"/GPT-5.*/i"`); 其他任何标志或无效模式会在仪表板中报告并被忽略 |
| `"*"` | 每个模型 | 你的默认值放这里 |
| `""` | 什么都不匹配 | 无效; 报告并忽略 |

键逐字符比较: 不做任何修剪 (前导空格是键的一部分), 精确键和通配键区分大小写 - `/re/i` 是唯一不区分大小写的形式。对不寻常的 ID 和不完美的记录, 有几个推论:

- 含 `/` 的 ID (比如 `anthropic/claude-4`) 由普通精确键匹配 - 只有以 `/` *开头*的键才算正则形态。在以 `/` 开头的键里, 最后一个 `/` 之后只能跟受支持的标志 (`i`, 或什么都不跟), 所以 `"/anthropic/claude"` 无效并被报告; 自身以 `/` 开头的 ID 要用把斜杠写进正则主体的键来匹配 (`"/\\/anthropic.*/"`)。
- 以 `*` 结尾的键总是读作通配, 所以字面以 `*` 结尾的 ID 需要用转义星号的正则表达式: `"/gpt-5\\*/"`。
- `*` 出现在键末尾之外的任何位置 (`"gpt*5"`) 既不是通配也不是字面量 - 该键无效, 报告并忽略, 与空键或畸形正则相同。
- 以 `_` 开头的记录键是指令, 永远不是匹配器, 所以以 `_` 开头的 ID 只能由正则表达式键匹配。
- 匹配不到你当前任何模型的键不是错误: 它只是从不生效, 静静待命, 等这样的模型出现。只有畸形的键 (无效正则、不支持的标志、`""`) 才会被报告 - 它的记录随即永远匹配不到任何东西。
- 在一个记录里把同一个键写两次是 JSON 问题, 不是匹配器问题: VS Code 的编辑器会警告重复, 解析后只有最后一次出现存活 - 扩展根本看不到第一个。

键是模型匹配器, 仅此而已 - **全局层面没有服务器限定**。面向单个服务器的配置放在那个服务器条目自己的 `models.parameters` / `models.capabilities` 记录里, 语法相同 ([服务器](servers.md#每服务器模型配置))。对于通过 VS Code 自己的模型管理添加的服务器 (没有条目), 先[采用它](servers.md#外部服务器与采用)。

原生设置 GUI 无法编辑对象设置, 因此[仪表板](dashboard.md)为两个记录提供行编辑器: 匹配器字段会建议你已发现的模型 ID,「以 JSON 编辑」开关接受粘贴的记录, 编辑只在你按下「应用」时落地。直接在 settings.json 中编辑 JSON 效果相同。

### 哪条记录生效

具体度为匹配的键排序: 精确键比通配键更具体 (通配键之间, 字面前缀更长者胜出), 通配键比正则键更具体 (正则键之间, 记录中靠后者胜出), 一切都胜过 `"*"`。层级是严格的: 任何通配键都排在任何正则键之上, 无论正则读起来多窄, 而 `"/.*/"` 排在 `"*"` 之上, 尽管两者匹配相同的模型 - 它按正则计层。平局几乎不存在: 匹配同一 ID 的两个不同通配键前缀长度必然不同 (前缀相等就成了同一个键), 正则键之间由记录中靠后者决定 - 与下文继承链中靠后正则更靠近模型的顺序一致。

**默认情况下, 最具体的匹配记录整体胜出** - 它的字段生效, 其他记录一概不渗入。两个指令控制流动 - 给方标记字段, 收方做决定 - 而收方永远说了算:

| 指令 | 侧 | 含义 |
|---|---|---|
| `"_inheritable": true \| ["field", ...]` | 给方 | 把全部/列出的字段标记为可继承: 任何匹配得更具体、自身记录未另行声明的模型都会继承它们 (仅限它未设置的字段; 每字段以最近的可继承值为准) |
| `"_inherit_from": ["key", ...]` | 收方 | 恰好从点名的记录继承 - 它们的全部字面字段, 最近者优先 - 除此之外不继承任何东西。点名即是全部意图: 被点名的记录不需要 `_inheritable`, 它自己的继承设置不随之传递, 它与本记录之间的屏障被绕过。列表项是精确的记录键, 且还必须匹配该模型 - 点名了却不匹配该模型的记录对它没有任何贡献 (继承有来源, 没有包含); 点名不存在的键会在仪表板中标记, 列表其余部分照常生效 |
| `"_inherit_from": true` | 收方 | 继承到达本记录的一切 - 下一个更宽匹配的完整视图, 无论是否标记为可继承; 屏障仍然生效 |
| `"_inherit_from": false` | 收方 | 什么都不继承 - 完全自给自足。而且由于更宽的字段只能通过本记录的解析视图到达更具体的记录, 也没有任何东西能越过它流动: `false` 就是屏障 |

可继承字段沿具体度链传递, 并且必须*穿过*来源与模型之间的每条记录: 每条记录只向上传递它自己接受的东西。因此带 `"_inherit_from": false` 的记录会切断链条 - 它把自己*和*所有更具体的记录都与更宽的记录隔离开。绕过屏障的唯一办法是点名: `"_inherit_from"` 列表直达它点名的记录, 屏障与否无关。

实例 - 同一个家族, 两种配置方式:

```jsonc
"litellm-vscode-chat.models.parameters": {
  "*":        { "temperature": 0.7, "top_p": 0.9, "_inheritable": true },
  "gpt-5*":   { "temperature": 0.3, "_inheritable": true, "_inherit_from": false },
  "gpt-5.6":  { "max_tokens": 8192 },
  "claude*":  { "max_tokens": 4000 },
  "claude-4": { "temperature": 1.0 }
}
```

| 模型 | 结果 | 原因 |
|---|---|---|
| `gpt-5.6` | `max_tokens: 8192, temperature: 0.3` | 保持沉默, 于是继承到达它的东西: `gpt-5*` 把 `temperature` 标为可继承; 通配全收键的 `top_p` 死在 `gpt-5*` 的屏障上 |
| `gpt-5`、`gpt-5.7`、... | `temperature: 0.3` | 最佳匹配是 `gpt-5*`, 它自给自足 - 全收键的字段止步于此 |
| `claude-4` | `temperature: 1.0, top_p: 0.9` | 自己的 `temperature` 胜出; `top_p` 从全收键出发, 原样穿过沉默的 `claude*` 记录。`claude*` 自己的 `max_tokens` 不跟来: 它从未被标记为可继承 |
| `claude-4.1` | `max_tokens: 4000, temperature: 0.7, top_p: 0.9` | 最佳匹配是 `claude*`, 整体应用, 外加全收键中它未设置的可继承字段 |
| 其余一切 | `temperature: 0.7, top_p: 0.9` | 全收键本身就是最佳匹配 |

`claude-4` 那一行是穿透规则的现场演示: 没有指令的记录是透明的 - 可继承字段原样穿过它, 仍然带着来源的标记, 而它自己未标记的字段留在原地。

`"_inherit_from"` 列表显式指定祖先 - 它也是绕过屏障的唯一办法:

```jsonc
"gpt-5.6": { "max_tokens": 8192, "_inherit_from": ["gpt-5*"] }
// -> max_tokens 8192 + temperature 0.3 (恰好是点名的记录, 别无其他)

"gpt-5.6": { "max_tokens": 8192, "_inherit_from": ["gpt-5*", "*"] }
// -> max_tokens 8192, temperature 0.3, top_p 0.9 - 点名 "*" 绕过了屏障
```

#### 边界情况

- `"_inherit_from": []` 没有点名任何记录, 所以什么都不继承 - 空列表的行为与 `false` 完全一样, 屏障效果也在内。
- `"_inherit_from"` 列表的顺序无关紧要, 把同一记录点名两次也不增加任何东西: 两个被点名的记录设置了同一字段时, 更具体者胜出 - 「最近者优先」指的是具体度顺序, 不是列表顺序。
- 记录在 `"_inherit_from"` 中点名自己是无操作: 它贡献的是自己的字面字段, 而记录本来就有它们 - 自己的字段永远胜过继承来的。
- 在 `"*"` 记录上写 `"_inherit_from": false` 不改变任何事: 全收键是最宽的匹配, 没有更宽的东西可继承或可阻挡。它的 `_inheritable` 标记照常给出 - `_inherit_from` 只管记录接收什么。
- `"_inherit_from": true` 读取的是下一个更宽匹配的*解析视图*: 该记录自己的字段, 加上它从更外层接受的东西。如果那条记录本身是屏障, 它的视图就只有自己的字段 - `true` 看不穿它。
- 只有字段会流动。指令是其所在记录自己的指示: 更宽记录的 [`_openrouter_model`](#openrouter-目录)、`_inheritable` 或 `_inherit_from` 从不随继承传递。被继承字段随身携带的只有来源的 `_inheritable`、`_fallback` 或 `_force` 标记 - 仅此而已。
- 链条从不跨层: 条目记录的 `"_inherit_from"` 点名该条目自己记录中的键, 全局记录点名全局键。每层独立解析自己的整条链, 然后条目结果才逐字段胜过全局结果。点名只存在于另一层的键, 等同于点名不存在的键: 在仪表板中标记, 列表其余部分照常生效。

两条独立规则位于这条流动之外: 服务器条目的记录逐字段胜过全局记录 (各自先用自己的匹配解析), 流动的字段保留其来源记录的 [`_fallback`](#回退值-_fallback) 或 [`_force`](#强制参数-_force) 标记。

解析从不按请求发生: 每个模型的扁平结果计算一次并缓存 - 只在设置、条目或模型列表变化时重算 - 请求只在其上合并运行时值。[检查器](#检查器)和诊断标签页的[已解析模型视图](dashboard.md#诊断)渲染的正是这张缓存的表 - 调试匹配器的最快方式, 也正是将要发送的内容。

### 从前缀键迁移

旧版本的键是隐式前缀: `"gpt-5"` 也匹配 `gpt-5.7` 和 `gpt-5-turbo`。升级迁移会给每个既有键追加 `*` (并把旧的全匹配 `""` 变成 `"*"`), 所以旧配置继续匹配它们以前匹配的东西。只有从现在起你新写的键采用默认精确规则。

旧版本还允许在全局记录中使用服务器 URL 限定键 (`"https://litellm.example.com/gpt-4"`)。迁移把每个这样的键无损合并进匹配的服务器条目记录。URL 匹配不到任何条目的限定键留在原地 - 它永远匹配不到模型 ID, 所以是休眠的 - 仪表板会标记它并提示移入服务器条目。完整的重命名故事: [设置](settings.md#重命名与移除的设置)。

## 能力

能力是注册时的事实: 它们决定模型被提供来做什么 (工具、图像、推理)、它的 token 限制, 以及发送哪些附件。它们从不改变请求要求模型做什么 - 那是[参数](#参数)的职责。

能力**与来源无关**: 下面的解析既不知道也不关心模型是被发现的还是[声明的](#声明的模型)。没有服务器数据的声明模型只是从其余来源解析 - [匹配](#模型匹配)对它的 ID 一视同仁, 所以 `"*"` 记录的可继承字段或回退值同样到达声明的模型。

### 能力字段

`models.capabilities` 记录 (全局设置和[每条目字段](servers.md#每服务器模型配置)) 用这套封闭词汇表纠正和扩展服务器报告的内容:

| 字段 | 类型 | 控制什么 |
|-------|------|------------------|
| `context_length` | 数字 | 模型的上下文窗口 |
| `max_input_tokens` | 数字 | 输入预算; 无人设置时为上下文长度减最大输出 token 数 |
| `max_output_tokens` | 数字 | 输出限制, 兼作 `max_tokens` 回退 ([例外](#max_tokens-例外)) |
| `supports_function_calling` | 布尔 | 使用工具的请求 (代理模式) |
| `supports_vision` | 布尔 | 是否发送图像附件 |
| `supports_reasoning` | 布尔 | 选择器中的 Thinking Effort 控件 |
| `supports_audio_input` | 布尔 | 是否发送音频附件 |

与 `models.parameters` 不同, 这套词汇表是封闭的: 未知字段不会被转发到任何地方, 而是在[能力检查器](#检查器)中标记。数字字段取正整数; 无效值同样被标记, 由次优来源顶上。

### 服务器报告什么

发现从模型信息读取能力:

| 能力 | 从模型信息读取 | 备注 |
|------------|----------------------|-------|
| 工具调用 | `supports_function_calling` (或 `supports_tool_choice`); 提供方路由携带 `supports_tools` | 未声明时视为开启; 只有显式 `false` 才关闭 |
| 视觉 | `supports_vision` | |
| 音频输入 | `supports_audio_input` | |
| 推理 | `supports_reasoning`, 或 `supported_openai_params` 中含 `reasoning_effort` | 显式 `supports_reasoning: false` 胜出 |
| 提示缓存 | `supports_prompt_caching` | 不在覆盖词汇表中; `chat.promptCaching` 全局关闭该功能 ([设置](settings.md#提示缓存)) |
| Token 限制 | 模型信息的 token 限制字段 | 见 [Token 限制](#token-限制) |

服务器侧的错误标志值得在服务器上修: 扩展双向信任声明, 提供被声明的, 保留未声明的。服务器不归你管时, 就改用覆盖。

一处不对称: 服务器显式报告的 `supports_vision: false` 或 `supports_audio_input: false` 被当作没有报告处理, 所以对知名的模型 ID, [隐式目录匹配](#openrouter-目录)可能把该能力重新打开。要让这样的模型保持不收图像或音频, 请自己在 `models.capabilities` 中写下 `false` - 覆盖总是胜出 - 或者禁用目录。

### 覆盖

普通的能力字段说的是「服务器错了 (或没说) - 用这个」: 你的值逐字段胜过服务器的。

```json
{
  "litellm-vscode-chat.models.capabilities": {
    "gpt-4": { "context_length": 128000, "supports_vision": true },
    "my-gateway-model": { "max_output_tokens": 32000 }
  }
}
```

服务器条目可以携带限定到自己模型的同款记录 (`models.capabilities`, 同样的[匹配语法](#模型匹配), 不需要 URL 限定, 因为条目已经指明了自己的服务器); 条目字段逐字段胜过全局字段。仪表板的服务器表单有对应的「此服务器的...」区块。详情: [服务器](servers.md#每服务器模型配置)。

### 回退值: `_fallback`

覆盖说「服务器错了」; 回退说「以防服务器没说」。`_fallback` 指令把记录中的字段变成补缺者, 应用在服务器报告值*之下*:

```jsonc
"litellm-vscode-chat.models.capabilities": {
  "*": {
    "_fallback": true,             // 此记录的每个字段都是回退
    "context_length": 131072,      // 仅在服务器未报告时使用
    "max_output_tokens": 8192
  },
  "qwen*": {
    "_fallback": ["supports_vision"],  // 只有列出的字段回退
    "supports_vision": true,           // 补缺; 服务器的 "false" 胜出
    "context_length": 32768            // 未列出: 普通覆盖, 胜过服务器
  }
}
```

- `_fallback: true` 让记录中的每个字段都成为回退; `_fallback: ["field", ...]` 只让列出的字段回退, 其余仍是普通覆盖。
- 回退提供的 `max_output_tokens` 对 [`max_tokens` 例外](#max_tokens-例外)仍算用户设置: 解除 4096 上限。
- 被继承的字段带着来源的标记到达: 回退无论被[继承](#哪条记录生效)带到哪里都还是回退, 而接收记录不能重新标记不是自己写的字段 (它自己的 `_fallback` 列表只能点名自己的字段; [`_force`](#强制参数-_force) 遵循同一来源侧规则)。想让某个模型把继承来的回退变成硬覆盖? 在那里写明: `"gpt-5.6": { "context_length": 200000 }` - 自己的、未列出的字段就是覆盖, 而且只有那个模型脱离来源。
- 指令列表只能点名自己记录中存在的字段: 点名缺失字段会作为无效指令报告, 跳过该名字, 列表其余部分照常生效 (接收方重标记限制建立在同一规则上)。已知指令出现在错误的记录类型中 - `_fallback` 在参数记录里、`_force` 在能力记录里 - 会被报告并忽略, 而真正未知的 `_` 键为向前兼容保持静默忽略。

和每个指令一样, 下划线键是给扩展的指示 - 从不发送到任何地方。

### OpenRouter 目录

扩展内置一份 [OpenRouter](https://openrouter.ai) 公开模型目录的快照, 用它填补其他来源都不提供的能力字段。模型与目录相遇的两种方式:

- **显式**: `"_openrouter_model"` 为目录永远猜不到 ID 的模型点名目录条目:

  ```json
  {
    "litellm-vscode-chat.models.capabilities": {
      "my-alias": { "_openrouter_model": "anthropic/claude-sonnet-4" }
    }
  }
  ```

  由此派生的字段排在服务器报告*之上* - 该指令表示对这个模型不可信任服务器的数据。同一记录中你显式写的字段仍然胜过目录的。未知的目录 ID 在[能力检查器](#检查器)中显示警告, 模型回落到其他来源; 它永远不是错误。仪表板的能力编辑器为该 ID 提供搜索选择器。和每个指令一样, `_openrouter_model` 属于它所在的记录: 它从不被继承 - 记录之间只有字段流动 - 更具体的匹配记录会连同该记录的其余字段一起遮蔽它, 所以如果那个模型仍然需要, 请在那里重申该指令。

- **隐式**: 没有指令时, 自身 ID 与某个目录条目精确匹配的模型 (或与 `vendor/` 前缀之后的部分匹配, 当只有一个条目匹配时) 仍会从目录补缺 - 但只作为内置默认值之上最弱的来源, 永远无法顶替服务器报告的数据或你的设置。

数据从哪里来, 以及唯一的网络影响:

- 快照随 VSIX 一起分发, 大约每周从 `https://openrouter.ai/api/v1/models` 刷新一次 - 一个公开的、无需身份验证的模型列表。请求不携带提示、不携带用量、不携带账户数据, 也不携带任何关于你的服务器的信息; 刷新的副本缓存在 VS Code 的全局存储中, 刷新失败会静默回落到缓存或内置的快照。
- 用 "LiteLLM: Refresh OpenRouter Catalog" 命令按需刷新, 或用该设置仪表板行上的「刷新」按钮 - 该行还显示目录的大小和上次更新时间。手动刷新失败会在行状态中报告 - 没有弹窗。
- **退出**: 把 `litellm-vscode-chat.models.openRouterCatalog` 设为 `false` 可停止周期刷新 (所有目录网络请求) 和隐式匹配; 仪表板行转为休眠并附提示。显式 `_openrouter_model` 指令继续离线工作, 使用内置或缓存的快照 - 它们是你声明的意图, 不需要网络。

### 能力优先级

逐字段, 设置了它的最高来源胜出。在每个记录层内, 由[匹配规则](#哪条记录生效)在匹配的键之间挑选:

1. 条目 `models.capabilities`
2. 全局 `models.capabilities`
3. 由显式 `_openrouter_model` 指令派生的字段
4. 服务器报告的内容 (声明的模型没有)
5. `_fallback` 字段 (条目在全局之上, 各层内部按匹配规则)
6. 隐式 OpenRouter 目录匹配
7. 内置默认值: 工具开、视觉/音频/推理关、上下文 128000、最大输出 16000

值得知道的两个推论:

- 你自己设置的 `max_output_tokens` - 第 1、2 或 5 层 - 算作用户声明, 成为线上的 `max_tokens` 时原样发送; 模型的每个部署都声明了的服务器限制同样如此。任何目录派生值 (显式指令或隐式匹配) 和内置底线都算猜测, 把线上的 `max_tokens` 封顶在 4096 ([例外](#max_tokens-例外))。要为目录背书的模型解除上限, 自己写一个 `max_output_tokens`。
- 定价从不被覆盖: 服务器报告的定价永远胜出, 目录定价只填补服务器未报告的空缺。

### Token 限制

三个数字约束每个请求, 通过上面的优先级解析:

- `context_length` 是模型的整个窗口。
- `max_input_tokens` 是 Copilot 打包提示时依据的输入预算; 无人设置时, 派生为上下文长度减最大输出 token 数。
- `max_output_tokens` 约束回复, 并在没有参数设置时兼作线上的 `max_tokens` ([例外](#max_tokens-例外))。

对[负载均衡池](#负载均衡池), 注册的限制取最严格贡献者的 - 你自己的覆盖仍然胜过合并结果: 你设置的 `max_output_tokens` 即使各部署不一致也算已声明, 而合并出的服务器值只有在每个部署都声明时才算已声明。

#### 从已移除的默认设置迁移

旧版本有三个全局回退设置: `defaultContextLength`、`defaultMaxOutputTokens` 和 `defaultMaxInputTokens`。它们没有了; 升级迁移把你设置过的值写进一个 `"*"` 记录:

```jsonc
"litellm-vscode-chat.models.capabilities": {
  "*": {
    "_inheritable": true,
    "_fallback": ["context_length", "max_output_tokens"],
    "context_length": 100000,      // 原 defaultContextLength
    "max_output_tokens": 8000,     // 原 defaultMaxOutputTokens
    "max_input_tokens": 90000      // 原 defaultMaxInputTokens - 普通覆盖
  }
}
```

前两个搭 `_fallback`, 因为旧设置只在服务器报告之下补缺。记录还标了 `_inheritable: true`, 因为旧默认值不管你配置了什么都应用于每个模型: 没有这个标记, 任何有自己更具体记录的模型都会整体失去这些默认值; 有了它, 它们跟随每个不主动退出的模型 - 每个字段落到哪里都还是回退, 因为[被继承字段保留来源的标记](#回退值-_fallback)。`defaultMaxInputTokens` 从来都高于服务器的输入限制, 所以它作为普通覆盖迁移 - 行为不变, 换了新家。完整重命名表: [设置](settings.md#重命名与移除的设置)。

## 参数

参数是请求要求的东西: `temperature`、`max_tokens`、`reasoning_effort`, 你的 LiteLLM 部署和模型提供方接受的任何东西。扩展从不替你决定它们。

### 透传契约

当你什么都不配置 - 或没有配置匹配某模型的东西 - 时, 应用的是你的模型提供方自己的默认值:

- 扩展不注入默认 temperature, 没有允许列表, 什么都没有。
- 所有非保留的参数键原样透传; 扩展不限制你能设置哪些参数。
- 提供程序拥有的字段无法覆盖: `model`、`messages`、`stream`、`stream_options`, 以及 - 当工具参与时 - `tools` 和 `tool_choice`。
- 以 `_` 开头的键是扩展指令 ([`_force`](#强制参数-_force)), 从不发送。

### `max_tokens` 例外

扩展唯一会自行填入的字段是 `max_tokens`。当运行时选项和所有参数记录都没有设置它时, 请求携带模型解析出的最大输出 token 数:

- 数字为已声明时**原样发送**: 服务器报告的 (对[池化模型](#负载均衡池), 仅当每个部署都声明时), 或你在 `models.capabilities` 中设置的 - 覆盖或 `_fallback` 值皆可;
- 数字为猜测时**封顶 4096**: 目录值 (显式 `_openrouter_model` 指令或隐式匹配) 或内置默认值。

在[优先级链](#参数优先级)中的任何地方设置 `max_tokens`, 这个例外就永不启动: 值按你写的原样发出 - 扩展从不编辑或钳制用户设置的参数, 即使它超过模型解析出的 `max_output_tokens` (该能力继续管辖注册和输入预算, 不管请求)。而在[能力](#能力字段)中设置 `max_output_tokens` 并不绕过这个例外 - 它为例外供值: 回退用你的数字触发, 它算已声明, 于是 4096 上限永不适用。

### 参数来自哪里

四个来源可以为请求设置参数, 从低到高列出:

1. **全局设置** - `litellm-vscode-chat.models.parameters`, 以[匹配器](#模型匹配)为键:

   ```json
   {
     "litellm-vscode-chat.models.parameters": {
       "gpt-5*": { "temperature": 1 },
       "claude-opus": { "max_tokens": 16000, "temperature": 0.5 }
     }
   }
   ```

   适合有硬性要求的模型 (gpt-5 拒绝 1 以外的任何 `temperature`) 或全家默认值 (一个 `"*"` 键)。常用参数: `max_tokens`、`temperature`、`top_p`、`frequency_penalty`、`presence_penalty`、`stop`、`response_format`、`reasoning_effort`、`seed`。

2. **条目参数** - 服务器条目的 `models.parameters`, 语法相同, 逐字段应用在全局记录之上; 服务器专属值的家 ([服务器](servers.md#每服务器模型配置))。只有当请求经过的提供程序组在标签和基础 URL 两方面都与条目匹配时, 请求才拾取该条目的参数; 没有条目的外部组, 以及标签或 `baseUrl` 编辑留下的过期组, 只得到全局设置 - 仪表板以[「params inactive」通知](troubleshooting.md#每服务器模型参数未生效)标记这种情况。

3. **选择器配置** - Copilot 选择器中的每模型[配置菜单](#每模型配置) (目前: 推理强度)。这些选择算作用户设置, 像任何配置的参数一样转发, 只是只有 schema 声明的属性会发出, 映射到它们的线上键。

4. **运行时选项** - 聊天客户端 (Copilot, 或调用该模型的其他扩展) 在请求本身上设置的内容。

### 强制参数: `_force`

运行时选项通常胜出 - 聊天客户端要求了具体的东西。`_force` 指令为选中的字段反转这一点, 用于你的值必须永远胜出的网关或模型:

```jsonc
"litellm-vscode-chat.models.parameters": {
  "gpt-5*": {
    "_force": ["temperature"],   // 或 true, 强制记录中的每个字段
    "temperature": 1,            // 连 Copilot 的运行时选项都赢
    "top_p": 0.9                 // 未列出: 普通字段, 运行时选项仍胜出
  }
}
```

- `_force: true` 强制记录中的每个字段; `_force: ["field", ...]` 只强制列出的。
- 与 [`_fallback`](#回退值-_fallback) 一样, 标记在来源侧: 被强制的字段无论被[继承](#哪条记录生效)带到哪里都保持强制, 记录自己的 `_force` 列表只能点名自己的字段 - 要强制继承来的字段, 在其来源处标记 (或在本地重申并强制)。
- 提供程序拥有的字段既不能设置也不能强制: 点名它们的 `_force` 会在仪表板中报告, 该键被忽略。
- `max_tokens` 不属于提供程序拥有的字段, *可以*被强制: 被强制的值胜过运行时选项, 而且作为用户设置的值, 永远不会被 [`max_tokens` 例外](#max_tokens-例外)封顶。
- 条目记录的强制字段胜过全局记录的强制字段。

### 参数优先级

当多个来源为同一请求设置同一参数时, 更高者胜出。在每个记录层内, 由[匹配规则](#哪条记录生效)在匹配的键之间挑选:

1. 强制字段 ([`_force`](#强制参数-_force)) - 条目在全局之上
2. 运行时选项 - 聊天客户端自己的请求设置
3. 选择器配置 - 每模型[配置菜单](#每模型配置)
4. 条目 `models.parameters`
5. 全局 `models.parameters`

五层都未设置的参数落到你的模型提供方的默认值, 外加上文的 [`max_tokens` 例外](#max_tokens-例外)。要查看这些层为某个模型如何解析, 用[检查器](#检查器)。

## 选择器

每个服务器条目在 Copilot 的模型选择器中成为一个提供程序组, 以其标签命名, 服务器的模型列在其下。条目显示服务器声明的提供方名称 (模型信息的 `litellm_provider`, 或提供方路由的名称), 未声明时回落到 `litellm`; `(cheapest)` 和 `(fastest)` [聚合条目](#提供方路由与聚合条目)始终显示 `litellm`。[仪表板的模型表格](dashboard.md#模型)显示同样的数据和精确的 ID。

### 每模型配置

有些模型在选择器中提供「配置」菜单 - 这就是[参数优先级](#参数优先级)中的「选择器配置」层。目前它携带一个控件, Thinking Effort, 出现在宣布推理支持的模型上:

1. 在选择器中选中该模型。
2. 单击聊天输入框中模型名称旁的 "Thinking Effort" 标签。
3. 从 Off 到 Extra High 之间选一档; VS Code 会为该模型记住这个选择。

每档发送什么:

- 之后每个请求都相应携带 `reasoning_effort`; "Off" 以 `reasoning_effort: "none"` 发出, 在支持该取值的模型上关闭思维。
- "Provider default" (初始状态) 不发送任何东西, 由你的提供方决定。
- 每个推理模型的菜单都相同, 因为 LiteLLM 报告哪些模型接受 `reasoning_effort`, 但不报告每个模型接受哪些值。如果你选了模型拒绝的档位 (比如在最高只到 High 的模型上选 Extra High), 请求会带着服务器自己的错误消息失败; 换一档重试即可。

temperature 有意留在 `models.parameters` 中自由设置: 配置菜单只能呈现固定选项, 所以扩展不在那里添加 temperature 预设。

### 选择器中的定价

- 模型信息中的每 token 成本会换算成模型选择器和[仪表板](dashboard.md)模型表格显示的每百万 token 数字, 连同已声明的缓存与长上下文分层成本。
- 恰好为零的成本对被视为未声明而非免费, 因为 LiteLLM 会给没有定价数据的模型打上零。
- cheapest/fastest 聚合条目完全不带定价: 在那里, 请求实际花多少由代理的路由决定。

请求实际花了多少钱, 按服务器和相对预算, 在[用量](usage.md#用量面板)。

## 多模态输入

附件在线上变成什么, 取决于它的类型和模型解析出的[能力](#能力):

| 附件 | 能力门槛 | 在其他模型上 |
|------------|-----------------|-----------------|
| 图像 (附件, 以及从先前轮次重放的图像) | 只发给声明视觉支持的模型 | 文本照常通过, 图像被丢弃, 「LiteLLM」输出通道记一条说明 |
| PDF (作为用户消息上的文件块发送) | 不设能力门槛 | 接受不了 PDF 的模型带着其服务器自己的错误消息失败 |
| 音频 (WAV、MP3; 作为音频输入块发送) | 只发给声明音频输入支持的模型 | 丢弃并在输出通道记说明 |
| 可解码为文本的文件 (纯文本、JSON、源码文件) | 无: 解码后作为文本发往任何模型 | - |

工具结果转发文本, 在视觉模型上外加图像。助手历史中的二进制内容没有线上形态; 重放时只有其文本存活。

## 思维、来源、生成媒体与 token 用量

除了纯文本, 回复中 (或关于回复) 还可能回来四样东西:

- **思维。**流式输出推理内容的模型 (thinking 块、`reasoning_content` 增量) 会在 Copilot 的思维 UI 中随到随显 - 在暴露 thinking-part API 的 VS Code 构建上。在没有它的构建上, 推理被丢弃并在输出通道记说明, 只含推理的回复会以一条要求更新 VS Code 的错误失败; 见[故障排除](troubleshooting.md#常见问题)。
- **来源。**LiteLLM 路由返回引用或搜索结果的模型 (启用网络搜索的路由) 会在回复末尾得到一个按 URL 去重的来源列表。
- **生成媒体。**在聊天中生成媒体的模型把它流式送回回复: 生成的图像随到随渲染, 生成的音频按每段话一个剪辑到达, 其转写作为普通文本流式显示。扩展解码不了、或 VS Code 构建显示不了的媒体, 丢弃并在输出通道记说明。
- **Token 用量。**每个请求都向服务器索要 token 用量, 返回的计数 (提示、补全、总数, 以及服务器报告时的缓存与推理 token 明细) 传给 Copilot 用于其用量显示。只从响应中提取这些已知的数字计数; 原始用量记录从不被整体转发或记录。服务器侧的支出与预算是另一个功能: [用量](usage.md#用量面板)。

## 检查器

本页的每条规则都可观察。[仪表板](dashboard.md)的模型表格给每个模型两个检查器:

- **参数** ([生效参数](dashboard.md#生效参数)): 将要发出的每个参数、解析出的值, 以及设置它的来源 - 哪条记录、哪个匹配键 - 被遮蔽的值显示在胜出者下方, 外加请求将携带的 `max_tokens` 及其原因。
- **能力** ([生效能力](dashboard.md#生效能力)): 每个能力字段及其解析值和来源 - 条目或全局记录键、`_openrouter_model` 派生、服务器的报告、`_fallback` 补缺、目录匹配, 或内置默认值 - 同样在下方显示被遮蔽的值。

检查器还会呈现本页点名的诊断: 无效的匹配键、未知的能力字段、无效值、未知的目录 ID, 以及作用在不可强制键上的 `_force`。当匹配器做出出人意料的事时, 从这里开始 - 答案离你只有一次「参数」或「能力」点击的距离。
