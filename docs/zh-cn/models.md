# 模型与能力

[English](../models.md) | 简体中文 | [繁體中文](../zh-tw/models.md)

扩展读取每个服务器的模型信息, 并把发现的内容注册给 Copilot Chat: 模型的 token 限制、定价和能力标志都来自那里。能力决定模型被提供来做什么 (工具、图像、推理); 它们从不改变扩展要求模型做什么, 那是[模型参数](model-parameters.md)的职责。

## 哪些模型会注册

发现读取服务器的 `/v1/model/info` 终结点; 当该调用失败、未返回数据数组, 或返回的条目全都不可用时, 回退到更朴素的 `/v1/models` 列表 (格式正确的空列表会注册零个模型, 不触发回退)。

可达服务器报告的每个聊天模型都会出现在选择器中。适用三条排除规则:

- `model_info.mode` 指向非聊天终结点 (`embedding`、`image_generation`、`audio_speech`、`audio_transcription`、`rerank`、`moderation`) 的模型被有意排除, 因为对它们的聊天请求只会失败。未声明 mode 的模型始终注册。
- 代理已暂停的部署 (`model_info.blocked`) 被跳过。
- 不过滤其他任何东西: 完全没有能力数据的模型仍会注册, 使用[设置](settings.md#token-限制)中的回退 token 限制。

当一个模型名称由多个部署提供服务 (负载均衡池) 时, 它只注册一次, 采用最严格贡献者的 token 限制, 这样请求永远不会超出实际服务它的那个部署。

### 提供方路由与聚合条目

带有 `providers` 路由数组的模型注册方式不同。两个终结点都可能携带这类条目; 常规的 LiteLLM 代理通常不携带, 对一个模型名称的多个部署做负载均衡的代理也不会产生它 (那些部署合并成上文的单一条目)。

- 当至少一条路由支持工具时 (一条就够), 每条支持工具的路由都注册自己的选择器条目 (命名为 `via <provider>`), 外加让 LiteLLM 按请求挑选路由的 `(cheapest)` 和 `(fastest)` 聚合条目; 这种情况下不注册无后缀的基础条目。
- 当没有路由支持工具时, 改为注册单个基础条目, 不带聚合条目。
- 聚合条目声明支持工具的路由中最严格者的 token 限制。

选择器和仪表板的「系列」列来自同一数据: 条目显示服务器声明的提供方名称 (模型信息的 `litellm_provider`, 或提供方路由的名称), 未声明时回退到 `litellm`; `(cheapest)` 和 `(fastest)` 聚合条目始终显示 `litellm`。

## 能力

| 能力 | 从模型信息读取 | 控制什么 |
|------------|----------------------|------------------|
| 工具调用 | `supports_function_calling` (或 `supports_tool_choice`); 提供方路由携带 `supports_tools` | Copilot 能否发送使用工具的请求 (Agent 模式); 未声明时开启, 仅显式 `false` 时关闭 |
| 视觉 | `supports_vision` | 是否发送图像附件 (见下文) |
| 音频输入 | `supports_audio_input` | 是否发送音频附件 |
| 推理 | `supports_reasoning`, 或 `supported_openai_params` 中含 `reasoning_effort` (显式的 `supports_reasoning: false` 胜出) | 选择器中的「Thinking Effort」控件; 参见[模型参数](model-parameters.md#模型选择器中的推理强度) |
| 提示缓存 | `supports_prompt_caching` | 是否放置缓存断点; 参见[设置](settings.md#提示缓存) |

服务器端的错误标志值得在服务器端修复: 扩展在两个方向上都信任声明, 提供声明了的, 扣下未声明的。

## 多模态输入

附件在线路上变成什么, 取决于它的类型和模型声明的能力:

| 附件 | 能力门控 | 在其他模型上 |
|------------|-----------------|-----------------|
| 图像 (附件, 以及从此前轮次重放的图像) | 只发送给声明视觉支持的模型 | 文本照常通过, 图像被丢弃, 并在「LiteLLM」输出通道中留下一条说明 |
| PDF (作为用户消息上的文件块发送) | 不做能力门控 | 无法接收 PDF 的模型会带着其服务器自己的错误消息失败 |
| 音频 (WAV、MP3; 作为音频输入块发送) | 只发送给声明音频输入支持的模型 | 被丢弃, 输出通道中留有说明 |
| 可解码为文本的文件 (纯文本、JSON、源代码文件) | 无: 处处解码后作为文本发送 | - |

工具结果转发文本, 在视觉模型上还转发图像。助手历史中的二进制内容没有线路形态; 重放时只有其文本保留。

## 思维、来源、生成媒体与 token 用量

除纯文本外, 回复中 (或关于回复) 还可能带回四样东西:

- **思维。** 流式输出推理内容 (思维块、`reasoning_content` 增量) 的模型会在 Copilot 的思维 UI 中随到随显, 前提是 VS Code 构建暴露了思维部分 API。在没有它的构建上, 推理会被丢弃并在输出通道中留下说明, 只包含推理的回复会以一条提示你更新 VS Code 的错误失败; 参见[故障排除](troubleshooting.md#常见问题)。
- **来源。** LiteLLM 路由返回引用或搜索结果的模型 (启用网络搜索的路由) 会在回复末尾得到一个按 URL 去重的来源列表。
- **生成媒体。** 在聊天中生成媒体的模型会把媒体流式送回回复: 生成的图像随到随原位渲染, 生成的音频以每段话一个剪辑到达, 其转写作为普通文本流式输出。扩展无法解码、或 VS Code 构建无法显示的媒体会被丢弃, 输出通道中留有说明。
- **Token 用量。** 每个请求都会向服务器请求 token 用量, 返回的计数 (提示、补全、总数, 以及服务器报告的缓存和推理 token 明细) 会传给 Copilot 用于其用量显示。只从响应中提取这些已知的数字计数; 原始用量记录从不被整体转发或记录。

## 选择器中的定价

- 模型信息中的每 token 成本会换算成模型选择器和[仪表板](dashboard.md)模型表格显示的每百万 token 数字, 连同声明了的缓存和长上下文档位成本。
- 恰好为零的成本对被视为未声明而非免费, 因为 LiteLLM 会给没有定价数据的模型盖上零。
- cheapest/fastest 聚合条目完全不带定价: 在那里, 一个请求实际花费什么由代理的路由决定。
