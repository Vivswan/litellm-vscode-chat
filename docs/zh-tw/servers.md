# 伺服器

[English](../servers.md) | [简体中文](../zh-cn/servers.md) | 繁體中文

延伸模組可同時連線任意數量的 LiteLLM 伺服器, 並把它們的模型彙整進同一份選擇器清單。本頁涵蓋關於伺服器的一切: 宣告它、向它驗證、塑造它的模型、它在 VS Code 中的生命週期, 以及它的祕密如何儲存。

## 伺服器如何運作

三個概念承載其餘一切:

- **項目** - `litellm-vscode-chat.servers` 設定中的一個物件: 關於伺服器的宣告式真相。[儀表板](dashboard.md)的新增/編輯表單寫入的是同一個設定, 因此 JSON 編輯與表單始終一致。
- **提供者群組** - VS Code 自己為每個伺服器持有的東西 (位於 `<profile>/User/chatLanguageModels.json`, 即「模型檔案」)。延伸模組會在啟用時以及設定每次變更時, 自動把項目同步為群組。
- **身分** - 項目的 `label` 加 `baseUrl`。群組以標籤命名, 這正是重新命名與移除會出現[下文](#生命週期-重新命名移除與隱藏的群組)所述生命週期怪癖的原因。

`servers` 設定是機器範圍的: 只存在於您的使用者設定, 工作區無法覆寫它 (複製下來的儲存庫永遠無法把您的伺服器重新指向另一台主機), 設定同步也不攜帶它 - 伺服器與認證留在您輸入它們的那台機器上。要把它們搬到另一台機器, 用 ["LiteLLM: Export Settings..."](settings.md#匯出與匯入), 它也能攜帶祕密儲存體中的值。

來自舊版本的項目 (扁平的 `apiKey`、`oauth*`、`virtualKey*`、`modelParameters` 等欄位) 會由一次性移轉自動重構。已在祕密儲存體中的祕密不受影響 - 重構只改動設定文字, 不需重新輸入任何東西。

## 快速開始

最小形式 - 不需驗證的本機代理:

```jsonc
"litellm-vscode-chat.servers": [
  { "label": "Local", "baseUrl": "http://localhost:4000" }
]
```

典型形式 - 託管閘道, 金鑰不放進設定檔:

```jsonc
"litellm-vscode-chat.servers": [
  { "label": "prod", "baseUrl": "https://litellm.example.com" }
]
// 然後: 儀表板 -> 編輯 "prod" -> API 金鑰 -> 「安全儲存」,
// 或命令選擇區 -> "LiteLLM: Set Server Secret"
```

儲存後, 伺服器的模型片刻之內就會出現在模型選擇器中。儀表板的**測試連線**按鈕會依當下輸入的內容原樣探測草稿 - 包含尚未儲存的編輯, 已儲存的祕密從其存放處讀取 - 發出一次探索呼叫, 回報模型數量或確切錯誤, 當失敗看起來是設定問題時, 附上指向對應[疑難排解](troubleshooting.md#常見問題)小節的連結。它不儲存也不同步任何東西。

金鑰晚於項目時要知道的一條時序規則: 提供者群組在項目第一次同步的那一刻從項目建立, 認證也包含在內, 而 VS Code 無法更新既有群組 - 第一次同步之後才儲存的金鑰, 要等群組重新建立後才會到達請求, 伺服器列會顯示確切步驟 ([生命週期](#生命週期-重新命名移除與隱藏的群組))。儀表板的新增表單避開了這一點: 它在項目第一次同步之前就把金鑰存好。

## 項目參考

項目能攜帶的每個屬性:

| 屬性 | 型別 | 作用 |
|---|---|---|
| `label` | 字串, 必填 | 伺服器在模型選擇器中的名稱; 項目身分的一半 |
| `baseUrl` | 字串, 必填 | 伺服器的根 URL。延伸模組會自行附加 `/v1`; 若 URL 已以 `/v1` 或 `/v2` 這樣的版本區段結尾, 則按原樣使用; `apiVersion` 欄位可覆寫兩者 |
| `apiVersion` | 字串 | 附加到基礎 URL 的內容。未設定 = 自動 (`/v1`, 或 URL 中已有的版本區段); `""` = 不附加任何內容; `"v2"` = 附加 `/v2`。與所有各項目欄位一樣, 只透過符合項目標籤和基底 URL 的提供者群組生效; 過時群組會回退到自動規則, 儀表板會在該伺服器列的下方說明 |
| `auth` | 物件 | `apiKey`、`oauth`、`virtualKey` 恰取一種形式, 可選擇帶級別較低的附隨認證 ([下文](#身分驗證))。伺服器不需要認證時整個省略。含糊不清的形態會被回報, 項目按設定錯誤處理 |
| `headers` | 物件 | 發往此伺服器的每個請求上的自訂 HTTP 標頭 ([下文](#自訂標頭)); 衝突時延伸模組管理的驗證標頭勝出 |
| `models.parameters` | 記錄 | 只針對此伺服器模型的請求參數; 與全域設定相同的[比對鍵](models.md#模型比對), 逐欄位套用在它之上 ([詳情](models.md#參數)) |
| `models.capabilities` | 記錄 | 只針對此伺服器模型的能力覆寫; 機制相同 ([詳情](models.md#能力)) |
| `discovery.declared` | 字串陣列 | 即使探索列不出也要註冊的精確模型 ID ([下文](#宣告的模型)) |
| `discovery.expectedFailures` | 字串陣列 | 此伺服器預期失敗的探索端點: `"modelListing"` (`/v1/models`)、`"modelInfo"` (`/v1/model/info`)。各只嘗試一次, 記一條 info 層級記錄而非紅色錯誤 ([下文](#探索與預期失敗)) |
| `budget` | 數字 | 用於[用量警示](usage.md#預算)的手動預算 (以伺服器自身的計費貨幣計)。優先於金鑰自身的 `max_budget`; 儀表板兩者都顯示 |

一個完整的項目:

```jsonc
{
  "label": "prod",
  "baseUrl": "https://gateway.internal",
  "auth": { "apiKey": "sk-..." },
  "headers": { "x-routing-env": "prod" },
  "models": {
    "parameters":   { "gpt-5*": { "temperature": 0.2 } },
    "capabilities": { "deepseek-r1": { "supports_reasoning": true, "context_length": 131072 } }
  },
  "discovery": {
    "expectedFailures": ["modelListing", "modelInfo"],
    "declared": ["deepseek-r1"]
  },
  "budget": 50
}
```

表格容納不了的邊界情況:

- 標籤在項目之間唯一: 重複使用先前項目標籤的項目會被略過並回報 - 第一個項目勝出。要把兩個項目指向同一主機, 給它們不同的標籤; 它們隨即成為端到端的兩個伺服器 - 兩個選擇器群組、模型分別列在各自群組下, 每個項目的驗證、標頭與 `models` 記錄只套用於自己的群組。
- 空的或只有空白的 `label` 或 `baseUrl` 讓項目無法使用: 略過並回報。JavaScript 保留名稱 `__proto__`、`constructor` 與 `prototype` 會被拒絕作為標籤。
- 基底 URL 可以帶路徑 (`https://intranet.example.com/litellm`, 掛載在某路徑下的閘道); `/v1` 附加在其後, 除非路徑已以 `/v1` 或 `/v2` 這樣的版本區段結尾 (按原樣使用) - `apiVersion` 欄位可覆寫兩者 (空字串 = 什麼都不附加)。結尾斜線無害 - 比較或使用 URL 之前會將其去除。
- 純 `http` 可以用, 而且是本機代理的常規選擇; 但在網路上它會明文攜帶您的認證, 因此任何遠端伺服器都請優先用 `https`。
- `budget` 必須是大於 0 的數字 ([用量 - 預算](usage.md#預算))。
- 短暫損壞的項目 (比如編輯到一半的 settings.json) 會被略過並回報, 但絕不會被誤認為移除: 它的提供者群組不會被隱藏。[移除](#生命週期-重新命名移除與隱藏的群組)只在標籤本身從設定中消失時發生。

## 身分驗證

選擇與您的閘道期望相符的形式。每個項目恰好一種形式, 形式依 `oauth` > `apiKey` > `virtualKey` 分級: 一種形式可以攜帶級別較低的*附隨認證*, 供要求在第二個標頭中提供第二份認證的閘道使用 - `oauth` 可帶 `apiKey` 和/或 `virtualKey` 附隨認證 (放在 `oauth` 物件內部), `apiKey` 可帶一個 `virtualKey` 附隨認證 (與它並排), 而級別最低的 `virtualKey` 不帶任何附隨認證。

| 您的閘道期望 | 設定 |
|---|---|
| 金鑰作為 bearer 權杖 (最常見, LiteLLM 虛擬金鑰也算) | `auth.apiKey` |
| 金鑰放在自訂標頭中 (例如 `x-litellm-api-key`) | `auth.virtualKey` |
| bearer 金鑰**加**自訂標頭中的金鑰 | `auth.apiKey` + 與它並排的 `virtualKey` 附隨認證 |
| OAuth2 用戶端認證權杖 | `auth.oauth` |
| OAuth 權杖**加**旁邊一把 LiteLLM 金鑰 | `auth.oauth` + 其 `apiKey` 或 `virtualKey` 附隨認證 |

兩個邊界情況:

- 缺少必要部分的驗證形式 (`oauth` 缺 `tokenUrl` 或 `clientId`) 是和設定兩種形式一樣的設定錯誤: 回報, 且項目在修復之前不被使用。而只是*在等它的祕密*的形式 (`virtualKey` 標頭有了但值還沒設定, `apiKey` 還沒存放在任何地方) 則不同: 項目照常運作, 請求只是不攜帶認證, 伺服器的 401 會告訴您缺什麼 - 這是新增項目與執行 "LiteLLM: Set Server Secret" 之間的正常狀態。

- **完全沒有 `auth`** 代表不送出認證標頭 - 除非該項目的[已儲存祕密](#祕密與祕密儲存體)另有說法; 儲存也算形態的一部分。沒有獨立的「免金鑰」模式可選: 結果需要金鑰的伺服器會回答 401 (「驗證失敗」), 把金鑰加到項目上就是修法。
- **含糊不清的 `auth` 形態**絕不會讓延伸模組在認證之間亂猜: `oauth` 與任何其他東西並列在 `auth` 頂層 (它的附隨認證屬於 `oauth` 物件*內部*), 或者 `auth` 內出現延伸模組不認識的鍵 (否則一個筆誤會悄悄變成「沒有認證」), 都是設定錯誤 - 儀表板的伺服器列與其「設定」診斷會點名出問題的鍵 - 項目在修復之前不被使用。其他項目不受影響。`apiKey` 與 `virtualKey` 並排*不*算含糊: 按級別讀, 那是 API 金鑰形式加一個虛擬金鑰附隨認證。

### API 金鑰

```jsonc
"auth": { "apiKey": "sk-..." }   // 或存放在祕密儲存體; 見下文「祕密」
```

以 `Authorization: Bearer` 標頭送出, 並附一份 `X-API-Key` 副本 (有的閘道讀前者, 有的讀後者)。

同時檢查 bearer **與**自訂標頭中金鑰的閘道, 把第二份認證作為附隨認證放在金鑰旁邊:

```jsonc
"auth": {
  "apiKey": "sk-...",
  "virtualKey": { "header": "x-litellm-api-key", "value": "sk-..." }  // 選填附隨認證: 額外標頭
}
```

把 `Authorization` 或 `X-API-Key` 指定為標頭的附隨認證, 會從 API 金鑰手中接管那一個標頭。

### 自訂標頭中的虛擬金鑰

虛擬金鑰是 LiteLLM 代理自己核發的金鑰, 限定於某個預算、團隊或一組模型 ([LiteLLM 的文件](https://docs.litellm.ai/docs/proxy/virtual_keys))。大多數閘道把它當成一般 bearer 權杖接受 - 那種情況用 `auth.apiKey`。這種形式是給期望它出現在自訂標頭中的閘道:

```jsonc
"auth": {
  "virtualKey": {
    "header": "x-litellm-api-key",
    "value": "sk-..."            // 或存放在祕密儲存體
  }
}
```

把 `Authorization` 指定為標頭, 等於把整個該標頭交給虛擬金鑰。`header` 是必填欄位, 是一般的設定文字; `value` 是可作祕密的那一半, 因此只帶標頭的項目就是[祕密儲存體形態](#祕密與祕密儲存體) - 值從其存放處讀取。

### OAuth 用戶端認證

給位於身分識別提供者之後、拒絕靜態金鑰的閘道:

```jsonc
"auth": {
  "oauth": {
    "tokenUrl": "https://idp.example.com/oauth2/token",
    "clientId": "my-client-id",
    "clientSecret": "...",       // 公用用戶端省略; 可存放在祕密儲存體
    "scopes": "read write"       // 選填, 以空格分隔
  }
}
```

延伸模組用認證換取一個短效 bearer 權杖, 在發往該伺服器的每個請求上以 `Authorization` 送出, 並在到期前不久重新整理。交換在每個請求上都受 `discovery.timeout` 約束 - 它是驗證管線, 不是聊天呼叫, 所以身分提供者緩慢時該調高的是 `discovery.timeout`, 而不是 `chat.timeout`; 在聊天請求上, 交換同時也計入 `chat.timeout` 的整體預算。被拒絕的權杖會被捨棄, 下一個請求會取得新權杖。

**附隨認證** - 有些企業閘道同時檢查兩份認證: OAuth bearer 向身分識別提供者證明您的身分, 而第二個標頭中的 LiteLLM 金鑰告訴代理該向哪個預算或團隊計費。由於 `Authorization` 已被 bearer 佔用, 第二份認證走自己的標頭:

```jsonc
"auth": {
  "oauth": {
    "tokenUrl": "https://idp.example.com/oauth2/token",
    "clientId": "my-client-id",
    "apiKey": "sk-...",          // 選填: 一併送出, 僅作為 X-API-Key
    "virtualKey": { "header": "x-litellm-api-key", "value": "sk-..." }  // 選填: 額外標頭
  }
}
```

把 `Authorization` 指定為標頭的附隨 `virtualKey` 會接管該標頭, 並完全略過 OAuth 交換。

## 自訂標頭

項目的 `headers` 物件為發往此伺服器的每個請求 - 探索與聊天皆然 - 附加額外的 HTTP 標頭。它的職責是閘道管線: 路由標籤、追蹤標頭、額外的閘道金鑰。

```jsonc
{
  "label": "prod",
  "baseUrl": "https://gateway.internal",
  "auth": { "apiKey": "sk-..." },
  "headers": { "x-routing-env": "prod", "x-trace-source": "vscode" }
}
```

- 衝突時延伸模組管理的驗證標頭勝出: 這裡的自訂標頭會輸給項目的 `auth` 形式送出的任何標頭 - `Authorization`、`X-API-Key`, 或虛擬金鑰指定的標頭, 附隨認證也算。名稱依 HTTP 標頭慣例不分大小寫比較, 所以寫 `authorization` 不會改變任何事。
- 和每個項目層級欄位一樣, 標頭只透過與項目的標籤和基底 URL 都相符的提供者群組生效: 過時的群組 (重新命名的殘留, 或早於項目標籤的群組) 送出的請求不帶它們 ([疑難排解](troubleshooting.md#各伺服器模型參數未生效))。
- 因為標頭存放在項目上, 它們是機器範圍的, 從不隨設定同步傳播 - 類似認證的值留在這台機器上。(有意不提供全域標頭設定, 正是出於這個原因。)
- 只有大小寫不同的兩個標頭名稱是同一個標頭 (HTTP 標頭名稱不分大小寫): 物件中的第一個勝出, 衝突作為設定診斷回報。
- 標頭值是一般設定文字, 不是祕密。真正需要保密的值屬於[`auth` 形式](#身分驗證), 後者可以存放在祕密儲存體。

## 各伺服器模型設定

項目的 `models` 物件塑造此伺服器的模型是什麼樣子、如何被呼叫。兩個欄位都對應全域 `models.*` 設定 - 學一次記錄形態, 兩處都能用。

### 參數與能力

- `models.parameters` 針對請求: 它使用與全域 `models.parameters` 相同的[比對鍵](models.md#模型比對), 逐欄位套用在其**之上**。項目記錄是伺服器專屬設定的唯一去處 - 全域鍵只是模型比對器, 沒有伺服器限定。
- `models.capabilities` 針對註冊: token 上限、視覺、工具呼叫、推理 - 修正或補完探索回報的內容。能力與來源無關: 無論模型是被探索的還是[宣告的](#宣告的模型), 套用方式完全相同。

儀表板的編輯表單對兩者都有對應的「此伺服器的...」區段, 帶逐列驗證, 以及與全域編輯器相同的有效值檢查器。

### 宣告的模型

當探索列不出某個模型時 - 沒有 `/v1/models` 的閘道、被閘道隱藏的模型 - 宣告它, 它照樣註冊:

```jsonc
"discovery": { "declared": ["deepseek-r1", "qwen2.5-vl-72b"] }
```

- ID 是精確的 (沒有比對器): 宣告說的是「這個模型在這裡存在」。空的 `declared` 清單等於沒有清單。
- 宣告的模型只在探索尚未列出它時建立; 一旦伺服器開始列出它, 宣告轉為休眠, 伺服器的資料接手。
- 唯一的判準是該 ID 是否被列出 - 而不是它為什麼缺少。無論端點是預期缺少、探索整輪失敗 (伺服器列仍會回報那次失敗), 還是伺服器列出了其他模型卻隱藏了這個, 宣告的模型都會註冊。
- 休眠與生效之間的切換發生在探索回合上: 工作階段中途開始 (或停止) 列出某個已宣告 ID 的伺服器, 在下一次重新整理之前什麼都不會變 - 探索的清單有快取 ([`discovery.cacheTtl`](settings.md#參考)) - 想立即看到就執行 "LiteLLM: Sync Models Now"。
- 兩個項目可以宣告同一個 ID: 各自在自己的伺服器下註冊自己的副本, 和兩個伺服器都提供的模型一模一樣。
- 宣告模型和描述模型是兩個獨立步驟: 宣告模型的能力來自 `models.capabilities`、OpenRouter 目錄和內建預設值, 和其他任何模型完全一樣。
- 宣告始終是按伺服器的。對於透過 VS Code 自己的模型管理新增的伺服器 (沒有項目), 先[採用它](#外部伺服器與採用)。
- 和每個項目層級欄位一樣, 宣告透過項目的標籤加基底 URL 相符來解析: 服務該伺服器的過時群組 (重新命名的殘留, 或早於項目標籤的群組) 不會註冊任何宣告的模型。修法與[未生效的各伺服器參數](troubleshooting.md#各伺服器模型參數未生效)相同。

### 探索與預期失敗

探索先嘗試 `/v1/model/info` (豐富的中繼資料), 再退回 `/v1/models` (單純清單)。請求是冪等的, 暫時性失敗會在 `discovery.timeout` 之內重試。

如果您的閘道就是不提供其中一個或兩個端點, 說出來, 延伸模組就不再把它當成故障:

```jsonc
"discovery": { "expectedFailures": ["modelListing", "modelInfo"] }
```

- 每個被指名的端點只嘗試一次 (不重試), 記一條 info 層級記錄而非紅色錯誤; 伺服器不計為無法連線。
- 「預期」標記的是失敗不足為奇, 而不是端點被禁用: 被指名卻有回應的端點照常使用 - 它的資料照常勝出, 它列出的任何[宣告的](#宣告的模型) ID 轉為休眠。無論成敗, 只嘗試一次是唯一持續的效果。
- 清單中的未知值 (`"modelListing"` 與 `"modelInfo"` 之外的任何東西) 會被忽略並回報。
- 與 `discovery.declared` 組合, 就是完全沒有探索能力的閘道的配方: 宣告模型, 預期兩種失敗, 伺服器表現得像一等公民 - 狀態列、儀表板與「測試連線」都回報宣告的模型而不是錯誤。

## 祕密與祕密儲存體

可作祕密的欄位 - `auth.apiKey`、`auth.oauth.clientSecret`、`auth.virtualKey.value`, 以及附隨認證的金鑰/值 (OAuth 的或 API 金鑰形式的) - 每個都提供逐項目的選擇:

- **內嵌**在 settings.json, 當該檔案中出現純文字值可以接受時。
- **VS Code 祕密儲存體** (加密, 依機器), 透過儀表板表單的「安全儲存」選項或 "LiteLLM: Set Server Secret"。項目隨即乾脆省略該欄位。
- 內嵌值優先於已儲存的值。

儲存的值在 settings.json 中沒有任何標記, 所以形態與儲存共同起作用: 只要項目的形態沒有另作說明, 已儲存的 `apiKey` 就會啟用 bearer - 在完全沒有 `auth` 的項目上、在 API 金鑰形式上, 或與已宣告的 `virtualKey` 並存時 (按級別讀, 那是 API 金鑰形式加附隨認證)。在 `oauth` 之下它保持為附隨認證: `Authorization` 屬於 OAuth bearer, 已儲存的金鑰只以 `X-API-Key` 送出。要停止送出已儲存的金鑰, 請移除儲存的值本身 (下文的核取方塊) - 只刪除設定文字搆不到它。

哪些會回顯到儀表板: 已儲存的值永遠不會 - 表單顯示值存放在哪裡, 不顯示值是什麼。內嵌值會預填到編輯表單 (以「顯示」切換遮罩), 因為它們本來就以純文字存在於您的 settings.json 中。

一個欄位可能同時有兩份副本 - 先安全儲存了一個值, 後來又內嵌貼上一個。請求使用內嵌那份, 儲存的那份原地不動: 清空內嵌欄位會退回使用儲存的值, 而不是清除它。要擺脫儲存的副本, 用編輯表單下方的「移除已儲存的...」核取方塊。

編輯已儲存的項目時:

- 清空的祕密欄位保留已儲存的值; 它不會清除祕密。
- 刪除已儲存的祕密是明確的選擇: 編輯表單在每個已有值的祕密欄位下方顯示「移除已儲存的...」核取方塊。

設定或輪替已儲存的祕密等同於變更項目的認證: 已同步的群組無法接收它, 請求繼續使用群組建立時的認證, 伺服器列會顯示重新建立的步驟 ([生命週期](#生命週期-重新命名移除與隱藏的群組))。

當延伸模組需要為認證保留一個非祕密識別時 (讓同步狀態保持一致的變更偵測器), 它儲存的是以隨機的每次安裝專屬祕密為鍵的指紋, 而非一般雜湊 - 那些記錄不會向能讀取延伸模組狀態但讀不到祕密儲存體的任何東西洩漏認證的任何資訊, 哪怕是一把短到可猜的金鑰。而當 VS Code 的祕密儲存體本身無法使用時 (比如沒有金鑰圈服務的 Linux 桌面), 同步會在這一輪略過該項目, 伺服器列會說明 - 見[疑難排解](troubleshooting.md#祕密儲存體無法使用)。

已儲存的祕密只屬於項目的標籤 - 基底 URL 不參與。兩個後果:

- 直接在 settings.json 中重新命名會把值留在舊標籤下: 在您重新設定它們或從儀表板重新儲存之前, 重新命名後的項目一直不帶認證地運作; 透過儀表板的編輯表單重新命名, 則會替您把已儲存的祕密搬到新名稱下。
- 把熟悉的標籤重新指向另一台主機, 仍會撿起該標籤已儲存的值並送給它。要把退役的標籤重新用於不應看到舊認證的伺服器, 請先移除儲存的值 (編輯表單的「移除已儲存的...」核取方塊)。

移除項目不會刪除它儲存的祕密: 重新加入同標籤的項目會再次找到它們。解除安裝前移除所有祕密的方法見[疑難排解](troubleshooting.md#解除安裝與清理)。

## 生命週期: 重新命名、移除與隱藏的群組

一項 VS Code 限制解釋了整個小節: **主機 API 可以建立提供者群組, 但永遠無法更新或移除它們。**延伸模組誠實地繞過它, 而不是假裝沒有。

| 您做什麼 | 發生什麼 |
|---|---|
| 新增項目 | 建立一個提供者群組; 模型出現在選擇器中 |
| 變更項目的 URL 或認證 | 既有群組無法更新。伺服器列顯示錯誤與修法: 從模型檔案刪除該群組的物件、重新載入、執行 "LiteLLM: Sync Models Now" - 群組會從項目重新建立。在那之前, 請求繼續使用群組建立時的認證 - 輪替後的金鑰尚未生效 |
| 重新命名項目 (`label`) | 在新名稱下建立新群組; 舊群組留在原處。延伸模組的通知會點名它並開啟模型檔案, 以便刪除它的物件; 儀表板把殘留列標示為「外部」, 徽章提示中註明這次重新命名。直接在 settings.json 中重新命名不會搬動該標籤已儲存的祕密 - 它們留在舊名稱下 ([祕密](#祕密與祕密儲存體)); 透過儀表板重新命名會把它們帶過去 |
| 移除項目 | 群組無法被移除, 所以延伸模組*隱藏*它: 記住這次移除, 用空模型清單回應該群組 (模型離開選擇器), 把該列折疊進儀表板的「隱藏的群組」一行並提供「取消隱藏」動作。移除通知點名該群組並開啟模型檔案以便永久刪除 |
| 重新加入標籤與基底 URL 相同的項目 | 它隱藏的群組自行回歸 |

模型檔案是 `<profile>/User/chatLanguageModels.json` - 一個有文件說明、使用者可編輯的 JSON 檔案。VS Code 在啟動時讀取它並保留在記憶體中, 因此編輯後請結束或重新載入視窗; 執行中的視窗可能覆寫外部編輯。

## 外部伺服器與採用

群組在本延伸模組之外新增的伺服器 (VS Code 自己的模型管理介面 - 模型選擇器中的 "Manage LiteLLM Provider" 流程 - 或其他工具) 仍然可用; 由於沒有設定項目, 儀表板把它們標示為「外部」。當延伸模組知道來歷時, 徽章的懸停提示會說明該列從何而來 - 已移除項目的殘留 (註明名稱), 或重新命名的殘留 (註明新舊標籤)。

外部列提供兩個動作:

- **移除**會隱藏該群組, 與移除宣告項目相同; 後續通知會開啟模型檔案以便永久刪除。
- **編輯**會把該群組採用進設定:

1. 在外部列上按一下「編輯」- 那就是採用動作。
2. 選擇項目的標籤。表單會預填該群組目前的標籤, 但通常值得改名: 名稱仍被某個既有群組占用的項目, 在該群組的物件從模型檔案刪除之前無法同步。
3. 選擇每個祕密的存放位置 (祕密儲存體或內嵌)。認證值在延伸模組內部複製, 絕不經過儀表板頁面。
4. 儲存: 該群組的連線細節成為一個新的 `servers` 項目, 像任何宣告的項目一樣可編輯。
5. 從模型檔案刪除原始群組的物件並重新載入 (採用無法移除它); 在那之前它的模型會出現兩次 - 採用之後儀表板會提醒您。

## 多台機器與設定同步

- `servers` 設定是機器範圍的; 設定同步 (Settings Sync) 從不攜帶它。祕密儲存體中的值同樣不同步。在第二台機器上, 請重新加入伺服器及其祕密。
- 其他每個 `litellm-vscode-chat.*` 設定都正常同步 - 包括 `models.parameters` 與 `models.capabilities`, 所以您的模型設定會跟著您走。在伺服器尚未重新加入的機器上, 這些同步來的記錄只是沒有模型可比對 - 它們靜靜待命, 伺服器一到位就立即生效。任何綁定伺服器的東西 (認證、自訂標頭、預算) 都存放在項目上, 依設計留在原地。
