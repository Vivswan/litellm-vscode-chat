- [能力](#能力) - 模型能做什麼: 欄位詞彙表、覆寫、後備、OpenRouter 目錄、定價、token 上限
- [參數](#參數) - 請求要求什麼: 直通契約、`max_tokens` 例外、強制、優先順序
- [選擇器](#選擇器) - 模型如何呈現在 Copilot Chat 中, 以及各模型的「設定」選單

三個概念承載整頁。**能力**描述模型*能做什麼* - 它們在註冊時解析一次, 決定模型被提供來做什麼。**參數**是請求*要求它做什麼* - 逐請求解析, 隨請求上線送出。**宣告**是在探索看不見時宣布模型*存在*。三者從不混淆: 能力從不作為請求欄位送出, 參數也從不改變模型註冊成什麼。

## 模型如何出現

### 探索

延伸模組詢問每個已設定的伺服器它提供什麼 - 在啟用時、設定變更時, 以及每當 VS Code 重新解析其模型提供者時:

- 探索先讀 `/v1/model/info` - 帶有 token 上限、價格與能力旗標的豐富端點 - 當該呼叫失敗、未回傳資料陣列, 或回傳的項目沒有一個可用時, 退回單純的 `/v1/models` 清單。格式良好的空清單註冊零個模型, 不觸發退回。
- 探索請求是冪等的 GET, 所以暫時性失敗會重試; 整輪 - 含重試與任何 OAuth 權杖交換 - 受 `discovery.timeout` (預設 30 秒) 約束。重試規則詳情: [疑難排解](troubleshooting.md#逾時與重試)。
- *預期*某端點失敗的伺服器 (沒有模型清單的閘道) 在項目的 `discovery.expectedFailures` 裡說明: 單次嘗試、一條 info 層級記錄、沒有錯誤噪音。見[伺服器](servers.md#探索與預期失敗)。
- 結果會沿用 `discovery.cacheTtl` (預設 1 小時), 因為 VS Code 重新解析提供者很頻繁 - 有時一秒好幾次。失敗從不快取, 同時發生的重新整理共用一個請求, "LiteLLM: Sync Models Now" 在您需要立即拿到新清單時略過快取。
- 當背景重新整理失敗, 但最近一次成功探索仍在 `discovery.staleServeWindow` 之內 (預設十分鐘) 時, 最後已知的模型保持可用, 標記為過時 (警告圖示加懸停說明), 而不是在工作階段中途從選擇器裡消失。伺服器休眠或重啟更久就調高這個視窗; 設為 `0` 則首次重新整理失敗即移除該伺服器的模型。

### 宣告的模型

探索不是唯一入口: 伺服器項目的 `discovery.declared` 列出即使伺服器列不出也要註冊的精確模型 ID, 而探索開始列出某個 ID 後, 對應宣告轉為休眠。宣告模型和描述模型是兩個獨立步驟 - 宣告模型的[能力](#能力)與每個被探索模型一樣, 從相同來源解析, 它在[儀表板的模型清單](dashboard.md#模型)的列上標註「宣告」。完整的故事, 包括無探索能力閘道的單物件配方, 在[伺服器 - 宣告的模型](servers.md#宣告的模型)。

### 哪些模型會註冊

可連線伺服器回報的每個可聊天模型都會出現在選擇器中。三條排除規則:

- `model_info.mode` 指向非聊天端點 (`embedding`、`image_generation`、`audio_speech`、`audio_transcription`、`rerank`、`moderation`) 的模型被刻意排除, 因為對它們的聊天請求只會失敗。未宣告 mode 的模型始終註冊。
- 代理已暫停的部署 (`model_info.blocked`) 被略過。
- 其他不做任何過濾: 完全沒有能力資料的模型照樣註冊, 空缺由下文的[能力來源](#能力優先順序)填補。

### 負載平衡池

當一個模型名稱由多個部署提供 (負載平衡池) 時, 它註冊一次, 採用最嚴格貢獻者的 token 上限, 這樣請求絕不會超出實際服務它的那個部署。這次合併與 [`max_tokens` 例外](#max_tokens-例外)相關: 合併後的輸出上限只有在每個部署都宣告了輸出上限時才算已宣告。

同樣保守的合併不止於 token 上限: 池只有在每個部署都宣告某項能力時才對外宣告它 - 一個部署宣告關閉工具呼叫, 池就失去它; 一種模態 (視覺、音訊) 只有在所有部署都具備時才留存; 「思考力度」控制項只在每個部署都宣告推理時出現 (其伺服器宣告的檔位選單收窄為每個部署都標記的檔位)。定價只在每個部署逐欄位宣告完全一致的成本時顯示 (不一致時, 請求實際花多少由代理的路由決定, 所以選擇器寧可不顯示, 也不顯示錯誤數字); 選擇器的提供者名稱跟隨第一個部署。被合併丟掉的能力可以用 [`models.capabilities` 覆寫](#能力)恢復。

### 提供者路由與彙總項目

帶有 `providers` 路由陣列的模型註冊方式不同。兩個探索端點都可能攜帶這類項目; 常規 LiteLLM 代理通常不會, 對同一模型名稱做負載平衡的代理也不會產生這種形態 (那些部署合併進上面的單一項目)。

- 當至少一條路由支援工具時 (一條就夠), 每條支援工具的路由註冊自己的選擇器項目 (命名為 `via <provider>`), 外加 `(cheapest)` 與 `(fastest)` 彙總項目, 讓 LiteLLM 按請求挑選路由; 此時不註冊無後綴的基礎項目。
- 當沒有路由支援工具時, 只註冊一個基礎項目, 沒有彙總項目。
- 彙總項目對外宣告最嚴格的支援工具路由的 token 上限。

這些項目在自己的 ID 下註冊 - `<id>:cheapest`、`<id>:fastest` 與 `<id>:<provider>` - [比對鍵](#模型比對)比對的就是這個帶後綴的 ID, 而不是伺服器回報的基礎 ID: 像 `gpt-4` 這樣的精確鍵碰不到它們之中的任何一個, 而萬用鍵 (`gpt-4*`) 涵蓋整個家族。[儀表板的模型清單](dashboard.md#模型)的複製動作給出的就是精確的帶後綴 ID。

## 模型比對

兩個以模型為鍵的記錄 - `models.parameters` 與 `models.capabilities`, 全域與各項目皆然 - 用相同的鍵語法選中模型。鍵比對的是伺服器回報的模型精確 ID (路由型模型的項目按其[帶後綴的 ID](#提供者路由與彙總項目) 比對), 而選擇器不顯示它; [儀表板的模型清單](dashboard.md#模型)在每列上提供複製它的動作。

**除非鍵自己說明, 否則按精確比對處理:**

| 鍵 | 比對 | 備註 |
|---|---|---|
| `"gpt-5"` | 只比對 ID `gpt-5` | 不比對 `gpt-5.7`, 也不比對 `gpt-5-turbo` |
| `"gpt-5*"` | 以 `gpt-5` 開頭的每個 ID | 萬用字元 (glob); `*` 必須在結尾 |
| `"/gpt-[45].*/"` | 正規表示式比對到的一切 | 以斜線包裹, 對整個 ID 比對; 在結尾斜線後加 `i` 表示不分大小寫 (`"/GPT-5.*/i"`); 其他任何旗標或無效模式會在儀表板中回報並被忽略 |
| `"*"` | 每個模型 | 您的預設值放這裡 |
| `""` | 什麼都不比對 | 無效; 回報並忽略 |

鍵逐字元比較: 不做任何修剪 (前導空格是鍵的一部分), 精確鍵與萬用字元鍵區分大小寫 - `/re/i` 是唯一不分大小寫的形式。對不尋常的 ID 與不完美的記錄, 有幾個推論:

- 含 `/` 的 ID (比如 `anthropic/claude-4`) 由一般精確鍵比對 - 只有以 `/` *開頭*的鍵才算正規表示式形態。在以 `/` 開頭的鍵裡, 最後一個 `/` 之後只能跟受支援的旗標 (`i`, 或什麼都不跟), 所以 `"/anthropic/claude"` 無效並被回報; 自身以 `/` 開頭的 ID 要用把斜線寫進正規表示式主體的鍵來比對 (`"/\\/anthropic.*/"`)。
- 以 `*` 結尾的鍵總是讀作萬用字元, 所以字面以 `*` 結尾的 ID 需要用跳脫星號的正規表示式: `"/gpt-5\\*/"`。
- `*` 出現在鍵結尾之外的任何位置 (`"gpt*5"`) 既不是萬用字元也不是字面值 - 該鍵無效, 回報並忽略, 與空鍵或格式錯誤的正規表示式相同。
- 以 `_` 開頭的記錄鍵是指示詞, 永遠不是比對器, 所以以 `_` 開頭的 ID 只能由正規表示式鍵比對。
- 比對不到您目前任何模型的鍵不是錯誤: 它只是從不生效, 靜靜待命, 等這樣的模型出現。只有格式錯誤的鍵 (無效正規表示式、不支援的旗標、`""`) 才會被回報 - 它的記錄隨即永遠比對不到任何東西。
- 在一筆記錄裡把同一個鍵寫兩次是 JSON 問題, 不是比對器問題: VS Code 的編輯器會警告重複, 解析後只有最後一次出現存活 - 延伸模組根本看不到第一個。

鍵是模型比對器, 僅此而已 - **全域層面沒有伺服器限定**。針對單一伺服器的設定放在那個伺服器項目自己的 `models.parameters` / `models.capabilities` 記錄裡, 語法相同 ([伺服器](servers.md#各伺服器模型設定))。對於透過 VS Code 自己的模型管理新增的伺服器 (沒有項目), 先[採用它](servers.md#外部伺服器與採用)。

原生設定 GUI 無法編輯物件設定, 因此[儀表板](dashboard.md)為兩個記錄提供列編輯器: 比對器欄位會建議您已探索的模型 ID, 「以 JSON 編輯」切換接受貼上的記錄, 編輯只在您按下「套用」時落地。直接在 settings.json 編輯 JSON 效果相同。

### 哪筆記錄生效

具體度為相符的鍵排序: 精確鍵比萬用字元鍵更具體 (萬用字元鍵之間, 字面前置詞較長者勝出), 萬用字元鍵比正規表示式鍵更具體 (正規表示式鍵之間, 記錄中較後者勝出), 一切都勝過 `"*"`。層級是嚴格的: 任何萬用字元鍵都排在任何正規表示式鍵之上, 無論正規表示式讀起來多窄, 而 `"/.*/"` 排在 `"*"` 之上, 儘管兩者比對相同的模型 - 它按正規表示式計層。平手幾乎不存在: 比對同一 ID 的兩個不同萬用字元鍵前置詞長度必然不同 (前置詞相等就成了同一個鍵), 正規表示式鍵之間由記錄中較後者決定 - 與下文繼承鏈中較後正規表示式更靠近模型的順序一致。

**預設情況下, 最具體的相符記錄整體勝出** - 它的欄位套用, 其他記錄一概不滲入。兩個指示詞控制流動 - 給方標記欄位, 收方做決定 - 而收方永遠說了算:

| 指示詞 | 側 | 意義 |
|---|---|---|
| `"_inheritable": true \| ["field", ...]` | 給方 | 把全部/列出的欄位標記為可繼承: 任何比對得更具體、自身記錄未另行聲明的模型都會繼承它們 (僅限它未設定的欄位; 每個欄位以最近的可繼承值為準) |
| `"_inherit_from": ["key", ...]` | 收方 | 恰好從指名的記錄繼承 - 它們的全部字面欄位, 最近者優先 - 除此之外不繼承任何東西。指名即是全部意圖: 被指名的記錄不需要 `_inheritable`, 它自己的繼承設定不隨之傳遞, 它與本記錄之間的屏障被繞過。清單項目是精確的記錄鍵, 且還必須比對到該模型 - 被指名卻不比對該模型的記錄對它沒有任何貢獻 (繼承有來源, 沒有包含); 指名不存在的鍵會在儀表板中標記, 清單其餘部分照常生效 |
| `"_inherit_from": true` | 收方 | 繼承到達本記錄的一切 - 下一個更寬比對的完整檢視, 無論是否標記為可繼承; 屏障仍然生效 |
| `"_inherit_from": false` | 收方 | 什麼都不繼承 - 完全自給自足。而且由於更寬的欄位只能透過本記錄的解析檢視到達更具體的記錄, 也沒有任何東西能越過它流動: `false` 就是屏障 |

可繼承欄位沿具體度鏈傳遞, 並且必須*穿過*來源與模型之間的每筆記錄: 每筆記錄只向上傳遞它自己接受的東西。因此帶 `"_inherit_from": false` 的記錄會切斷鏈條 - 它把自己*和*所有更具體的記錄都與更寬的記錄隔離開。繞過屏障的唯一辦法是指名: `"_inherit_from"` 清單直達它指名的記錄, 屏障與否無關。

實例 - 同一個家族, 兩種設定方式:

```jsonc
"litellm-vscode-chat.models.parameters": {
  "*":        { "temperature": 0.7, "top_p": 0.9, "_inheritable": true },
  "gpt-5*":   { "temperature": 0.3, "_inheritable": true, "_inherit_from": false },
  "gpt-5.6":  { "max_tokens": 8192 },
  "claude*":  { "max_tokens": 4000 },
  "claude-4": { "temperature": 1.0 }
}
```

| 模型 | 結果 | 原因 |
|---|---|---|
| `gpt-5.6` | `max_tokens: 8192, temperature: 0.3` | 保持沉默, 於是繼承到達它的東西: `gpt-5*` 把 `temperature` 標為可繼承; 萬用鍵的 `top_p` 死在 `gpt-5*` 的屏障上 |
| `gpt-5`、`gpt-5.7`、... | `temperature: 0.3` | 最佳比對是 `gpt-5*`, 它自給自足 - 萬用鍵的欄位止步於此 |
| `claude-4` | `temperature: 1.0, top_p: 0.9` | 自己的 `temperature` 勝出; `top_p` 從萬用鍵出發, 原樣穿過沉默的 `claude*` 記錄。`claude*` 自己的 `max_tokens` 不跟來: 它從未被標記為可繼承 |
| `claude-4.1` | `max_tokens: 4000, temperature: 0.7, top_p: 0.9` | 最佳比對是 `claude*`, 整體套用, 外加萬用鍵中它未設定的可繼承欄位 |
| 其餘一切 | `temperature: 0.7, top_p: 0.9` | 萬用鍵本身就是最佳比對 |

`claude-4` 那一列是穿透規則的現場示範: 沒有指示詞的記錄是透明的 - 可繼承欄位原樣穿過它, 仍然帶著來源的標記, 而它自己未標記的欄位留在原地。

`"_inherit_from"` 清單明確指定祖先 - 它也是繞過屏障的唯一辦法:

```jsonc
"gpt-5.6": { "max_tokens": 8192, "_inherit_from": ["gpt-5*"] }
// -> max_tokens 8192 + temperature 0.3 (恰好是指名的記錄, 別無其他)

"gpt-5.6": { "max_tokens": 8192, "_inherit_from": ["gpt-5*", "*"] }
// -> max_tokens 8192, temperature 0.3, top_p 0.9 - 指名 "*" 繞過了屏障
```

#### 邊界情況

- `"_inherit_from": []` 沒有指名任何記錄, 所以什麼都不繼承 - 空清單的行為與 `false` 完全一樣, 屏障效果也在內。
- `"_inherit_from"` 清單的順序無關緊要, 把同一記錄指名兩次也不增加任何東西: 兩筆被指名的記錄設定了同一欄位時, 更具體者勝出 - 「最近者優先」指的是具體度順序, 不是清單順序。
- 記錄在 `"_inherit_from"` 中指名自己是無作用: 它貢獻的是自己的字面欄位, 而記錄本來就有它們 - 自己的欄位永遠勝過繼承來的。
- 在 `"*"` 記錄上寫 `"_inherit_from": false` 不改變任何事: 萬用鍵是最寬的比對, 沒有更寬的東西可繼承或可阻擋。它的 `_inheritable` 標記照常給出 - `_inherit_from` 只管記錄接收什麼。
- `"_inherit_from": true` 讀取的是下一個更寬比對的*解析檢視*: 該記錄自己的欄位, 加上它從更外層接受的東西。如果那筆記錄本身是屏障, 它的檢視就只有自己的欄位 - `true` 看不穿它。
- 只有欄位會流動。指示詞是其所在記錄自己的指示: 更寬記錄的 [`_openrouter_model`](#openrouter-目錄)、`_inheritable` 或 `_inherit_from` 從不隨繼承傳遞。被繼承欄位隨身攜帶的只有來源的 `_inheritable`、`_fallback` 或 `_force` 標記 - 僅此而已。
- 鏈條從不跨層: 項目記錄的 `"_inherit_from"` 指名該項目自己記錄中的鍵, 全域記錄指名全域鍵。每層獨立解析自己的整條鏈, 然後項目結果才逐欄位勝過全域結果。指名只存在於另一層的鍵, 等同於指名不存在的鍵: 在儀表板中標記, 清單其餘部分照常生效。

兩條獨立規則位於這條流動之外: 伺服器項目的記錄逐欄位勝過全域記錄 (各自先用自己的比對解析), 流動的欄位保留其來源記錄的 [`_fallback`](#後備值-_fallback) 或 [`_force`](#強制參數-_force) 標記。

解析從不按請求發生: 每個模型的扁平結果計算一次並快取 - 只在設定、項目或模型清單變更時重算 - 請求只在其上合併執行階段值。[檢查器](#檢查器)與診斷區段的[已解析模型檢視](dashboard.md#診斷)呈現的正是這張快取的表 - 除錯比對器的最快方式, 也正是將要送出的內容。

### 從前置詞鍵移轉

舊版本的鍵是隱含前置詞: `"gpt-5"` 也比對 `gpt-5.7` 與 `gpt-5-turbo`。升級移轉會給每個既有鍵附加 `*` (並把舊的全比對 `""` 變成 `"*"`), 所以舊設定繼續比對它們以前比對的東西。只有從現在起您新寫的鍵採用預設精確規則。

舊版本還允許在全域記錄中使用伺服器 URL 限定鍵 (`"https://litellm.example.com/gpt-4"`)。移轉把每個這樣的鍵無損合併進相符的伺服器項目記錄。URL 比對不到任何項目的限定鍵留在原地 - 它永遠比對不到模型 ID, 所以是休眠的 - 儀表板會標記它並提示移入伺服器項目。完整的重新命名故事: [設定](settings.md#重新命名與移除的設定)。

## 能力

能力是註冊時的事實: 它們決定模型被提供來做什麼 (工具、影像、推理)、它的 token 上限, 以及送出哪些附件。它們從不改變請求要求模型做什麼 - 那是[參數](#參數)的職責。

能力**與來源無關**: 下面的解析既不知道也不在乎模型是被探索的還是[宣告的](#宣告的模型)。沒有伺服器資料的宣告模型只是從其餘來源解析 - [比對](#模型比對)對它的 ID 一視同仁, 所以 `"*"` 記錄的可繼承欄位或後備值同樣到達宣告的模型。

### 能力欄位

`models.capabilities` 記錄 (全域設定與[各項目欄位](servers.md#各伺服器模型設定)) 修正與擴充伺服器回報的內容。與 `models.parameters` 一樣, 這套詞彙表是**開放的**: 伺服器是您的, 它的 `model_info` 可能攜帶延伸模組從未聽過的欄位, 所以任何欄位名稱都會被接受並套用。欄位之間的差別只在於它們驅動什麼。

**核心七項**決定註冊; 它們總會解析出值 (內建預設值兜底 - `max_input_tokens` 則由「上下文減輸出」衍生兜底), 取正整數或布林值:

| 欄位 | 型別 | 控制什麼 |
|-------|------|------------------|
| `context_length` | 數字 | 模型的上下文視窗 |
| `max_input_tokens` | 數字 | 輸入預算; 無人設定時為上下文長度減最大輸出 token 數 |
| `max_output_tokens` | 數字 | 輸出上限, 兼作 `max_tokens` 後備 ([例外](#max_tokens-例外)) |
| `supports_function_calling` | 布林 | 使用工具的請求 (代理模式) |
| `supports_vision` | 布林 | 是否送出影像附件 |
| `supports_reasoning` | 布林 | 選擇器中的 Thinking Effort 控制項 |
| `supports_audio_input` | 布林 | 是否送出音訊附件 |

**被消費的欄位**是延伸模組會在某處讀取的其餘一切欄位; 每個都按其型別驗證, 無效值會被標記並由次佳來源頂上, 與核心欄位完全一樣:

| 欄位 | 型別 | 驅動什麼 |
|-------|------|------------------|
| `input_cost_per_token`、`output_cost_per_token` | 成本 | 選擇器與儀表板中的[定價](#定價) |
| `cache_read_input_token_cost`、`cache_creation_input_token_cost` | 成本 | 快取定價數字 |
| `long_context_input_cost_per_token`、`long_context_output_cost_per_token`、`long_context_cache_read_input_token_cost`、`long_context_cache_creation_input_token_cost` | 成本 | 長上下文分層定價。寫這些合成名稱即可; 探索會替您把 LiteLLM 帶門檻後綴的線上鍵 (`input_cost_per_token_above_200k_tokens` 等) 解析成它們 |
| `supports_prompt_caching` | 布林 | 是否放置提示快取標記 - 唯一會改變請求內容的能力。該功能仍是雙重門控: [`chat.promptCaching` 設定](settings.md#提示快取)也必須開啟 |
| `supports_pdf_input`、`supports_response_schema` | 布林 | 目前什麼都不驅動: 兩者都會解析並顯示在[能力檢查器](#檢查器)中, 但不門控任何行為 - PDF 無論如何都送給每個模型 ([多模態輸入](#多模態輸入)) |
| `supported_openai_params` | 字串陣列 | 清單中含 `reasoning_effort` 是 Thinking Effort 控制項在 `supports_reasoning` 之外的第二個訊號; 兩者中在更高優先層解析出的那個說了算, 平手時旗標勝出 |
| `reasoning_effort_levels` | 字串陣列 | Thinking Effort 選單的檔位, 按選單順序 ([各模型設定](#各模型設定))。任何檔位名稱都可以 - 選單原樣呈現您的字串並按原樣送出。只決定選單的內容, 不決定控制項是否存在 |

成本欄位取非負的每 token 美元數; 您自己寫下零對表示真正免費 ([定價](#定價))。

**其餘一切** - 任何其他不以 `_` 開頭的欄位 - 都是開放的附加欄位: 按原樣保留 (任何名稱都行, 連 `toString` 這樣彆扭的也可以), 透過與其他欄位完全相同的比對、優先順序和繼承解析, 並帶出處顯示在[能力檢查器](#檢查器)和[已解析模型檢視](dashboard.md#已解析模型)中。它的值只來自您的記錄: 探索只為核心和被消費的欄位讀取伺服器的回報, 所以伺服器端的自訂欄位從不提供值 - 它的*名稱*仍算作下文的筆誤證據。註冊目前不消費開放附加欄位; 未來版本可能會。

驗證是建議性的, 從不攔截。延伸模組不消費的欄位名稱只有在存在它可能是筆誤的真實證據時, 才會在檢查器中得到一條「不是本延伸模組認識的欄位」的說明: 也就是伺服器自己的 `/model/info` 鍵集已知、非空且不含該欄位。沒有這種證據 - 只有宣告模型的項目、預期的 `modelInfo` 失敗、`/models` 退回 - 就根本不會有說明。無論哪種情況, 該值都按原樣作為覆寫套用: 關於您自己的伺服器, 您永遠是對的。

### 伺服器回報什麼

探索從模型資訊讀取能力:

| 能力 | 從模型資訊讀取 | 備註 |
|------------|----------------------|-------|
| 工具呼叫 | `supports_function_calling` (或 `supports_tool_choice`); 提供者路由攜帶 `supports_tools` | 未宣告時視為開啟; 只有明確的 `false` 才關閉 |
| 視覺 | `supports_vision` | |
| 音訊輸入 | `supports_audio_input` | |
| 推理 | `supports_reasoning`, 或 `supported_openai_params` 中含 `reasoning_effort` | 明確的 `supports_reasoning: false` 勝出 |
| 推理強度檔位 | `supports_<level>_reasoning_effort` 旗標 (例如 `supports_max_reasoning_effort`) | 標為 `true` 的檔位成為 Thinking Effort 選單; `false` 與 `null` 視為未回報, 完全沒有 `true` 旗標時選單退回內建清單 |
| 提示快取 | `supports_prompt_caching` | 與每個欄位一樣可覆寫; 該功能仍受 `chat.promptCaching` 雙重門控 ([設定](settings.md#提示快取)) |
| 定價 | 八個成本欄位 (`input_cost_per_token` 等) | 恰好為 0/0 的輸入/輸出對是 LiteLLM「沒有定價資料」的印記, 視為完全沒有回報 ([定價](#定價)) |
| Token 上限 | 模型資訊的 token 上限欄位 | 見 [Token 上限](#token-上限) |

伺服器端的錯誤旗標值得在伺服器上修: 延伸模組雙向信任宣告, 提供被宣告的, 保留未宣告的。伺服器不歸您管時, 就改用覆寫。

一處不對稱: 伺服器明確回報的 `supports_vision: false` 或 `supports_audio_input: false` 被當作沒有回報處理, 所以對知名的模型 ID, [隱含目錄比對](#openrouter-目錄)可能把該能力重新打開。要讓這樣的模型保持不收影像或音訊, 請自己在 `models.capabilities` 中寫下 `false` - 覆寫總是勝出 - 或者停用目錄。

### 覆寫

一般的能力欄位說的是「伺服器錯了 (或沒說) - 用這個」: 您的值逐欄位勝過伺服器的。

```json
{
  "litellm-vscode-chat.models.capabilities": {
    "gpt-4": { "context_length": 128000, "supports_vision": true },
    "my-gateway-model": { "max_output_tokens": 32000 }
  }
}
```

伺服器項目可以攜帶限定到自己模型的同款記錄 (`models.capabilities`, 同樣的[比對語法](#模型比對), 不需要 URL 限定, 因為項目已經指明了自己的伺服器); 項目欄位逐欄位勝過全域欄位。儀表板的伺服器表單有對應的「此伺服器的...」區段。詳情: [伺服器](servers.md#各伺服器模型設定)。

### 後備值: `_fallback`

覆寫說「伺服器錯了」; 後備說「以防伺服器沒說」。`_fallback` 指示詞把記錄中的欄位變成補缺者, 套用在伺服器回報值*之下*:

```jsonc
"litellm-vscode-chat.models.capabilities": {
  "*": {
    "_fallback": true,             // 此記錄的每個欄位都是後備
    "context_length": 131072,      // 僅在伺服器未回報時使用
    "max_output_tokens": 8192
  },
  "qwen*": {
    "_fallback": ["supports_vision"],  // 只有列出的欄位是後備
    "supports_vision": true,           // 補缺; 伺服器的 "false" 勝出
    "context_length": 32768            // 未列出: 一般覆寫, 勝過伺服器
  }
}
```

- `_fallback: true` 讓記錄中的每個欄位都成為後備; `_fallback: ["field", ...]` 只讓列出的欄位後備, 其餘仍是一般覆寫。記錄設定的任何欄位都可以帶這個標記 - 核心、成本或開放附加欄位皆可。
- 後備提供的 `max_output_tokens` 對 [`max_tokens` 例外](#max_tokens-例外)仍算使用者設定: 解除 4096 上限。
- 被繼承的欄位帶著來源的標記到達: 後備無論被[繼承](#哪筆記錄生效)帶到哪裡都還是後備, 而接收記錄不能重新標記不是自己寫的欄位 (它自己的 `_fallback` 清單只能指名自己的欄位; [`_force`](#強制參數-_force) 遵循同一來源側規則)。想讓某個模型把繼承來的後備變成硬覆寫? 在那裡寫明: `"gpt-5.6": { "context_length": 200000 }` - 自己的、未列出的欄位就是覆寫, 而且只有那個模型脫離來源。
- 指示詞清單只能指名自己記錄中存在的欄位: 指名不存在的欄位會作為無效指示詞回報, 略過該名稱, 清單其餘部分照常生效 (接收方重新標記限制建立在同一規則上)。已知指示詞出現在錯誤的記錄類型中 - `_fallback` 在參數記錄裡、`_force` 在能力記錄裡 - 會被回報並忽略, 而真正未知的 `_` 鍵為向前相容保持靜默忽略。

和每個指示詞一樣, 底線鍵是給延伸模組的指示 - 從不送出到任何地方。

### OpenRouter 目錄

延伸模組內建一份 [OpenRouter](https://openrouter.ai) 公開模型目錄的快照, 用它填補其他來源都不提供的能力欄位。目錄只攜帶能力 - token 上限、視覺、工具、推理 - 從不攜帶定價: 任何成本欄位都不會來自它, 明確指示詞與隱含比對皆然 ([定價](#定價))。模型與目錄相遇的兩種方式:

- **明確**: `"_openrouter_model"` 為目錄永遠猜不到 ID 的模型指名目錄項目:

  ```json
  {
    "litellm-vscode-chat.models.capabilities": {
      "my-alias": { "_openrouter_model": "anthropic/claude-sonnet-4" }
    }
  }
  ```

  由此衍生的欄位排在伺服器回報*之上* - 該指示詞表示對這個模型不可信任伺服器的資料。同一記錄中您明確寫的欄位仍然勝過目錄的。未知的目錄 ID 在[能力檢查器](#檢查器)中顯示警告, 模型退回其他來源; 它永遠不是錯誤。儀表板的能力編輯器為該 ID 提供搜尋選擇器。和每個指示詞一樣, `_openrouter_model` 屬於它所在的記錄: 它從不被繼承 - 記錄之間只有欄位流動 - 更具體的相符記錄會連同該記錄的其餘欄位一起遮蔽它, 所以如果那個模型仍然需要, 請在那裡重申該指示詞。

- **隱含**: 沒有指示詞時, 自身 ID 與某個目錄項目精確相符的模型 (或與 `vendor/` 前置詞之後的部分相符, 當只有一個項目相符時) 仍會從目錄補缺 - 但只作為內建預設值之上最弱的來源, 永遠無法取代伺服器回報的資料或您的設定。

資料從哪裡來, 以及唯一的網路影響:

- 快照隨 VSIX 一起發布, 大約每週從 `https://openrouter.ai/api/v1/models` 重新整理一次 - 一份公開、不需驗證的模型清單。請求不攜帶提示、不攜帶用量、不攜帶帳戶資料, 也不攜帶任何關於您伺服器的資訊; 重新整理的副本快取在 VS Code 的全域儲存區, 重新整理失敗會靜默退回快取或內建的快照。
- 用 "LiteLLM: Refresh OpenRouter Catalog" 命令隨選重新整理, 或用該設定儀表板列上的「重新整理」按鈕 - 該列還顯示目錄的大小與上次更新時間。手動重新整理失敗會在列狀態中回報 - 沒有彈出視窗。
- **退出**: 把 `litellm-vscode-chat.models.openRouterCatalog` 設為 `false` 可停止週期重新整理 (所有目錄網路存取) 與隱含比對; 儀表板列轉為休眠並附提示。明確的 `_openrouter_model` 指示詞繼續離線運作, 使用內建或快取的快照 - 它們是您聲明的意圖, 不需要網路。

### 能力優先順序

逐欄位, 設定了它的最高來源勝出 - 每個欄位都走同一條鏈, 核心、成本和開放附加欄位一視同仁。在每個記錄層內, 由[比對規則](#哪筆記錄生效)在相符的鍵之間挑選:

1. 項目 `models.capabilities`
2. 全域 `models.capabilities`
3. 由明確 `_openrouter_model` 指示詞衍生的欄位
4. 伺服器回報的內容 - 僅限核心和被消費的欄位 (宣告的模型沒有; 恰好為 0/0 的輸入/輸出成本對視為完全沒有定價回報 - [定價](#定價))
5. `_fallback` 欄位 (項目在全域之上, 各層內部按比對規則)
6. 隱含 OpenRouter 目錄比對
7. 核心欄位的內建預設值: 工具開、視覺/音訊/推理關、上下文 128000、最大輸出 16000; `max_input_tokens` 沒有自己的預設值, 而是衍生為上下文長度減最大輸出。其他欄位沒有預設值, 上面沒人設定時就保持缺席

值得知道的兩個推論:

- 您自己設定的 `max_output_tokens` - 第 1、2 或 5 層 - 算作使用者宣告, 成為線上的 `max_tokens` 時原樣送出; 模型的每個部署都宣告了的伺服器上限同樣如此。任何目錄衍生值 (明確指示詞或隱含比對) 與內建下限都算猜測, 把線上的 `max_tokens` 封頂在 4096 ([例外](#max_tokens-例外))。要為目錄背書的模型解除上限, 自己寫一個 `max_output_tokens`。
- 目錄層 (第 3 和第 6 層) 只攜帶能力, 從不攜帶成本欄位, 所以價格只能來自伺服器的回報或您自己 ([定價](#定價))。

### 定價

模型的價格恰好來自兩個地方 - LiteLLM 的 `/model/info` 回報和您自己的 `models.capabilities` 成本欄位 - 透過上面的[優先順序](#能力優先順序)解析:

- 伺服器的回報是基準, 附帶一條讀取規則: 恰好為 0/0 的輸入/輸出成本對是 LiteLLM 給沒有定價資料的模型打的印記, 所以它算作未宣告 - 不顯示價格, 印記旁零散的快取或長上下文成本也隨之捨棄。
- 您的成本欄位像任何能力覆寫一樣逐欄位勝過伺服器的; 標了 `_fallback` 的只在伺服器未回報處補缺。
- *您*寫下的 0/0 對與伺服器的印記不同: 您說了這個模型免費, 所以它按真正免費定價 - $0 in / $0 out, 外加 cheapest 徽章。
- OpenRouter 目錄從不提供定價, 所以免費部署上的知名模型 ID 不會繼承公開價目表。

### Token 上限

三個數字約束每個請求, 透過上面的優先順序解析:

- `context_length` 是模型的整個視窗。
- `max_input_tokens` 是 Copilot 打包提示時依據的輸入預算; 無人設定時, 衍生為上下文長度減最大輸出 token 數。
- `max_output_tokens` 約束回覆, 並在沒有參數設定時兼作線上的 `max_tokens` ([例外](#max_tokens-例外))。

對[負載平衡池](#負載平衡池), 註冊的上限取最嚴格貢獻者的 - 您自己的覆寫仍然勝過合併結果: 您設定的 `max_output_tokens` 即使各部署不一致也算已宣告, 而合併出的伺服器值只有在每個部署都宣告時才算已宣告。

#### 從已移除的預設設定移轉

舊版本有三個全域後備設定: `defaultContextLength`、`defaultMaxOutputTokens` 與 `defaultMaxInputTokens`。它們沒有了; 升級移轉把您設定過的值寫進一個 `"*"` 記錄:

```jsonc
"litellm-vscode-chat.models.capabilities": {
  "*": {
    "_inheritable": true,
    "_fallback": ["context_length", "max_output_tokens"],
    "context_length": 100000,      // 原 defaultContextLength
    "max_output_tokens": 8000,     // 原 defaultMaxOutputTokens
    "max_input_tokens": 90000      // 原 defaultMaxInputTokens - 一般覆寫
  }
}
```

前兩個搭 `_fallback`, 因為舊設定只在伺服器回報之下補缺。記錄還標了 `_inheritable: true`, 因為舊預設值不管您設定了什麼都套用於每個模型: 沒有這個標記, 任何有自己更具體記錄的模型都會整體失去這些預設值; 有了它, 它們跟隨每個不主動退出的模型 - 每個欄位落到哪裡都還是後備, 因為[被繼承欄位保留來源的標記](#後備值-_fallback)。`defaultMaxInputTokens` 從來都高於伺服器的輸入上限, 所以它作為一般覆寫移轉 - 行為不變, 換了新家。完整重新命名表: [設定](settings.md#重新命名與移除的設定)。

## 參數

參數是請求要求的東西: `temperature`、`max_tokens`、`reasoning_effort`, 您的 LiteLLM 部署與模型提供者接受的任何東西。延伸模組從不替您決定它們。

### 直通契約

當您什麼都不設定 - 或沒有設定比對到某模型的東西 - 時, 套用的是您的模型提供者自己的預設值:

- 延伸模組不注入預設 temperature, 沒有允許清單, 什麼都沒有。
- 所有非保留的參數鍵原樣直通; 延伸模組不限制您能設定哪些參數。
- 提供者擁有的欄位無法覆寫: `model`、`messages`、`stream`、`stream_options`, 以及 - 當工具參與時 - `tools` 與 `tool_choice`。
- 以 `_` 開頭的鍵是延伸模組指示詞 ([`_force`](#強制參數-_force)), 從不送出。

### `max_tokens` 例外

延伸模組唯一會自行填入的欄位是 `max_tokens`。當執行階段選項與所有參數記錄都沒有設定它時, 請求攜帶模型解析出的最大輸出 token 數:

- 數字為已宣告時**原樣送出**: 伺服器回報的 (對[池化模型](#負載平衡池), 僅當每個部署都宣告時), 或您在 `models.capabilities` 中設定的 - 覆寫或 `_fallback` 值皆可;
- 數字為猜測時**封頂 4096**: 目錄值 (明確 `_openrouter_model` 指示詞或隱含比對) 或內建預設值。

在[優先順序鏈](#參數優先順序)中的任何地方設定 `max_tokens`, 這個例外就永不啟動: 值按您寫的原樣送出 - 延伸模組從不編輯或箝制使用者設定的參數, 即使它超過模型解析出的 `max_output_tokens` (該能力繼續管轄註冊與輸入預算, 不管請求)。而在[能力](#能力欄位)中設定 `max_output_tokens` 並不繞過這個例外 - 它為例外供值: 後備用您的數字觸發, 它算已宣告, 於是 4096 上限永不套用。

### 參數來自哪裡

四個來源可以為請求設定參數, 從低到高列出:

1. **全域設定** - `litellm-vscode-chat.models.parameters`, 以[比對器](#模型比對)為鍵:

   ```json
   {
     "litellm-vscode-chat.models.parameters": {
       "gpt-5*": { "temperature": 1 },
       "claude-opus": { "max_tokens": 16000, "temperature": 0.5 }
     }
   }
   ```

   適合有硬性要求的模型 (gpt-5 拒絕 1 以外的任何 `temperature`) 或全家預設值 (一個 `"*"` 鍵)。常用參數: `max_tokens`、`temperature`、`top_p`、`frequency_penalty`、`presence_penalty`、`stop`、`response_format`、`reasoning_effort`、`seed`。

2. **項目參數** - 伺服器項目的 `models.parameters`, 語法相同, 逐欄位套用在全域記錄之上; 伺服器專屬值的家 ([伺服器](servers.md#各伺服器模型設定))。只有當請求經過的提供者群組在標籤與基底 URL 兩方面都與項目相符時, 請求才拾取該項目的參數; 沒有項目的外部群組, 以及標籤或 `baseUrl` 編輯留下的過時群組, 只得到全域設定 - 儀表板會在該伺服器列的下方說明 ([疑難排解](troubleshooting.md#各伺服器模型參數未生效))。

3. **選擇器設定** - Copilot 選擇器中的各模型[設定選單](#各模型設定) (目前: 推理程度)。這些選擇算作使用者設定, 像任何設定的參數一樣轉送, 只是只有 schema 宣告的屬性會送出, 對應到它們的線上鍵。

4. **執行階段選項** - 聊天用戶端 (Copilot, 或呼叫該模型的其他延伸模組) 在請求本身上設定的內容。

### 強制參數: `_force`

執行階段選項通常勝出 - 聊天用戶端要求了具體的東西。`_force` 指示詞為選中的欄位反轉這一點, 用於您的值必須永遠勝出的閘道或模型:

```jsonc
"litellm-vscode-chat.models.parameters": {
  "gpt-5*": {
    "_force": ["temperature"],   // 或 true, 強制記錄中的每個欄位
    "temperature": 1,            // 連 Copilot 的執行階段選項都贏
    "top_p": 0.9                 // 未列出: 一般欄位, 執行階段選項仍勝出
  }
}
```

- `_force: true` 強制記錄中的每個欄位; `_force: ["field", ...]` 只強制列出的。
- 與 [`_fallback`](#後備值-_fallback) 一樣, 標記在來源側: 被強制的欄位無論被[繼承](#哪筆記錄生效)帶到哪裡都保持強制, 記錄自己的 `_force` 清單只能指名自己的欄位 - 要強制繼承來的欄位, 在其來源處標記 (或在本地重申並強制)。
- 提供者擁有的欄位既不能設定也不能強制: 指名它們的 `_force` 會在儀表板中回報, 該鍵被忽略。
- `max_tokens` 不屬於提供者擁有的欄位, *可以*被強制: 被強制的值勝過執行階段選項, 而且作為使用者設定的值, 永遠不會被 [`max_tokens` 例外](#max_tokens-例外)封頂。
- 項目記錄的強制欄位勝過全域記錄的強制欄位。

### 參數優先順序

當多個來源為同一請求設定同一參數時, 較高者勝出。在每個記錄層內, 由[比對規則](#哪筆記錄生效)在相符的鍵之間挑選:

1. 強制欄位 ([`_force`](#強制參數-_force)) - 項目在全域之上
2. 執行階段選項 - 聊天用戶端自己的請求設定
3. 選擇器設定 - 各模型[設定選單](#各模型設定)
4. 項目 `models.parameters`
5. 全域 `models.parameters`

五層都未設定的參數落到您的模型提供者的預設值, 外加上文的 [`max_tokens` 例外](#max_tokens-例外)。要查看這些層為某個模型如何解析, 用[檢查器](#檢查器)。

## 選擇器

每個伺服器項目在 Copilot 的模型選擇器中成為一個提供者群組, 以其標籤命名, 伺服器的模型列在其下。項目顯示伺服器宣告的提供者名稱 (模型資訊的 `litellm_provider`, 或提供者路由的名稱), 未宣告時退回 `litellm`; `(cheapest)` 與 `(fastest)` [彙總項目](#提供者路由與彙總項目)始終顯示 `litellm`。[儀表板的模型清單](dashboard.md#模型)顯示同樣的資料與精確的 ID。

### 各模型設定

有些模型在選擇器中提供「設定」選單 - 這就是[參數優先順序](#參數優先順序)中的「選擇器設定」層。目前它帶有一個控制項, Thinking Effort, 出現在宣告推理支援的模型上:

1. 在選擇器中選中該模型。
2. 按一下聊天輸入框中模型名稱旁的 "Thinking Effort" 標籤。
3. 選一檔; VS Code 會為該模型記住這個選擇。

每檔送出什麼:

- 之後每個請求都相應攜帶 `reasoning_effort`; 「關閉」以 `reasoning_effort: "none"` 送出, 在支援該值的模型上關閉思考。
- 「提供者預設」(初始狀態) 不送出任何東西, 由您的提供者決定。

選單的檔位像任何能力欄位一樣按模型解析 ([優先順序](#能力優先順序)), 來源從高到低:

1. 您的 [`models.capabilities` 記錄](#能力)中的 `reasoning_effort_levels` 清單 (項目優先於全域)。任何字串都可以 - 詞彙表是開放的, 選中的檔位按原樣送出。您自己寫下的空清單會把選單清空到只剩「提供者預設」。
2. 伺服器模型資訊中的 `supports_<level>_reasoning_effort` 旗標, 當 LiteLLM 宣告了它們時 (對[負載平衡池](#負載平衡池), 取每個部署都標記的檔位; 互不相交的旗標視為未回報)。
3. 您的記錄中帶 `_fallback` 標記的清單, 在伺服器未回報時填充。
4. 內建清單: 關閉、最小、低、中、高、極高、最大。

```json
"litellm-vscode-chat.models.capabilities": {
  "grok-*": { "reasoning_effort_levels": ["low", "high", "max"] }
}
```

如果選中的檔位對該模型仍然不對 (比如在提供者最高只到 High 時選「最大」), 請求會帶著伺服器自己的錯誤訊息失敗; 換一檔重試即可。該清單只決定選單本身: 控制項是否存在仍由上面的 `supports_reasoning` 與 `supported_openai_params` 決定。強度檔位之外的推理參數 (`thinking` 區塊、`reasoning` 物件、預算) 不屬於選單, 仍走 [`models.parameters` 直通](#參數)。

temperature 刻意留在 `models.parameters` 中自由設定: 設定選單只能呈現固定選項, 所以延伸模組不在那裡加 temperature 預設檔。

### 選擇器中的價格

- 生效的每 token 成本 - 伺服器的回報加上您的覆寫 ([定價](#定價)) - 會換算成模型選擇器與[儀表板](dashboard.md)模型清單顯示的每百萬 token 數字, 連同已宣告的快取與長上下文分層成本。
- *伺服器回報的*恰好為零的成本對被視為未宣告而非免費, 因為 LiteLLM 會給沒有價格資料的模型打上零。您自己寫下的零對顯示為免費 - $0 in / $0 out, 外加 cheapest 徽章。
- cheapest/fastest 彙總項目不帶*伺服器*價格 - 在那裡, 請求實際花多少由代理的路由決定 - 不過比對到彙總項目[帶後綴 ID](#提供者路由與彙總項目) 的使用者成本記錄仍會為它定價。

請求實際花了多少錢, 按伺服器與相對預算, 在[用量](usage.md#用量面板)。

## 多模態輸入

附件在線上變成什麼, 取決於它的類型與模型解析出的[能力](#能力):

| 附件 | 能力門檻 | 在其他模型上 |
|------------|-----------------|-----------------|
| 影像 (附件, 以及從先前回合重播的影像) | 只送給宣告視覺支援的模型 | 文字照常通過, 影像被捨棄, 「LiteLLM」輸出通道記一條說明 |
| PDF (作為使用者訊息上的檔案區塊送出) | 不設能力門檻 (`supports_pdf_input` 會解析並顯示, 但目前不門控任何行為) | 接受不了 PDF 的模型帶著其伺服器自己的錯誤訊息失敗 |
| 音訊 (WAV、MP3; 作為音訊輸入區塊送出) | 只送給宣告音訊輸入支援的模型 | 捨棄並在輸出通道記說明 |
| 可解碼為文字的檔案 (純文字、JSON、原始碼檔案) | 無: 解碼後作為文字送往任何模型 | - |

工具結果轉送文字, 在視覺模型上外加影像。助理歷史中的二進位內容沒有線上形態; 重播時只有其文字存活。

## 思考、來源、生成媒體與 token 用量

除了純文字, 回覆中 (或關於回覆) 還可能回來四樣東西:

- **思考。**串流推理內容的模型 (thinking 區塊、`reasoning_content` 差量) 會在 Copilot 的思考 UI 中隨到隨顯 - 在提供 thinking-part API 的 VS Code 組建上。在沒有它的組建上, 推理被捨棄並在輸出通道記說明, 只含推理的回覆會以一則要求更新 VS Code 的錯誤失敗; 見[疑難排解](troubleshooting.md#常見問題)。
- **來源。**LiteLLM 路由回傳引用或搜尋結果的模型 (啟用網頁搜尋的路由) 會在回覆結尾得到一份按 URL 去重的來源清單。
- **生成媒體。**在聊天中生成媒體的模型把它串流送回回覆: 生成的影像隨到隨呈現, 生成的音訊按每段話一個剪輯到達, 其轉錄文字作為一般文字串流顯示。延伸模組解碼不了、或 VS Code 組建顯示不了的媒體, 捨棄並在輸出通道記說明。
- **Token 用量。**每個請求都向伺服器索取 token 用量, 回傳的計數 (提示、補全、總數, 以及伺服器回報時的快取與推理 token 明細) 傳給 Copilot 用於其用量顯示。只從回應中取出這些已知的數字計數; 原始用量記錄從不被整體轉送或記錄。伺服器端的支出與預算是另一個功能: [用量](usage.md#用量面板)。

## 檢查器

本頁的每條規則都可觀察。[儀表板](dashboard.md)的模型清單給每個模型一個「檢查」動作, 開啟一個帶兩個來源區段的面板:

- **參數** ([有效參數](dashboard.md#有效參數)): 將要送出的每個參數、解析出的值, 以及設定它的來源 - 哪筆記錄、哪個比對鍵 - 被遮蔽的值顯示在勝出者下方, 外加請求將攜帶的 `max_tokens` 及其原因。
- **能力** ([有效能力](dashboard.md#有效能力)): 每個能力欄位及其解析值與來源 - 項目或全域記錄鍵、`_openrouter_model` 衍生、伺服器的回報、`_fallback` 補缺、目錄比對, 或內建預設值 - 同樣在下方顯示被遮蔽的值。

檢查器還會呈現本頁點名的診斷: 無效的比對鍵、無效值、未知的目錄 ID, 以及作用在不可強制鍵上的 `_force` - 外加針對延伸模組不認識的能力欄位的建議性說明, 它只在有真實的 `/model/info` 證據時顯示, 並且從不阻止該值生效 ([能力欄位](#能力欄位))。當比對器做出出人意料的事時, 從這裡開始 - 答案離您只有一次「檢查」點擊的距離。
