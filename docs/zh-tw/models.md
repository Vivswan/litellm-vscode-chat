# 模型與功能

[English](../models.md) | [简体中文](../zh-cn/models.md) | 繁體中文

延伸模組讀取每個伺服器的模型資訊, 並把讀到的內容註冊給 Copilot Chat: 模型的 token 上限、價格與功能旗標全都來自那裡。功能決定模型被提供來做什麼 (工具、圖片、推理); 它們永遠不改變延伸模組要求模型做什麼, 那是[模型參數](model-parameters.md)的職責。

## 註冊哪些模型

探索會讀取伺服器的 `/v1/model/info` 端點, 在該呼叫失敗、未回傳資料陣列, 或回傳的項目全都不可用時, 退回較簡單的 `/v1/models` 清單 (格式正確的空清單會註冊零個模型, 不會觸發退回)。

可連線伺服器回報的每個聊天模型都會出現在選擇器中。有三種排除:

- `model_info.mode` 指名非聊天端點 (`embedding`、`image_generation`、`audio_speech`、`audio_transcription`、`rerank`、`moderation`) 的模型是刻意排除的, 因為對它們發出聊天請求只會失敗。未宣告 mode 的模型一律註冊。
- Proxy 已暫停的部署 (`model_info.blocked`) 會被略過。
- 其他一概不過濾: 完全沒有功能資料的模型仍會註冊, 並使用[設定](settings.md#token-上限)中的後備 token 上限。

當同一個模型名稱由多個部署提供 (負載平衡集區) 時, 它只註冊一次, 並採用最嚴格貢獻者的 token 上限, 這樣不論由哪個部署服務, 請求都不會超限。

### 提供者路由與彙總項目

回報時背後帶有 `providers` 路由陣列的模型會以不同方式註冊。兩個端點都可能帶有這種項目; 一般的 LiteLLM Proxy 通常沒有, 而對同一模型名稱的多個部署做負載平衡的 Proxy 也不會產生它 (那些部署會合併成上述的單一項目)。

- 只要至少一條路由支援工具 (一條就夠), 每條支援工具的路由都會註冊自己的選擇器項目 (名為 `via <provider>`), 外加讓 LiteLLM 逐請求挑選路由的 `(cheapest)` 與 `(fastest)` 彙總項目; 這種情況下不註冊無後綴的基礎項目。
- 當沒有任何路由支援工具時, 改註冊單一基礎項目, 不帶彙總項目。
- 彙總項目宣告的是支援工具的路由中最嚴格者的 token 上限。

選擇器與儀表板的「系列」欄來自同一份資料: 各項目顯示伺服器宣告的提供者名稱 (模型資訊的 `litellm_provider`, 或提供者路由的名稱), 未宣告時退回 `litellm`; `(cheapest)` 與 `(fastest)` 彙總項目一律顯示 `litellm`。

## 功能

| 功能 | 從模型資訊讀取 | 控制什麼 |
|------------|----------------------|------------------|
| 工具呼叫 | `supports_function_calling` (或 `supports_tool_choice`); 提供者路由帶 `supports_tools` | Copilot 能否送出使用工具的請求 (代理程式模式); 未宣告時開啟, 只有明確的 `false` 才關閉 |
| 視覺 | `supports_vision` | 是否傳送圖片附件 (見下文) |
| 音訊輸入 | `supports_audio_input` | 是否傳送音訊附件 |
| 推理 | `supports_reasoning`, 或 `supported_openai_params` 中有 `reasoning_effort` (明確的 `supports_reasoning: false` 優先) | 選擇器中的「Thinking Effort」控制項; 參閱[模型參數](model-parameters.md#模型選擇器中的推理程度) |
| 提示快取 | `supports_prompt_caching` | 是否放置快取中斷點; 參閱[設定](settings.md#提示快取) |

伺服器端的錯誤旗標值得在那一側修正: 延伸模組雙向信任宣告, 提供已宣告的, 未宣告的則不提供。

## 多模態輸入

附件在線路上變成什麼, 取決於其類型與模型宣告的功能:

| 附件 | 功能閘控 | 在其他模型上 |
|------------|-----------------|-----------------|
| 圖片 (附件, 以及先前回合重播的圖片) | 只傳給宣告視覺支援的模型 | 文字照常送出, 圖片被捨棄, 並在「LiteLLM」輸出通道留下說明 |
| PDF (以檔案區塊附在使用者訊息上) | 不做功能閘控 | 無法接受 PDF 的模型會以其伺服器自己的錯誤訊息失敗 |
| 音訊 (WAV、MP3; 以音訊輸入區塊傳送) | 只傳給宣告音訊輸入支援的模型 | 捨棄並在輸出通道留下說明 |
| 可解碼為文字的檔案 (純文字、JSON、原始碼) | 無: 一律解碼後以文字傳送 | - |

工具結果會轉送文字, 在視覺模型上再加上圖片。助理歷史中的二進位內容沒有線路格式; 重播時只有文字存留。

## 思考、來源、生成媒體與 token 用量

除了純文字, 回覆中 (或關於回覆) 還可能回來四種東西:

- **思考。** 串流推理內容的模型 (thinking 區塊、`reasoning_content` 差量) 會在支援 thinking-part API 的 VS Code 版本上, 即時顯示在 Copilot 的思考 UI 中。在沒有該 API 的版本上, 推理會被捨棄並在輸出通道留下說明, 而只包含推理的回覆會以要求您更新 VS Code 的錯誤失敗; 參閱[疑難排解](troubleshooting.md#常見問題)。
- **來源。** LiteLLM 路由回傳引文或搜尋結果的模型 (啟用網頁搜尋的路由), 會在回覆結尾得到依 URL 去重的來源清單。
- **生成媒體。** 在聊天中生成媒體的模型會把它串流回覆中: 生成的圖片隨到隨顯示, 生成的音訊以每段語句一個剪輯送達, 其逐字稿以一般文字串流。延伸模組無法解碼, 或 VS Code 版本無法顯示的媒體, 會被捨棄並在輸出通道留下說明。
- **Token 用量。** 每個請求都會向伺服器要求 token 用量, 回傳的計數 (提示、完成、總計, 加上伺服器有回報時的快取與推理 token 明細) 會交給 Copilot 的用量顯示。只從回應中取用這些已知的數字計數; 原始用量記錄絕不整批轉送或記入記錄。

## 選擇器中的價格

- 模型資訊中的每 token 成本會換算成模型選擇器與[儀表板](dashboard.md)模型表格顯示的每百萬 token 數字, 連同有宣告時的快取與長上下文級距成本。
- 成本對恰好為零時視為未宣告而非免費, 因為 LiteLLM 會在沒有價格資料的模型上蓋上零。
- cheapest/fastest 彙總項目完全不帶價格: 在那裡, 請求實際花費多少由 Proxy 的路由決定。
