# 用量與預算

[English](../usage.md) | [简体中文](../zh-cn/usage.md) | 繁體中文

當 LiteLLM 伺服器追蹤支出時, 延伸模組會把它呈現出來: 您的金鑰相對其預算花了多少、預算用完前的警示、一個平時不礙事但關鍵時刻會出現的狀態列項目, 以及一個展示全貌的儀表板面板。這裡的一切都是唯讀的 - 延伸模組從您的伺服器讀取支出資料, 從不變更預算、金鑰或伺服器端的任何東西。支出資料也從不寫入延伸模組的記錄或 bug 回報; 它只存在於您與您的伺服器之間。

四個設定驅動全部, 每個都在下文的情境中詳述:

| 設定 | 預設值 | 一句話 |
|---|---|---|
| [`usage.pollInterval`](settings.md#參考) | `300000` 毫秒 | 背景多久擷取一次支出; `0` = 關閉 ([輪詢](#輪詢)) |
| [`usage.alertThresholds`](settings.md#參考) | `[0.8, 0.95]` | 觸發通知的預算比例 ([警示](#警示)) |
| [`usage.statusBar`](settings.md#參考) | `"always"` | `always` / `alerts-only` / `off` ([狀態列](#狀態列)) |
| 項目的 [`budget`](servers.md#項目參考) | 未設定 | 按伺服器的手動預算 (美元) ([預算](#預算)) |

## 需求

用量功能需要帶資料庫執行的 LiteLLM 伺服器 - 支出追蹤與[虛擬金鑰](https://docs.litellm.ai/docs/proxy/virtual_keys)的標準配置。延伸模組最多讀取三個端點, 始終只查詢自己的金鑰 (伺服器項目用來驗證的那把), 以及在金鑰歸屬於某使用者時該使用者自己的彙總 - 從不列舉其他金鑰或使用者:

| 端點 | 延伸模組讀取什麼 |
|---|---|
| `/key/info` | 呼叫金鑰的支出、`max_budget` 與 `budget_reset_at` |
| `/user/daily/activity` | 最近 30 天的請求數、成功率與快取讀取 token 計數 |
| `/user/info` | 所屬使用者的支出、`max_budget` 與 `budget_reset_at` - 僅當 `/key/info` 回報金鑰歸屬於某使用者時才讀取 |

在沒有資料庫的伺服器上, 這些端點不存在。延伸模組偵測一次後就為該伺服器靜默隱藏所有用量介面: 沒有儀表板區段、沒有狀態列項目、沒有警示、沒有錯誤噪音、沒有需要設定的東西。可用性按伺服器判斷, 所以混合的伺服器群也沒問題 - 用量恰好出現在資料存在的地方。

這個偵測結果會一直沿用: 背景輪詢不會重新檢查已判定缺少的端點。之後補上資料庫時, 執行 "LiteLLM: Refresh Usage Now" - 或編輯該伺服器的項目 - 延伸模組就會重新探測可用性。

金鑰也能在有資料庫支撐的伺服器上以同樣方式隱藏用量: 當伺服器在 `/key/info` 與 `/user/daily/activity` 上都拒絕該金鑰時 (401 或 403 - 無權讀取用量資料的金鑰), 延伸模組把這當作同樣永久的狀態, 隱藏同樣的介面。下面的 curl 測試能區分兩者: 缺資料庫回答的是路由錯誤, 受限金鑰回答的是 401 或 403 - 此時的修法是一把允許讀取自己用量的金鑰, 而不是資料庫。

要檢查伺服器支援什麼, 問它延伸模組問的同一個問題:

```bash
curl -s -H "Authorization: Bearer $YOUR_LITELLM_KEY" https://litellm.example.com/key/info
```

有資料庫支撐的伺服器回答帶 `spend` 與 `max_budget` 欄位的 JSON; 沒有資料庫的伺服器回答錯誤, 因為沒有資料庫時該路由不提供。如果 curl 成功但延伸模組什麼都不顯示, 檢查項目的金鑰是不是您測試用的那把 - 資料是按金鑰的。而且那是金鑰在伺服器端的總數: 透過那把金鑰消費的每個用戶端都計入其中, 不只是 VS Code。

可用性除了按伺服器, 還按端點: 一個伺服器 (或您的金鑰在它上面) 可能回答 `/key/info` 但不回答 `/user/daily/activity`。此時[用量面板](#用量面板)顯示支出與預算, 但沒有請求統計 - 這在某些配置上是正常形態, 不是錯誤。

## 預算

預算可以來自兩個地方:

- **金鑰回報**: LiteLLM 存放在金鑰本身上的 `max_budget`, 建立金鑰時在伺服器端設定。`/key/info` 連同目前支出一起回報它。
- **項目的 `budget` 欄位**: [伺服器項目](servers.md#項目參考)上的手動數字 (美元, 大於 0):

```jsonc
"litellm-vscode-chat.servers": [
  {
    "label": "prod",
    "baseUrl": "https://litellm.example.com",
    "auth": { "apiKey": "sk-..." },
    "budget": 50
  }
]
```

兩者都存在時, 項目的值是**有效預算**: 百分比與[警示](#警示)都相對它計算, 而每個顯示預算的介面都會兩者並列 (`預算 $50 - 金鑰回報 $100`), 伺服器端的上限永不從視野中消失。項目欄位為兩種情況而存在: 伺服器沒有給 `max_budget` 的金鑰, 以及設在伺服器硬上限之下的個人警戒線。

有支出資料但兩個來源都沒有預算的伺服器, 顯示支出而不顯示百分比, 也永不警示 - 沒有可計算比例的東西。

預算旁顯示的重設日期是金鑰的 `budget_reset_at`: LiteLLM 將在何時為下一週期把支出歸零。重設後, 支出回落, 已觸發的[警示](#警示)自行重新武裝。回落在下一次擷取時才可見 - 背景輪詢、開啟儀表板, 或 "LiteLLM: Refresh Usage Now" - 而不是重設瞬間; 沒有重設排程的金鑰就不顯示重設日期。

值得知道的邊界情況:

- **項目的 `budget` 需要支出資料來衡量。**在不提供用量資料的伺服器上它不改變任何事 - 用量介面照樣隱藏。
- **高於金鑰上限的項目 `budget` 會讓警示失效。**項目的值無條件勝出, 所以在上限 $100 的金鑰上把 `budget` 設為 $200, 每個百分比都相對 $200 計算 - 伺服器在 $100 就切斷金鑰, 第一條警告還來不及觸發。延伸模組無法調高伺服器端的 `max_budget`: 想在上限之前被提醒, 請把項目的值保持在上限或其之下, 或乾脆不設, 讓金鑰自己的數字驅動。
- **支出可以越過預算。**延伸模組是唯讀的, 從不攔截請求; 金鑰越過 `max_budget` 後伺服器是否繼續服務, 是 LiteLLM 的政策, 不是延伸模組的。每個門檻都不超過 1, 所以越過預算的支出位於最高門檻之上: 錯誤背景, 所有警示都已觸發。
- **資料跟著金鑰走, 不跟項目。**輪換項目的認證會把它的數字切到新金鑰的支出與預算。用同一把金鑰驗證的兩個項目各自顯示那把金鑰的支出 - 由於[狀態列](#狀態列)取最大值而非總和, 共享的支出不會在那裡被重複計算。

## 輪詢

`usage.pollInterval` (毫秒, 預設 `300000` - 5 分鐘) 驅動一個背景輪詢器, 讓警示與狀態列在儀表板關閉時也運作。負值箝制為 `0`; 低於 `30000` (30 秒) 的非零值向上箝制到它, 所以最快的節奏是每個伺服器每 30 秒擷取一次。

`0` 完全關閉背景輪詢:

- 不發出背景請求, 不觸發警示。
- 儀表板每次開啟時仍會擷取新資料。
- "LiteLLM: Refresh Usage Now" 仍會在您執行它時立即擷取。

**新鮮度。**伺服器的用量資料在最近一次擷取成功且距今不足兩個輪詢間隔時算*新鮮*; 輪詢關閉時, 隨選擷取的資料保鮮十分鐘 (預設間隔的兩倍), 而 "LiteLLM: Refresh Usage Now" 總是產生新鮮資料。資料一旦過時 - 伺服器不再回應, 或窗口期用完 - 延伸模組在[用量面板](#用量面板)繼續顯示最後已知的值, 標註其存在時間 (「上次更新於 25 分鐘前」), 但[狀態列](#狀態列)會把該伺服器從彙總中剔除, 而不是把舊數字當成目前值展示。

同一規則涵蓋離線或睡眠過的機器: 睡眠期間沒有輪詢, 所以醒來時超過兩個間隔的資料都算過時 - 面板帶著存在時間繼續顯示, 狀態列項目則保持隱藏, 直到下一次成功擷取取代它。

- 回報 `max_budget: 0` 的金鑰算作沒有預算 (LiteLLM 的「零即無上限」慣例); 伺服器項目的 `budget` 必須是正數 - 零或負值作為設定診斷回報並忽略。

## 警示

`usage.alertThresholds` 是有效預算的比例清單, 每個大於 0 且不超過 1; 達到門檻就算越過 (在 80.0% 時 0.8 的警示觸發, `[1.0]` 門檻在支出等於預算時觸發)。超出範圍的值被捨棄並作為設定診斷回報。預設的 `[0.8, 0.95]` 在 80% 警告一次, 95% 再警告一次。清單會替您去重與排序; 空清單關閉警示。

- 越過門檻時, 每個伺服器每個門檻只顯示**一則**通知 - 每五分鐘輪詢一次不等於每五分鐘跳一次通知。當一次輪詢一舉越過多個門檻時, 只有最高的觸發。所有預算通知使用同一嚴重性層級; 逐級升色的故事在[狀態列](#狀態列)。
- 已觸發的門檻在支出回落到其下方時重新武裝: 新的計費週期、調高的預算, 警示就再次待命。
- 警示在每次擷取時評估 - 背景輪詢與手動重新整理一視同仁; 揭示出越線的 "LiteLLM: Refresh Usage Now" 會立即跳出通知。每伺服器每門檻一次的規則依然適用。

在 $50 有效預算與預設值下, 您會在 $40 與 $47.50 收到延伸模組的訊息 - 然後直到預算重設前不再打擾。

較短的清單運作方式相同, 只在[狀態列](#狀態列)上有一處細節: 那裡的嚴重程度以*設定的最高*門檻為頂, 所以像 `[0.5]` 這樣只有一項的清單, 那一個門檻就是警報器 - 越過它直接進入錯誤背景。另一端, `[1.0]` 讓延伸模組在預算幾乎用完之前保持沉默。

## 狀態列

`usage.statusBar` 控制一個刻意精簡的狀態列項目, 坐在 [LiteLLM 連線項目](dashboard.md#狀態列項目)旁邊:

| 值 | 行為 |
|---|---|
| `"always"` (預設) | 只要有東西可顯示就可見 |
| `"alerts-only"` | 門檻觸發前隱藏, 觸發期間可見 |
| `"off"` | 從不顯示 |

該項目的文字只有一樣東西: **最差新鮮伺服器**的支出百分比 - 在有[新鮮資料](#輪詢)且有預算的伺服器中, 支出對有效預算比率最高的那個。其餘一切都在工具提示裡。

| 情況 | 該項目顯示 |
|---|---|
| 每個新鮮伺服器都在門檻之下 (`"always"`) | 最差百分比, 一般樣式 - 例如 `42%` |
| 任何新鮮伺服器越過最低門檻 | 警告背景上的百分比 |
| 任何新鮮伺服器越過最高門檻 | 錯誤背景上的百分比 |
| `"alerts-only"`, 沒有越過門檻的 | 什麼都不顯示 |
| 沒有伺服器有預算, 或 `"off"` | 什麼都不顯示 |
| 完全沒有新鮮資料 | 什麼都不顯示 |

使用自訂門檻清單時, 嚴重程度刻度以設定的最高門檻為頂: 越過最高的得到錯誤背景, 越過任何較低的得到警告背景 - 所以單門檻清單被越過時直接進入錯誤背景; 它就是警報器。

超過 100% 時, 該項目顯示字面數字 (`112%`) - 面板的進度列只是填滿, 真實百分比在其標籤上。

最後一列是新鮮度規則在履行職責: 該項目從不把過時數字當成目前值顯示。過時的伺服器被排除在彙總之外並在工具提示中註明; 當*沒有*伺服器有新鮮資料時, 該項目整個隱藏 - 連線項目已經在講故障的故事, 第二個紅色的東西不會增加任何資訊。

工具提示帶有完整的按伺服器明細: 支出、兩個預算、百分比、重設日期、還有多少*其他*伺服器越過門檻, 以及資料上次更新時間。按一下該項目開啟[用量面板](#用量面板)。

上述規則隱含的邊界情況, 明說出來:

- **數字可能在兩次更新之間跳動。**最差伺服器在每次輪詢時重算, 所以百分比可能切到*另一個*伺服器的比率, 而不只是沿一個伺服器的支出上下移動; 工具提示的明細顯示目前數字背後是哪個伺服器。
- **百分比從不相加。**該項目是跨伺服器的最大值: 兩個各花一半的預算顯示為兩者中較大者, 而不是 100%。
- **`"alerts-only"` 同樣遵循新鮮度。**當唯一越線伺服器的資料過時時, 該項目隱藏, 儘管預算多半仍然是花掉的狀態 - 等新鮮資料確認了狀態它才回來, 無論確認成哪邊。面板期間繼續顯示最後已知的值。
- **`"off"` 只隱藏該項目, 其他什麼都不動。**警示照常觸發, 用量面板照常運作; 該設定只控制一個狀態列項目。

## 用量面板

儀表板的[用量區段](dashboard.md#用量區段)是全貌所在。對每個有用量資料的伺服器:

- 一條**支出對預算進度列**與百分比, 相對有效預算; 兩者不同時, 金鑰回報的預算顯示在旁。
- **重設日期** (`budget_reset_at`)。
- **最近 30 天 (UTC 日曆日, 含今天) 的請求數、成功率與快取命中率**, 當伺服器提供 `/user/daily/activity` 時; 沒有它的伺服器只顯示支出與預算。
- 一個**立即重新整理**按鈕: 立即擷取, 擷取進行中自我停用, 並顯示資料上次更新時間。

開啟儀表板會擷取新資料, 即使[輪詢](#輪詢)已關閉。當伺服器的資料過時時, 它最後已知的值留在畫面上, 標註「上次更新於 X 前」- 您仍能讀到的歷史, 清楚地標成歷史。

## 命令

| 命令 | 作用 |
|---|---|
| LiteLLM: Refresh Usage Now | 立即擷取每個伺服器的支出資料, 不受 `usage.pollInterval` 約束, 並重新檢查每個伺服器的用量可用性 |
| LiteLLM: Open Dashboard | 開啟儀表板; 用量區段一步之遙 (或經狀態列項目直達) |
