# 疑難排解

[English](../troubleshooting.md) | [简体中文](../zh-cn/troubleshooting.md) | 繁體中文

本頁按症狀索引: 找到您正在看到的現象, 每個條目會說它代表什麼、如何修復, 以及完整故事在哪裡。延伸模組把狀態放在您看得到的地方 - 連線一個狀態列項目、用量一個、細節在儀表板的診斷區段、完整記錄在輸出通道 - 下文沒有相符項時就從那裡開始。

## 狀態列

兩個項目坐在右下角。左邊是**連線項目** - 它回答「我現在能聊天嗎?」:

| 項目 | 狀態 | 意義 |
|------|--------|---------|
| `$(warning) LiteLLM` | 未設定 | 沒有設定伺服器 - 按一下進行設定 |
| `$(loading~spin) LiteLLM` | 載入中 | 正在從伺服器擷取模型 |
| `$(check) LiteLLM` | 已連線 | 所有伺服器可連線; 工具提示帶有模型數量 |
| `$(warning) LiteLLM` | 已降級 | 部分伺服器發生故障 (無法連線或同步失敗); 工具提示說明仍有多少可用模型 |
| `$(error) LiteLLM` | 錯誤 | 所有伺服器都失敗了 - 診斷區段有每個伺服器的錯誤 |

按一下它開啟[儀表板](dashboard.md); 診斷區段有各伺服器的細節。

它旁邊的**用量項目**回答「我離預算還有多近?」- 最差伺服器的支出百分比:

| 它顯示 | 意義 |
|----------|---------|
| 一般百分比, 例如 `42%` | 每個伺服器都在其警示門檻之下 |
| 警告背景上的百分比 | 某伺服器越過了最低門檻 (預設 80%) |
| 錯誤背景上的百分比 | 某伺服器越過了最高門檻 (預設 95%) |
| 什麼都不顯示 | 沒有新鮮的預算資料 (故障由連線項目負責提示)、用量功能不適用於您的伺服器, 或 `usage.statusBar` 隱藏了它 |

按一下它開啟儀表板的[伺服器頁](dashboard.md#伺服器頁上的用量), 每列都帶著自己的支出。預算、門檻與輪詢如何配合, 在[用量](usage.md#狀態列)頁面。(只設定了一個門檻時, 它既是最低也是最高, 所以越過它直接進入錯誤背景。)

所以: **左邊紅**代表請求過不去 - 按下面的[常見問題](#常見問題)排查。**右邊紅**代表請求暢通但預算快花完了 - 見[用量: 警示](usage.md#警示)。

## 常見問題

### 「聊天介面或 "Manage Models..." 不見了」

本延伸模組接入的是 GitHub Copilot Chat; 沒有它就沒有聊天檢視, 也沒有模型選擇器。

- 安裝 GitHub Copilot Chat 延伸模組, 登入 GitHub, 並確保它已啟用。
- VS Code 較舊時請更新: 延伸模組需要 1.129.0 或更高版本。
- 在處於受限模式的視窗中 (不受信任的資料夾), VS Code 會整個停用本延伸模組: LiteLLM 命令、狀態列項目和已註冊的模型全部消失, 直到您信任該工作區。

### 「連線錯誤: 無法連線」

基底 URL 上沒有任何東西回應。

- 確認基底 URL 正確 (例如 `http://localhost:4000`), 且您的 LiteLLM 代理正在執行。
- `.localhost` 下的主機 (如 `http://www.localhost:8001`) 通常無法解析, 請改用純 `localhost` (`http://localhost:8001`); 錯誤訊息會給出修正後的 URL。
- 以 `/v1` 結尾的 URL 沒有問題: 只有當 URL 尚未以 `/v1` 或 `/v2` 這樣的版本區段結尾時, 延伸模組才會附加 `/v1`; 每伺服器的 `apiVersion` 欄位可覆寫兩者 (空字串 = 什麼都不附加)。
- 檢查 VS Code 與伺服器之間的防火牆、VPN 或 Proxy 設定。

[項目參考](servers.md#項目參考)記載了基底 URL 規則。

### 「SSL 憑證錯誤」

VS Code 無法與基底 URL 建立可信任的 HTTPS 連線; 延伸模組沒有繞過憑證驗證的設定。

- 「... 的 SSL 憑證已過期」: 請您的 LiteLLM 伺服器管理員更新憑證。
- 其他任何憑證問題會顯示「無法驗證伺服器的 SSL 憑證, 連線已被封鎖」, 下方的詳細資訊行 (`SSL certificate error for ...`) 點名伺服器和 TLS 失敗 - 自我簽署或內部 CA 憑證, 在企業部署上很常見: 把 CA 加入作業系統的信任存放區, 或用指向 CA 憑證包的 `NODE_EXTRA_CA_CERTS` 啟動 VS Code。信任決定屬於 VS Code 的執行階段, 不屬於本延伸模組。

### 「驗證失敗」

兩種 401 訊息點名的是不同的認證:

- 單純的**「驗證失敗: 您的 LiteLLM 伺服器需要 API 金鑰」**代表代理拒絕了延伸模組的認證。編輯該伺服器 (儀表板, 或 `servers` 設定) 並更新它; 對照您的 LiteLLM 代理設定確認金鑰。修正後的金鑰在下一次同步或模型重新整理時生效 - 執行 "LiteLLM: Sync Models Now" 可立即套用。對於沒有項目的[外部群組](servers.md#外部伺服器與採用), 認證歸 VS Code 所有 - 透過模型選擇器的 "Manage LiteLLM Provider" 流程更新它, 或採用該群組。
- **「上游驗證失敗」**代表代理接受了您的金鑰, 但無法向模型的上游提供者驗證; 更新延伸模組的金鑰幫不上忙。請在 LiteLLM 伺服器上修復那個提供者的認證, 或請伺服器營運者處理。

兩個設定錯誤看起來像驗證失敗:

- `auth` 物件帶有含糊不清形態的項目 (比如 `apiKey` 與 `oauth` 並排) 按設定錯誤處理, 儀表板的伺服器列會指出; 不會在認證之間亂猜。恰好保留一種形式 - 真正同時檢查兩份認證的閘道, 需要的是級別較低的附隨認證 (`auth.oauth` 內部, 或 `auth.apiKey` 旁邊的 `virtualKey`)。見[伺服器: 身分驗證](servers.md#身分驗證)。
- 期望金鑰出現在自訂標頭中的閘道 (例如 `x-litellm-api-key`) 會拒絕標準 bearer 形式; 用 `auth.virtualKey` 配上它想要的標頭名稱。

### 「伺服器無法識別此請求」/「回應了 404 - 它有回應, 但不提供 LiteLLM API」

那個位址上有東西回應, 但不是 LiteLLM 代理 - 或者沒有這個模型。聊天請求上的錯誤顯示上面的標題, 下方的詳細資訊行 (`詳細資訊: LiteLLM 404 ...`) 引用伺服器的回應。

- 檢查那裡實際在聆聽什麼 - 一個網頁伺服器、別的服務, 或錯誤的連接埠 (LiteLLM 代理預設是 4000)。
- 以 `/v1` 或 `/v2` 這樣的版本區段結尾的基底 URL 按原樣使用; 否則延伸模組會附加 `/v1`。因此 404 代表位址在別的方面不對: 路徑前置詞不同、連接埠錯誤, 或伺服器根本不提供 LiteLLM API。每伺服器的 `apiVersion` 欄位可強制指定版本區段 (空字串 = 什麼都不附加)。
- 先前正常的伺服器在聊天請求上回傳 404, 通常代表該模型已從代理移除: 執行 "LiteLLM: Sync Models Now" 重新整理模型清單。如果每個請求都以 404 失敗, 按上文檢查基底 URL。

### 指向 Ollama、vLLM 或一般 OpenAI 相容伺服器

本延伸模組為 LiteLLM 代理而建, 所以探索會先請求 LiteLLM 的 `/v1/model/info` (能力、定價), 再回退到一般 OpenAI 的 `/v1/models` 清單。只提供其中一部分介面的伺服器也能正常運作 - 只需把缺少的端點宣告出來, 讓該失敗不再算作問題。被宣告的端點每次同步仍會探測一次 (懸置的端點會等滿一次 `discovery.timeout`), 所以如果同步太慢, 也請調低該設定。三種模式:

- **沒有 `/v1/model/info` (Ollama、vLLM、LM Studio 及多數 OpenAI 相容伺服器)。** 模型仍會經回退出現, 但每輪新的探索都要先為注定失敗的模型資訊探測買單 - 在 Ollama 上該請求會懸置直到探索逾時, 所以調大 `discovery.timeout` 只會更糟。儀表板的伺服器列會說明:「可以提供其模型, 但其模型資訊探測永遠不會回應, 每次同步都要等滿探索逾時。將該失敗宣告為預期, 即可把它標記為此伺服器的正常情況。」(當伺服器以 404/405 回應而非懸置時, 提示會點名缺少的端點); 它的「宣告預期失敗」按鈕會寫入該宣告, 也可以手動加入:

```jsonc
"litellm-vscode-chat.servers": [
  {
    "label": "Ollama",
    "baseUrl": "http://localhost:11434",
    "discovery": { "expectedFailures": ["modelInfo"] }
  }
]
```

- **連 `/v1/models` 也沒有, 或完全無法列出模型。** 當清單失敗而伺服器在其他方面有回應時, 錯誤會建議對稱的宣告 -「模型清單取得失敗, 但此伺服器有回應。如果它從不提供模型清單, 請在 ... 項目上宣告」- 伺服器列也提供同樣的一鍵「宣告預期失敗」。宣告 `"modelListing"` (或兩個類別都宣告), 並在 `discovery.declared` 中自行列出模型; 完整配方見[伺服器: 探索與預期失敗](servers.md#探索與預期失敗):

```jsonc
{
  "label": "my-gateway",
  "baseUrl": "https://gateway.example.com",
  "discovery": {
    "expectedFailures": ["modelListing", "modelInfo"],
    "declared": ["gpt-5", "deepseek-r1"]
  }
}
```

- **兩個端點都不可用。** 兩個端點都逾時的時候, 錯誤顯示為「位於 ... 的兩個探索端點都沒有回應 - 該位址看起來不是 LiteLLM 或 OpenAI 相容的 API」; 兩個端點都回覆不提供該路徑的時候, 則顯示為「位於 ... 的伺服器不提供任何一個探索端點」(模型列表回傳 404 時仍保留上文專門的 404 錯誤訊息)。這裡沒有任何宣告能幫上忙: 請檢查基底 URL 與連接埠 (LiteLLM 代理預設為 4000, Ollama 為 11434), URL 的解析規則見上文的 404 條目。

宣告究竟改變了什麼: 被點名的端點每輪只嘗試一次 (不重試), 其失敗按預期記錄而不再警示 - 對模型清單來說, 失敗也不再算作故障; 模型資訊探測的失敗本來就不致命 (探索總會回退), 宣告主要是讓日誌安靜下來並撤下儀表板的提示。除此之外什麼都不變。

而沒有 `/v1/model/info` 時失去的是中繼資料, 不是聊天: 能力與定價欄位不會到達, 所以重要的欄位請透過 [`models.capabilities`](models.md#能力) 補上 (知名模型 ID 由 OpenRouter 目錄自動回填)。

想恢復完整中繼資料 - 以及多提供者路由 - 的替代方案是在該伺服器前架設一個 LiteLLM 代理並把延伸模組指向它; [LiteLLM 自己的文件](https://docs.litellm.ai/docs/providers/ollama)介紹了如何前置 Ollama 等伺服器。

### 模型選擇器中沒有出現任何模型

先看狀態列 - 它點名故障類別。

- 連線項目顯示錯誤或降級狀態: 探索在失敗; 執行 "LiteLLM: Test Connection" 讀取確切錯誤, 然後與上面的條目對照。
- 一切顯示已連線, 但最近新增的模型不見了: 探索的清單有快取 (`discovery.cacheTtl`, 預設 1 小時)。執行 "LiteLLM: Sync Models Now" 略過快取。
- 閘道根本無法列出模型 (沒有 `/v1/models`): 用 `discovery.declared` 在項目上宣告它們, 並在旁邊加上 `discovery.expectedFailures`, 讓缺少的端點不再算作故障。配方: [伺服器: 宣告的模型](servers.md#宣告的模型)。
- 您之前確實見過的模型上有警告圖示, 代表背景重新整理失敗, 延伸模組正在提供標記為過時的最後已知清單 - 見[逾時與重試](#逾時與重試)。
- 一切顯示已連線, 您伺服器的標籤下卻什麼都沒有, 而您的 Copilot 席次來自組織 (Copilot Business 或 Enterprise): 組織的「Bring your own language model key」原則被停用了。隱藏發生在 Copilot 內部, 所以延伸模組自己的診斷全都回報成功; 請您的 Copilot 管理員啟用該原則, 然後重新載入 VS Code。

### 「伺服器有回應, 但未列出任何模型」

您的 LiteLLM 代理可以連線, 但沒有設定任何模型 (記錄行讀作 `Servers returned 0 models`)。

- 檢查您的 LiteLLM 代理設定 (`litellm_config.yaml`)。
- 執行 `litellm --config your_config.yaml`, 帶著模型啟動代理。

### 「我的嵌入或影像生成模型沒有出現在選擇器中」

LiteLLM `model_info.mode` 指向非聊天端點 (`embedding`、`image_generation`、`audio_speech`、`audio_transcription`、`rerank`、`moderation`) 的模型被刻意排除在聊天選擇器之外, 因為對它們的聊天請求只會失敗; 未宣告 mode 的模型始終註冊。代理已暫停的部署 (`model_info.blocked`) 同樣被略過。見[模型: 模型如何出現](models.md#模型如何出現)。

### 「模型不接受影像, 或從不使用工具」

能力把關提供什麼與送出什麼: 影像只送給宣告視覺支援的模型, 使用工具的請求只送給宣告工具呼叫的模型。當有能力的模型在伺服器端的宣告缺少或錯誤時, 覆寫它:

```jsonc
"litellm-vscode-chat.models.capabilities": {
  "qwen2.5-vl-72b": { "supports_vision": true }
}
```

在沒有視覺支援的模型上, 文字照常通過, 影像被捨棄, 「LiteLLM」輸出通道記一條說明。對知名的模型 ID, OpenRouter 目錄經常自動填補這些空缺。見[模型: 能力](models.md#能力)。

### 「此對話對該模型而言似乎過長」

當延伸模組自己的 token 估計超過模型的輸入預算時, 它在送出前拒絕請求; 標題下方的詳細資訊行為「詳細資訊: 傳送前已超出 token 上限: 本機估計 N 個 token (訊息 + 工具), 輸入上限 M」。計數是本機估計 (文字約四字元一個 token, 影像、PDF 或音訊剪輯按固定數字計), 所以可能與伺服器實際計費不同。

- 精簡對話或去掉附件, 或者
- 當真實模型能接受的比上限 `M` 說的更多時, 調高預算。上限來自模型宣告的輸入上限 (伺服器回報、目錄, 或您的覆寫); 在 `models.capabilities` 中修正它:

```jsonc
"litellm-vscode-chat.models.capabilities": {
  "my-model": { "max_input_tokens": 100000 }   // 或修正 context_length
}
```

鍵是精確比對的; 用 `"*"` 為每個模型設定下限。(舊版本為此提供 `defaultContextLength` / `defaultMaxInputTokens` / `defaultMaxOutputTokens` 設定; 它們沒有了, 已自動移轉進一個 `"*"` 記錄。) 見[模型: 能力](models.md#能力)。

### 「我設定的參數沒有生效」

不要猜 - 開啟儀表板的模型頁面, 查看該模型的參數[檢查器](models.md#檢查器): 它顯示每個有效欄位以及究竟是哪個來源設定了它。它通常揭示的是:

- **鍵比對不上。**鍵預設精確: `"gpt-5"` 只比對 `gpt-5`, 不比對 `gpt-5-turbo`。家族鍵需要結尾的 `*`。見[模型比對](models.md#模型比對)。
- **正規表示式鍵錨定整個 ID。**`"/gpt-5/"` 只比對字面 ID `gpt-5`, 不比對 `my-gpt-5-deployment` - 斜線包裹的模式必須比對整個模型 ID, 而不是它的子字串。要做包含比對, 寫 `"/.*gpt-5.*/"`。無效的模式 (或 `i` 之外的任何旗標) 會在儀表板中回報, 該鍵被忽略。
- **更寬的鍵沒有流入。**預設情況下最具體的相符記錄整體勝出 - `"*"` 或 `"gpt-5*"` 的值只有在標記了 `_inheritable` (且中間沒有 `_inherit_from: false` 屏障) 時才到達更具體的比對; 伺服器項目的記錄逐欄位勝過全域設定。查看診斷區段的繼承樹, 然後見[模型 - 比對](models.md#哪筆記錄生效)。
- **執行階段選項排在您前面。**請求時傳入的選項 (Copilot 或聊天工具) 與[選擇器的各模型設定](models.md#選擇器)勝過設定的記錄。要不管三七二十一釘住一個欄位, 標記為強制: `"gpt-5*": { "_force": ["temperature"], "temperature": 1 }`。見[模型: 參數](models.md#參數)。
- **就算被強制的欄位, 也需要它的記錄參與。**`_force` 只有在攜帶它的記錄參與該模型的解析時才勝過執行階段選項: 當更具體的記錄勝出且不繼承被強制的欄位時, 強制永遠到不了請求 - 診斷樹會顯示它停在哪裡。而提供者擁有的鍵 (`model`、`messages`、`stream` 等) 根本不能強制; 那樣的 `_force` 會被回報並忽略。
- **項目的記錄可能未生效。**如果伺服器在儀表板中的列說項目的依伺服器設定可能未套用, 見[下文](#各伺服器模型參數未生效)。

### 「模型只產生了推理輸出, 而此版本的 VS Code 無法顯示它」

您的 VS Code 組建缺少 thinking-part API, 所以串流的推理被捨棄 (輸出通道有說明), 只包含推理的回覆以此錯誤失敗。把 VS Code 更新到支援 thinking part 的版本, 或改用回傳最終文字的模型。

## 用量功能缺失

儀表板的伺服器列不顯示支出、不顯示支出百分比、也沒有警示觸發。按可能性排序:

- **伺服器沒有資料庫。**LiteLLM 只在有資料庫支撐時提供支出資料 (`/key/info`); 沒有它, 延伸模組偵測一次後為該伺服器隱藏所有用量功能 - 一個空的支出儲存格, 這是設計, 無需設定。從終端機確認: `curl -H "Authorization: Bearer sk-..." https://your-gateway/key/info` - 回答錯誤頁而非 JSON 即可確認。之後補上資料庫時, 背景輪詢不會自己注意到: 執行 "LiteLLM: Refresh Usage Now" 重新檢查。
- **金鑰讀不了用量資料。**在用量端點上回答 401 或 403 的資料庫支撐伺服器不顯示數字, 但不會被隱藏: 它在儀表板伺服器頁上的列帶一條問題行, 寫著「... 的用量不可用: 此金鑰無權讀取其用量資料。」, 並附一行點名端點和狀態碼的詳細資訊。此時上面的 curl 回傳的是 401 或 403 而不是錯誤頁; 請金鑰的核發者允許它讀取自己的 `/key/info`, 然後用「立即重新整理」- 延伸模組不會自己重新檢查。
- **輪詢關了。**`usage.pollInterval: 0` 停用背景輪詢; 儀表板開啟時只在一次擷取到期時才擷取 (本次工作階段還沒有完成過擷取、距上一次擷取已超過五分鐘, 或 `servers` 設定有變更 - [開啟冷卻](usage.md#用量面板)), 沒有警示觸發, 狀態列項目在一次擷取後顯示隨選資料十分鐘, 然後隱藏。執行 "LiteLLM: Refresh Usage Now" 立即擷取 - 它總能重新點亮該項目。
- **警示關了。**空的 `usage.alertThresholds` 清單代表沒有門檻, 所以永遠不會觸發任何警示通知, `"alerts-only"` 狀態列模式只在某個伺服器超出其整個預算時才顯示 (超過 100% 無論門檻如何都是錯誤色調)。
- **該項目被設定隱藏了。**`usage.statusBar: "off"` 隱藏該項目; `"alerts-only"` 只在門檻被越過或預算被超出時顯示。
- **哪裡都沒有預算。**百分比需要預算: 金鑰自身的 LiteLLM `max_budget`, 或項目的 `budget` 欄位。見[用量: 預算](usage.md#預算)。

一個相關的部分缺少情況: **支出顯示了, 但沒有請求計數**。抽屜裡的請求數、成功率與快取命中率來自第二個端點 (`/user/daily/activity`); 伺服器不提供它 - 或對您的金鑰拒絕它 - 時, 展開的列只顯示支出與預算, 缺少數字的位置就地寫明原因。可用性按端點偵測, 所以這在某些配置上是正常形態, 不是錯誤。

完整功能描述在[用量](usage.md#用量面板)頁面; 設定及其預設值在[參考](settings.md#參考)。

## 逾時與重試

兩個逾時設定約束什麼, 什麼會重試:

- **聊天補全從不重試。**補全可能有副作用 (支出、工具呼叫), 所以延伸模組呈現失敗, 而不是悄悄為第二次嘗試付費。因此 `chat.timeout` (預設 5 分鐘) 是一個請求可占用的總時間, 含串流; 長推理運行被截斷時調大它。
- **探索會重試。**模型探索請求是冪等的 GET, 暫時性失敗最多重試兩次, `discovery.timeout` (預設 30 秒) 是每個請求 (含其重試) 的硬性上限 - 按請求, 不是按整輪: 模型資訊清單、`/v1/models` 退回和任何 OAuth 權杖交換各自獲得一份新預算, 所以一輪最長可能耗時到它們之和。為緩慢的閘道基礎設施或緩慢的 OAuth 身分識別提供者調大它 - 權杖交換花的是自己的預算, 不是清單的 - 而且在聊天請求上交換同樣受 `discovery.timeout` 約束。
- **預期失敗不重試。**項目的 `discovery.expectedFailures` 指名的端點只嘗試一次, 記一條 info 層級記錄而非紅色錯誤 ([伺服器](servers.md#項目參考))。
- **最小值。**兩個逾時都箝制到至少 1000 毫秒。
- **過時清單寬限。**當背景重新整理失敗, 但最近一次成功探索仍在 `discovery.staleServeWindow` 之內 (預設十分鐘) 時, 延伸模組繼續提供最後已知的模型清單, 以警告圖示標記為過時, 而不是在工作階段中途丟掉您的模型。伺服器休眠更久就調高這個視窗; `0` 關閉寬限。

設定的預設值與單位在[參考](settings.md#參考)。

## 伺服器緩慢或被灌爆

VS Code 重新解析模型提供者很頻繁 - 有時一秒好幾次 - 而 `discovery.cacheTtl` (預設 1 小時) 正是防止這變成對您閘道的請求風暴的東西。如果您的伺服器記錄顯示延伸模組在不停地打 `/v1/models`, 那是有人把 TTL 設成了 `0` (每次都重新擷取); 調高它。快取從不儲存失敗, 同時發生的重新整理共用一個請求, "LiteLLM: Sync Models Now" 隨時依需略過, 所以長 TTL 的代價只是伺服器端模型變更後需要手動同步一次。

## 設定同步的意外之處

- **「我的伺服器沒有跟我到新機器。」**這是設計: `servers` 設定是機器範圍的, 設定同步從不攜帶它, 祕密儲存體也不同步 - 伺服器與認證留在您輸入它們的那台機器上。在新機器上重新加入。見[伺服器: 多台機器](servers.md#多台機器與設定同步)。
- **「新機器有我的模型設定, 卻沒有模型。」**同一規則的另一面: 設定同步送達您的全域設定 - `models.parameters`、`models.capabilities`、用量門檻 - 但不送 `servers` (也不送功能開關與模型選擇, 它們是機器可覆寫的, 留在各台機器上), 所以記錄暫時沒有可套用的對象。重新加入伺服器, 同步來的記錄會隨相符模型的註冊自行生效。存放在項目上的一切 (認證、各伺服器記錄、標頭、`budget` 欄位) 需要隨之重新輸入。
- **「工作區改不了我的伺服器。」**同樣是設計: `servers` 只接受使用者設定的值, 所以複製下來的儲存庫永遠無法把您的標籤重新指向另一台主機。
- **「那認證應該放在哪裡?」**放在伺服器項目裡 - 而且只放那裡。項目的 [`auth` 形式](servers.md#身分驗證) (可用祕密儲存體) 與它的各項目 `headers` 物件都是機器範圍的, 所以金鑰既不會透過設定同步複製, 也不會落進提交的 `.vscode/settings.json`。其他設定 (`models.parameters`、逾時、用量門檻) 正常同步, 且不攜帶任何類似認證的東西; 功能開關與模型選擇留在各台機器上 ([範圍](settings.md#設定如何運作))。

## 移除或重新命名伺服器後的殘留群組

VS Code 的提供者群組 API 可以建立群組, 但永遠無法更新或移除它們, 所以移除 `servers` 項目會隱藏它的群組 (模型立即離開選擇器) 而不是刪除它, 重新命名項目會把舊群組作為「外部」列留下。永久修法始終相同:

1. 開啟模型檔案 - 通知的按鈕, 或手動開啟 `<profile>/User/chatLanguageModels.json`。
2. 從 JSON 陣列刪除該群組的物件。手動編輯前先結束或重新載入 VS Code: 它把檔案保留在記憶體中, 可能覆寫外部編輯。
3. 重新載入視窗並執行 "LiteLLM: Sync Models Now"。

當您重新加入標籤與基底 URL 相同的項目, 或透過儀表板隱藏群組的「取消隱藏」動作時, 隱藏的群組自行回歸。在非英文語言的 VS Code 組建上, 延伸模組可能認不出主機的名稱衝突回應: 伺服器列隨即顯示的不是單條可操作的「提供者群組已占用此名稱」狀態, 而是每輪都重試的一般同步失敗 - 修法還是同樣三步。完整生命週期 - 每個操作留下什麼、為什麼 - 在[伺服器: 生命週期](servers.md#生命週期-重新命名移除與隱藏的群組); 外部列與採用[也在那裡](servers.md#外部伺服器與採用)。

## 各伺服器模型參數未生效

當伺服器項目帶有各項目 `models.parameters`, 但服務該伺服器的 VS Code 提供者群組可能不帶有項目的標籤化身分時, 儀表板在該伺服器列的下方放一條診斷行 -「可能未套用其依伺服器的模型參數」。這發生在群組早於項目標籤, 或重新命名、基底 URL 編輯留下了過時群組時; 經過這種群組的請求可能只得到全域 `models.parameters` 設定。

同一條診斷行也會點名其他每個受影響的部分: 項目的 `models.capabilities`、`discovery.declared` 與 `discovery.expectedFailures`、它的自訂 `headers`, 以及它的 `apiVersion` 覆寫 (請求回退到自動規則); 修法全都相同。

兩種修法:

- 從模型檔案 (`<profile>/User/chatLanguageModels.json`) 刪除該群組的物件, 重新載入視窗, 執行 "LiteLLM: Sync Models Now"; 延伸模組會從項目重新建立群組, 這次帶上它的身分。
- 或者用新標籤儲存項目; 會為它建立新群組。舊群組留著, 直到您從模型檔案刪除它的物件。

## 祕密儲存體無法使用

兩條伺服器列訊息代表問題出在 VS Code 的祕密儲存體, 而不是您的伺服器:

- **"Reading this entry's stored secrets failed, so it was not synced. Run Sync Models Now to retry."** 這一輪讀取失敗; 項目只是被略過, 不是永久失敗 - 下一輪 (或 "LiteLLM: Sync Models Now") 會再次讀取。
- **"VS Code secret storage could not be confirmed this session, so this entry was not synced. Syncing resumes on the next VS Code session."** 延伸模組無法確認它的同步狀態能在本工作階段之後留存, 所以寧可什麼都不同步, 也不去猜。

兩種狀態下項目都只是本輪被略過: 它的作用中提供者群組繼續提供最近一次同步的模型, 什麼都不會遺失。常見原因是作業系統的鑰匙圈或金鑰圈無法使用 - 在 Linux 上, 沒有金鑰圈服務 (gnome-keyring、KWallet) 的桌面工作階段是最常見的情況。恢復金鑰圈, 重新啟動 VS Code, 然後執行 "LiteLLM: Sync Models Now"。

## 來自舊版本的設定

如果某個設定在升級後好像消失了, 那是它被重新命名或重構了: 一次性移轉自動搬移一切 -

- 設定名稱進入新區段 (`requestTimeout` 到 `chat.timeout`、`modelParameters` 到 `models.parameters` 等等),
- 扁平伺服器項目進入 `auth`/`models`/`discovery` 形態,
- `default*` token 設定進入 `models.capabilities` 的 `"*"` 記錄,
- `_declare` 指示詞進入項目的 `discovery.declared` 清單,
- 舊的全域 `headers` 設定進入每個項目自己的 `headers` 物件 (無項目可接收的副本留在原地休眠, 附儀表板提示)。

不需重新輸入任何東西; [重新命名表](settings.md#重新命名與移除的設定)把每個舊名稱對應到新家。

比對器不再比對時值得知道的兩個移轉效果:

- 記錄鍵以前是隱含前置詞; 移轉給每個既有鍵附加了 `*`, 所以舊鍵比對它們以前比對的東西。只有從現在起您新寫的鍵預設精確 ([模型比對](models.md#模型比對))。
- 全域記錄中的伺服器 URL 限定鍵移入了相符的伺服器項目。URL 比對不到任何項目的限定鍵留在原地 - 休眠, 因為它永遠比對不到模型 ID - 儀表板會標記它並提示移入伺服器項目。

## 回報問題

「回報問題」動作會開啟預先填了診斷資訊的 GitHub Issue:

- 延伸模組與 VS Code 版本、平台與連線狀態
- 是否設定了 API 金鑰與基底 URL: 是、否, 或當認證由 VS Code 管理時為未知; 從不包含值本身
- 最近的錯誤與近期記錄行

延伸模組的記錄寫的是所發生事件的分類, 從不寫源自伺服器回應的文字, 因此預填的內文不可能洩漏您的提示、補全或認證; 即便如此, Issue 會在瀏覽器中開啟, 供您在提交前檢閱。當診斷資訊對 URL 而言過大時, 全文改為進入您的剪貼簿 (可能時還有一個本機檔案), Issue 內文會說明省略了什麼。

## 隱私與資料

您的提示、附件與補全只在 VS Code 與您設定的端點之間傳輸 - 另外, 任何作為聊天輪次送出的內容會去到聊天選擇器所指模型所在的地方, 除非您選了自己的模型, 否則那就是內建的 Copilot 模型:

- 聊天與模型探索請求發往您的 LiteLLM 伺服器的基底 URL。
- 提交訊息產生只在您明確叫用時送出已暫存的差異 - 未暫存任何內容時則是工作區差異加上未追蹤檔案的路徑 (只有路徑, 從不含內容) - 連同您最近五筆提交主旨, 發往您為它設定的 LiteLLM 伺服器 ([入門指南](getting-started.md#用您自己的模型產生提交訊息))。
- 提取要求描述產生只在您明確叫用時, 把分支名稱、該分支的提交訊息和每個變更檔案的一份修補檔 (從它將被合入的分支的合併基準點開始比較) 發往您為它設定的 LiteLLM 伺服器。
  - 若使用此功能在 GitHub Pull Requests 延伸模組的 Create Pull Request 檢視中註冊的產生按鈕, 則由該延伸模組組裝內容, 並會額外加入兩樣東西: 您儲存庫的提取要求範本, 以及提交訊息中引用的每個議題的標題與內文 (包括私有議題)。
  - 儀表板的「測試模型」按鈕只送出一個固定的小範例分支, 從不送出您的儲存庫 ([入門指南](getting-started.md#用您自己的模型產生提取要求描述))。
- 內嵌補全在開啟並選定模型後, 會在您輸入時自動把游標周圍的檔案內容 (游標之前最多 8000 個字元、之後最多 4000 個字元) 送到您為它設定的 LiteLLM 伺服器; 儀表板的「測試模型」按鈕只送出一小段固定的程式碼片段, 從不送出您的檔案 ([入門指南](getting-started.md#用-litellm-模型取得內嵌補全))。
- 諮詢工具在啟用且已選擇模型時, 會把聊天代理寫的問題和背景文字傳送到您為它設定的 LiteLLM 伺服器 - 一旦您啟用, 就由代理自行發起, 而不是您逐次要求。不會自動附帶任何內容, 但代理被要求帶上問題所依賴的程式碼和錯誤, 因此它讀到的工作區內容可能出現在那段文字裡; 傳送什麼由代理決定, 而不是一個固定集合。儀表板的「測試模型」按鈕改為傳送一個固定的小問題 ([入門指南](getting-started.md#讓代理向第二個模型提問))。
- 快速修復在開啟後, 只有當您從燈泡中選擇「修復」或「解釋」時, 才會送出診斷訊息以及它們所在的行 (上下各加兩行)。
  - 走聊天路徑時, 這就是一次普通的 `@litellm` 輪次, 因此會發往聊天選擇器指定的模型 - 您選了自己的 LiteLLM 模型就是您的, 否則就是內建的 Copilot 模型 - 並且和任何聊天輪次一樣, 該對話中先前的訊息會作為上下文一起帶上。
  - 聊天檢視無法作答時, 後備路徑改為把同樣的內容發往 `quickFix.model` 背後的伺服器; 儀表板上該行的「測試模型」按鈕只送出一小段固定的程式碼片段, 從不送出您的檔案 ([入門指南](getting-started.md#修復或解釋一條診斷))。
- 審查評論只在您明確叫用時把被審查的程式碼送到您為它設定的 LiteLLM 伺服器: 變更模式下是每個被審查檔案相對 HEAD 的差異, 檔案模式下是該檔案的全部內容, 兩種模式都帶上該檔案相對工作區或存放庫的路徑 (兩者都不屬於時只帶檔案名稱, 因此沒有絕對路徑離開這台機器), 檔案模式還帶上它的 VS Code 語言識別碼。
  - 在討論串中回覆時會送出該討論串的對話以及它錨定的那些行。
  - 沒有任何內容會被自動審查; 儀表板的「測試模型」按鈕只送出一小段固定的範例差異, 從不送出您的檔案 ([入門指南](getting-started.md#讓模型審查您的程式碼))。
- OAuth 認證只發往伺服器項目上設定的權杖端點。
- 一個預設開啟的例外: 延伸模組約每週從 `https://openrouter.ai/api/v1/models` 重新整理一次內建的 OpenRouter 模型目錄 - 一份公開、不需驗證的模型清單; 該請求不攜帶提示、不攜帶用量, 也不攜帶任何關於您或您伺服器的資訊。把 `litellm-vscode-chat.models.openRouterCatalog` 設為 `false` 可停止所有目錄網路存取 ([模型: 能力](models.md#能力))。
- 用量輪詢只呼叫您自己伺服器的支出端點, 用項目自己的認證。
- 延伸模組沒有遙測, 也沒有自己的後端; 不向發布者送出任何內容。
- 唯一的另一個對外通道是[問題回報器](#回報問題), 它在本機準備一切, 攜帶環境細節與延伸模組自身的記錄 (版本、平台、連線狀態、錯誤分類與堆疊 - 從不含提示或回應文字, 從不含金鑰值), 並在瀏覽器中開啟, 供您在提交前檢閱。

認證存放在哪裡、機器之間同步什麼, 見[伺服器](servers.md#祕密與祕密儲存體)。

## 解除安裝與清理

解除安裝延伸模組不會移除兩樣東西, 所以在意殘留認證的話請先清理:

- 您的 `litellm-vscode-chat.*` 設定留在 settings.json 中, 包括 `servers` 項目中的任何內嵌認證 - [`auth` 物件](servers.md#身分驗證)與任何各項目 `headers`。在設定編輯器中移除它們, 或從使用者 settings.json 刪除那些行。
- 伺服器同步成的 VS Code 提供者群組歸主機所有, 保留自己那份認證副本, 直到您移除它們: 從 `<profile>/User/chatLanguageModels.json` 刪除它們的物件 (之後結束或重新載入 VS Code)。

存放在 VS Code 祕密儲存體中的祕密可以在延伸模組仍安裝時移除, 透過編輯表單的「移除已儲存的...」核取方塊 ([伺服器](servers.md#祕密與祕密儲存體)); 解除安裝之後, 那份儲存歸 VS Code 的延伸模組資料處理管轄, 延伸模組自己的 UI 不再搆得到它。
