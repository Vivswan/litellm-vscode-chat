# 儀表板

[English](../dashboard.md) | [简体中文](../zh-cn/dashboard.md) | 繁體中文

"LiteLLM: Open Dashboard" 開啟一個面板, 一切盡在其中: 伺服器、已探索的模型、用量與預算, 以及延伸模組的設定, 整體連線狀態釘在旁邊的導覽列上。它是延伸模組其餘部分所用同一批儲存區的一個檢視, 因此您在這裡做的任何事, 都同樣可以透過 VS Code 設定與命令完成; 儀表板只是把它們集中一處, 附上原始 JSON 給不了的驗證與來源資訊。

## 版面配置

- 左側一條導覽列: 各個頁面的入口, 每個都在有數可顯示時帶著它所關心的即時數字 (伺服器數、模型數、支出對預算、待處理問題數), 其下是所有伺服器的整體連線狀態與上次同步時間, 在旁邊的頁面捲動時一直留在畫面上。導覽列底部有一個「同步模型」按鈕和一個低調的「回報錯誤」動作; 後者開啟預先填了版本、平台與近期記錄的 GitHub Issue。
- 五個頁面。**伺服器**是您的項目和它們的健康狀況, 每個伺服器的問題就寫在所屬列的下方。**模型**是那些伺服器回報的一切, 伺服器頁上某伺服器的模型數會跳轉到這裡並縮窄到該伺服器。**用量**顯示支出對預算。**診斷**是連線摘要、延伸模組發現的設定問題, 以及回饋與文件連結。**設定**以可編輯的表單控制項承載延伸模組的設定。
- 設定編輯寫入您的 VS Code 設定 (寫到值已所在的範圍, 否則寫到使用者設定), 按鈕執行的是命令選擇區提供的同一批命令。
- 各區段可從外部直達: 命令會落在它們關涉的區段上, 通知按鈕把儀表板開到「伺服器」- 只有預算警示的「開啟用量」按鈕例外, 它深層連結到用量區段 ([深層連結](#深層連結))。
- 窄面板會重排而不是橫向捲動, 下限為 320px。視窗窄於 1000px 時, 導覽列折疊成圖示列, 就像 VS Code 自己的活動列那樣; 每個導覽項目的名稱、整體連線狀態和同步時間都留在可存取名稱裡並以提示形式出現, 較寬的列則折成多行, 而不是丟掉資訊。

## 伺服器

伺服器清單顯示延伸模組知道的每個伺服器: 在 [`litellm-vscode-chat.servers` 設定](servers.md#項目參考)中宣告的項目, 以及只作為 VS Code 提供者群組存在的「外部」伺服器 (在本延伸模組之外新增 - 見[採用](servers.md#外部伺服器與採用))。被已移除項目隱藏的群組折疊進「隱藏的群組」一行, 附「取消隱藏」動作 ([生命週期](servers.md#生命週期-重新命名移除與隱藏的群組))。

每列的狀態標籤是六種狀態之一:

| 狀態 | 意義 |
|--------|---------|
| 已連線 | 探索成功 |
| 錯誤 | 上次檢查失敗 |
| 同步問題 | 伺服器有回應, 但上次設定同步回報了問題, 典型的是[群組更新限制](servers.md#生命週期-重新命名移除與隱藏的群組) |
| 預期失敗 | 探索只在項目的 [`discovery.expectedFailures`](servers.md#探索與預期失敗) 宣告的類別中失敗, 且沒有宣告的模型可提供 |
| 設定有誤 | 項目本身無效 - 例如超過一種[驗證形式](servers.md#身分驗證) - 修復前不被使用 |
| 尚未檢查 | 已宣告, 但還沒有探索回合看過它 |

每列的問題直接呈現在該列下方, 最嚴重的在前。每一條都以後果開頭 ("prod 未提供任何模型: ..."), 附上伺服器自己的錯誤文字 (如果有), 並就地給出對應的動作 - 「重試」「開啟項目」「在 settings.json 中修正」「宣告模型」「開啟模型檔案」或疑難排解連結。當有列需要處理時, 清單上方會有一條「N 個伺服器需要處理」的摘要; 安靜的建議性行只陳述無需處理的事實, 不計入該數字。[疑難排解](troubleshooting.md#常見問題)涵蓋復原步驟。一處刻意的柔化: 有[宣告模型](servers.md#宣告的模型)仍在提供的預期探索失敗不算問題 - 該列保持「已連線」, 配一條低調的建議性行說明這次預期中的失敗。什麼都沒宣告時, 該列像任何不提供模型的伺服器一樣顯示為紅色, 結論讀作「預期失敗」。

### 通知

- **項目設定未生效** (伺服器列下方的一條診斷行): 為項目提供服務的提供者群組可能不帶有項目的標籤化身分 (群組早於項目標籤, 或重新命名留下了過時群組), 所以項目宣告的一部分內容可能未被套用 - 依伺服器的模型參數、依伺服器的能力、宣告的模型與預期失敗、自訂標頭, 或 `apiVersion` 覆寫 (請求回退到自動規則)。該行會點名究竟哪些部分未生效, 旁邊就是「開啟模型檔案」動作。修法對所有情況都相同: 從模型檔案 (chatLanguageModels.json) 刪除該群組的物件, 重新載入視窗並重新同步 - 或給項目換個標籤; [疑難排解](troubleshooting.md#各伺服器模型參數未生效)有步驟。
- **什麼都沒宣告的預期探索失敗**是列下方的一條阻斷性診斷行: 探索只在項目預期的類別中失敗, 但項目的 `discovery.declared` 清單為空, 所以伺服器不提供任何模型; 該行的「宣告模型」動作會開啟項目 ([宣告的模型](servers.md#宣告的模型))。
- **採用外部伺服器之後**, 一次性通知提醒您原始群組仍然存在, 在您從模型檔案刪除其物件 (通知的按鈕會開啟它) 並重新載入視窗之前, 它的模型會出現兩次。

## 伺服器表單

「新增」與「編輯」把同一個表單作為主窗格中的一個頁面開啟, 導覽列仍在旁邊: 一個扁平的頁面, 項目的每個部分 - 連線、驗證、模型參數、模型能力、探索、標頭與預算 - 都帶著自己的標題從上到下排開, 沒有任何內容折疊在展開控制項後面。它寫入 `servers` 設定, 所以在這裡做的編輯與在 settings.json 裡做的編輯是同一回事; 表單的價值在於邊輸入邊檢核項目的結構, 而不是儲存之後才發現問題。每個欄位的提示就在它旁邊, 出錯時錯誤佔據提示的位置 (所以輸入時頁面不會跳動); 釘在底部的儲存列寫明項目將寫入哪個設定, 並統計還有多少處未儲存。離開這一頁 (頂端的返回路徑、導覽列、Esc 或「捨棄變更」) 不會立即生效: 有未儲存的編輯時會先詢問, 只有明確的「捨棄」才會丟棄草稿。焦點跟著您進來, 也跟著您回去, 回到您開啟時所在的那一列。

**身分** - `label` (選擇器名稱) 與 `baseUrl`。延伸模組會自行附加 `/v1`; 若 URL 已以 `/v1` 或 `/v2` 這樣的版本區段結尾, 則按原樣使用; `apiVersion` 欄位可覆寫兩者 ([原因](servers.md#項目參考))。

**驗證** - 驗證形式的選擇器: 無、API 金鑰、虛擬金鑰或 OAuth。這個選擇器*就是*[恰好一種形式規則](servers.md#身分驗證): 原始 JSON 要您自己守規矩, 表單則讓第二種形式根本無從設定。選擇 OAuth 會展開它的欄位與選填的附隨認證 - 隨 bearer 權杖一起送出的 `apiKey` 或 `virtualKey`, 給同時檢查兩份認證的閘道。

**祕密** - 每個可作祕密的欄位都提供逐欄位選擇: VS Code 祕密儲存體 (預設) 或內嵌設定值:

- 祕密儲存體中的祕密從不回顯到儀表板; 表單為它們顯示值存放在哪裡, 不顯示值是什麼。
- 內嵌值會預填到編輯表單, 以「顯示」切換遮罩: 它們本來就以純文字存在於您的 settings.json 中, 所以表單不會洩漏設定編輯器看不到的任何東西。
- 編輯時, 清空的祕密欄位保留儲存的值; 刪除祕密是表單明確的「移除已儲存的...」核取方塊 (見[祕密與祕密儲存體](servers.md#祕密與祕密儲存體))。

**各伺服器模型設定** - 表單以兩個區段承載項目的 [`models` 物件](servers.md#各伺服器模型設定):

- *此伺服器的模型參數*: 每個[比對器](models.md#模型比對)一列 - 比對鍵、它比對到什麼, 以及以低調文字呈現的欄位 (`temperature 0.2`), 指標懸停或取得焦點時變成控制項, 加號 `[+]` 用來新增。按一下一個欄位片會開啟一個小編輯器 - JSON 值、一個**強制**切換 (被強制的欄位勝過聊天用戶端的執行階段選項與模型選擇器的設定, [參數](models.md#參數); 在提供者擁有的鍵上停用並註明原因)、一個**可繼承**切換, 以及「移除欄位」。鉛筆圖示開啟完整的比對器編輯器。
- *此伺服器的模型能力*: 同樣的列, 用於能力覆寫。欄位名稱是自由的 (詞彙表是開放的, [能力](models.md#能力欄位)); 延伸模組不消費的名稱會在您輸入時得到一條不攔截的「可能是筆誤」提示 - 僅當伺服器觀察到的 `/model/info` 鍵集已知、非空且不含該名稱時 - 無論如何都按原樣套用。能力欄位片帶一個**後備**切換 - 後備欄位套用在伺服器回報*之下*而非之上 - `_openrouter_model` 指示詞則呈現為目錄欄位片, 它的編輯器就是 OpenRouter 目錄選擇器 ([能力](models.md#能力))。

**探索** - 面向探索看不見的東西的兩個控制項, 放在同一區段因為它們常常組合 ([無探索能力閘道的配方](servers.md#探索與預期失敗)):

- *宣告的模型* (`discovery.declared`): 一份單純清單, 列出即使探索列不出也要註冊的精確模型 ID ([宣告的模型](servers.md#宣告的模型))。舊版本中宣告是能力列上的「宣告此模型」切換; 移轉把那些移進了這份清單。
- *預期失敗*: 此伺服器已知不提供的端點的核取方塊 (`modelListing`、`modelInfo`)。

**標頭** - 項目 `headers` 物件的列編輯器: 發往此伺服器的每個請求上的額外 HTTP 標頭 (路由標籤、追蹤標頭)。項目自己的[驗證](servers.md#身分驗證)標頭在衝突時勝出, 所以自訂 `Authorization` 無法擠掉設定好的認證。標頭值是設定, 不是祕密 - 它們以純文字放在 settings.json; 認證屬於驗證形式, 後者可以存放在祕密儲存體。

**預算** - 驅動[用量警示](usage.md#預算)的手動預算, 以伺服器自身的計費貨幣計。

**測試連線**就在它所探測的基底 URL 旁邊, 在您提交之前試用草稿 - 用當下輸入的 URL 與認證發出一次探索呼叫, 回答「已連線 - 12 個模型」或確切的錯誤, 什麼都不儲存。探測遵循草稿的預期失敗與宣告的模型, 所以無探索能力的閘道回報它將提供什麼, 而不是硬失敗。延伸模組認得的設定類失敗 (錯誤的基底 URL、無法連線的代理、被拒的金鑰) 會在訊息下方附上指向[疑難排解指南](troubleshooting.md#常見問題)對應小節的連結。

外部列上的「編輯」是採用動作; 見[伺服器](servers.md#外部伺服器與採用)。

## 模型

您的伺服器回報的每個模型, 按註冊給 Copilot Chat 的樣子, 每個占兩行: 名稱加它的系列與伺服器, 然後是一行低調的規格說明 - token 上限、每百萬 token 價格, 以及模型能做什麼。排序與篩選控制項在清單上方。這些值從哪裡來、每個能力把關什麼、模型為什麼可能缺少: [模型](models.md#模型如何出現)。

- 按一下伺服器頁上某伺服器的模型數, 會開啟這一頁並縮窄到該伺服器; 篩選框旁的小標籤顯示目前範圍並可清除。
- 每列帶有一個複製動作 (懸停可見), 複製模型的精確 ID - 您的[比對鍵](models.md#模型比對)所比對的字串。
- 按一下一列會就地展開它的詳細資料 - 確切的 token 上限、原始模型 ID、包括快取與長上下文在內的每一級價格, 以及每個能力的是與否。一次只展開一列, 頁面不會跳轉。
- 由項目的[宣告清單](servers.md#宣告的模型)註冊而非在伺服器上探索到的模型, 在系列旁標註「宣告」, 其詳細資料會解釋這代表什麼。
- 清單有快取 ([`discovery.cacheTtl`](settings.md#參考)); 「同步模型」按鈕立即重新詢問伺服器。

### 有效參數

每列低調的「檢查」動作開啟模型檢查器 - 一個側面板, 分「參數」「能力」「定價」三個區段。參數區段回答一個問題: 發往這個模型的請求實際會攜帶什麼?

- 表格列出比對到該模型的每個已設定參數、它的值, 以及一枚點名來處的徽章 - `項目 gpt-5*` 或 `設定 *`, 即勝出的[比對器](models.md#模型比對)。當更具體的比對或更高的層覆寫了另一個值時, 落敗的值以刪除線顯示在下方, 所以在您意料之外觸發的比對器一眼就能找到元兇。
- 被強制的欄位標記為強制: 它們連聊天用戶端的執行階段選項都會勝過 ([完整優先順序](models.md#參數))。
- 延伸模組拒絕轉送的鍵 (提供者擁有的欄位、以 `_` 開頭的鍵) 以淡化樣式呈現並註明原因。
- 一列 `max_tokens` 始終在場, 說明該值及其來處: 您的設定、伺服器宣告的輸出上限, 還是封頂的預設值。
- 區段末尾把模型的記錄比對鏈擺在明面上, 每層一條「記錄路徑」, 其中每個鍵都能跳進擁有它的編輯器。

面板由請求路徑執行的同一套解析程式碼呈現, 所以它不可能偏離真實請求。兩樣它誠實承認無法顯示的東西: 聊天用戶端在每個請求上設定的執行階段選項 (它們覆寫列出的任何*未強制*參數), 以及推理模型的 Configure Model 選擇, 後者由 VS Code 存在自己那邊。

### 有效能力

檢查器的能力區段回答另一個問題: 延伸模組認為這個模型能做什麼, 為什麼?

- 每個能力欄位列出解析值與一枚來源徽章 - 某伺服器項目或全域 `models.capabilities` 記錄 (點名勝出的比對鍵)、伺服器自己的回報、OpenRouter 目錄項目 (明確 `_openrouter_model`, 或按精確 ID 或無歧義的廠商前置詞後段的隱含比對)、「上下文減輸出」衍生, 或內建預設值 - 起作用的指示詞以低調的記號標在旁邊 (「後備」「比對」), 被覆寫的值顯示在勝出者下方 (完整[優先順序](models.md#能力))。
- 表格下方的「輸出上限」一列說明輸出上限是不設頂送出 (使用者設定或伺服器宣告), 還是封頂 4,096 (猜測的預設值)。
- 記錄中的問題 - 無效值、無效的正規表示式比對器、目錄不認識的 `_openrouter_model` ID - 在這裡、在受影響的列旁邊指出。延伸模組不消費的欄位名稱得到的是一條建議性說明 - 該值照樣作為覆寫套用, 而且只有當伺服器自己的 `/model/info` 鍵集已知、非空且不含該名稱時才顯示 ([能力欄位](models.md#能力欄位))。
- 區段末尾同樣有自己的「記錄路徑」一行, 即能力記錄的比對鏈。

它由註冊路徑執行的同一個解析器呈現, 所以它顯示的就是告訴 Copilot Chat 的內容。

## 用量區段

支出對預算, 按伺服器, 涵蓋每個其 LiteLLM 執行個體追蹤支出的伺服器 - 沒有資料庫的伺服器乾脆不出現, 而當您的伺服器都不追蹤支出時, 該區段會明說, 而不是顯示空圖表。

每個伺服器是一列 - 標籤、支出對有效預算、計量條、百分比, 以及當下最要緊的那件事 - 展開它則列出延伸模組掌握的每個數字: 有效預算與金鑰回報預算 (兩者不同時)、預算的下次重設日期, 以及當伺服器提供每日活動資料時的請求數、成功率與快取命中率。伺服器沒有回報的欄位呈現為一個暗淡的短橫線加就地寫明的原因, 從不是零。區段標題裡的「立即重新整理」按鈕立即擷取 (擷取進行中時停用); 過時資料保持可見, 原因已知時標註原因 (「上次重新整理失敗」「用量存取遭拒」)。當一次明確的重新整理在每個伺服器上都失敗時, 會有一則警告快顯說明; 各伺服器的詳細資訊留在各列上。

開啟儀表板總會擷取新的用量資料, 即使背景輪詢關閉。深入內容 - 延伸模組讀什麼、從哪裡讀、兩個預算來源如何互動、輪詢與新鮮度、警示門檻、狀態列項目 - 在[用量與預算](usage.md)頁面。

## 設定

設定區段呈現的是原生設定編輯器顯示的同一批設定, 分組方式相同 (伺服器、模型、聊天、探索、用量、UI), 以表單列呈現, 帶單位、預設值與「重設」動作。已設定的列會說明其值存放在哪裡 (「已在使用者設定中修改」); 「重設」從該範圍移除值, 讓下一個範圍的值或預設值顯現。

- 物件形態的設定 - [`models.parameters`](settings.md#參考) 與 [`models.capabilities`](settings.md#參考) - 在這裡獲得比對器表格, 因為原生設定 GUI 無法編輯物件。它們使用與[伺服器表單](#伺服器表單)的各伺服器區段相同的表格: 每個比對器一列, 按從寬到窄排序 (捕獲全部的鍵在頂端, 精確 ID 在底部 - 僅是顯示順序; 儲存的鍵順序從不改變), 欄位呈現為帶強制/後備/可繼承徽章的欄位片, 欄位片快顯視窗用於快速編輯, 鉛筆圖示開啟完整的比對器編輯器。能力欄位名稱是自由的, 帶著與伺服器表單同款的建議性筆誤提示。每個欄位都解析通過之前,「套用」保持停用。(自訂 HTTP 標頭是按伺服器的, 不是全域的: 它們存放在項目上, 在[伺服器表單](#伺服器表單)中編輯。)
- 由於 VS Code 跨範圍合併物件設定, 每個記錄編輯器一次只操作一個範圍 (您的編輯寫入的那個), 其他範圍的項目以唯讀列出, 所以套用變更永遠不會把使用者範圍的值複製進工作區檔案。
- [`models.openRouterCatalog`](models.md#openrouter-目錄) 列帶有一條狀態線 - 目錄的大小與上次更新時間 - 和一個「重新整理」按鈕 (與 "LiteLLM: Refresh OpenRouter Catalog" 相同的動作)。設定關閉時該列休眠並附提示; 重新整理失敗在狀態線中回報, 從不以彈出通知呈現。
- **UI** 群組承載儀表板自己的外觀: 一個佈景主題選擇器 (跟隨編輯器佈景主題, 或固定淺色/深色) 和四個強調色色塊。兩者都在您選中的那一刻生效, 也都是普通設定 - 在 settings.json 中編輯 [`ui.theme`](settings.md#外觀) 或 [`ui.accent`](settings.md#外觀), 開啟著的儀表板同樣會換裝。無論選了哪一項, 高對比佈景主題始終跟隨編輯器。
- 末尾的**「匯入與匯出」**群組有兩個按鈕, 「匯出設定」與「匯入設定」- 與 "LiteLLM: Export Settings..." 和 "LiteLLM: Import Settings..." 命令相同的流程, 用於把您的配置搬到另一台機器 ([詳情](settings.md#匯出與匯入))。

## 診斷

診斷區段匯集支援介面; 命令選擇區中的 "LiteLLM: Show Diagnostics" 把儀表板直接開到它。

- 一份為整段貼進 bug 回報而寫的連線摘要: 導覽列顯示的同一結論、已設定伺服器數量、以絕對時間戳記表示的上次檢查 (附相對回顯), 以及每個伺服器一列結果 ("OK (12 models)", 否則是錯誤文字), 外加「測試連線」按鈕。帶有無自有列的移轉前伺服器的安裝, 還會看到「舊版登錄伺服器」計數。
- 設定診斷: 延伸模組在您的設定中發現的問題, 每個都在這裡以及它關涉的列旁邊呈現 ([下文](#設定診斷))。
- 「回報錯誤」開啟預先填了版本、平台與近期記錄的 GitHub Issue - 與導覽列按鈕相同的動作。
- 「請求功能」「為延伸模組評分」「文件」與「GitHub 儲存庫」是一般連結。

### 已解析模型

診斷區段還呈現延伸模組預先計算的解析表 - 每個已註冊模型最終得到的確切能力與參數, 涵蓋所有伺服器, 早於任何請求。同一份資料的兩個檢視:

- **繼承樹**: 您的比對鍵畫成一棵樹 - 每筆記錄掛在它的下一個更寬比對之下, 模型作為葉子掛在最具體的比對之下 - 每個節點標出自己的欄位、`_inheritable` 標記, 以及畫在被切斷分支上的 `_inherit_from: false` 屏障。一眼回答「gpt-5.6 的 temperature 為什麼是這個」: 沿它的分支向上走。

```text
*  temperature 0.7, top_p 0.9  (inheritable)
├─ gpt-5*  temperature 0.3  (inheritable)  [inheritance stops here]
│  ├─ gpt-5.6  max_tokens 8192   -> 8192 - 0.3
│  └─ gpt-5, gpt-5.7, ...        -> 0.3
├─ claude-4  temperature 1.0     -> 1.0 - top_p 0.9
└─ (everything else)             -> 0.7 - 0.9
```

- **扁平表**: 每模型一列, 列出最終解析值, 每個值帶來源小標籤 (自有、繼承自 `key`、強制、後備、伺服器、目錄、下限), 一個篩選框 (按模型 ID 或比對鍵 - 「顯示 `gpt-5*` 碰過的一切」), 以及逐列的「檢查」動作, 就地開啟該模型的[檢查器](#有效參數), 覆蓋在診斷頁之上。

關於樹的一條誠實說明: 它是對著您的伺服器*此刻*提供的模型畫的。記錄節點 - 尤其是正規表示式鍵 - 顯示的是它目前比對到的現存模型, 不是它可能比對的一切, 所以模型清單變了樹也會變。要得到關於某一個模型的權威答案, 扁平表的該模型列與檢查器才是正式檢視。

完全沒有設定比對記錄時, 扁平表仍列出每個模型 - 值隨即來自伺服器、目錄與內建下限 - 樹則塌縮為掛在隱含根節點下的模型, 附一條「不存在記錄」的提示。

兩者呈現的都是請求路徑使用的同一張預先計算表, 所以您看到的就是將要送出的。該檢視只存在於儀表板本機 - 從不包含在 GitHub 問題回報中。

### 設定診斷

設定問題從不無聲失敗; 每一個都作為診斷呈現, 帶出問題的鍵與修法:

| 診斷 | 意義 | 修法 |
|---|---|---|
| 無效的正規表示式比對器 | 一個 `/斜線包裹/` 的記錄鍵無法解析為正規表示式; 該鍵被忽略 | 修正模式 ([比對](models.md#模型比對)) |
| 不可強制的鍵 | `_force` 指名了提供者擁有的欄位, 任何東西都不得覆寫它; 對該欄位的強制被忽略 | 把該欄位從強制清單中去掉 ([參數](models.md#參數)) |
| 驗證設定錯誤 | 某伺服器項目設定了超過一種驗證形式; 修復前項目不被使用 | 恰好保留一種形式 ([身分驗證](servers.md#身分驗證)) |
| 舊版限定鍵 | 某全域記錄鍵仍在使用已移除的 `"<baseUrl>/matcher"` 伺服器限定語法; 它永遠比對不到模型 ID, 處於休眠 | 移入那個伺服器項目自己的記錄 ([移轉](models.md#從前置詞鍵移轉)) |
| 休眠的全域標頭 | 移轉在已移除的全域 `headers` 設定中發現了值, 卻沒有可接收它們的伺服器項目; 它們沒有套用到任何東西 | 把標頭加到伺服器項目上, 然後刪除舊的全域設定 ([移轉](settings.md#重新命名與移除的設定)) |
| 未知的 `_inherit_from` 鍵 | `_inherit_from` 清單指名了不存在的記錄鍵; 略過該名稱, 清單其餘部分照常生效 | 把名稱改成精確的記錄鍵 ([比對](models.md#哪筆記錄生效)) |
| 未識別的能力欄位 (建議性) | `models.capabilities` 記錄設定了延伸模組不消費的欄位, 且伺服器觀察到的 `/model/info` 鍵中沒有它; 該值按原樣作為覆寫套用 | 若是筆誤就改正拼寫; 若是有意為之就保留 ([能力欄位](models.md#能力欄位)) |

## 狀態列項目

延伸模組最多擁有兩個狀態列項目; 儀表板是它們的點擊落點。

- **連線項目**在一切健康時讀作 `$(check) LiteLLM`, 工具提示裡有伺服器與模型數量; 錯誤與部分狀態會改變圖示與工具提示, 而工具提示的各行是為貼進問題回報而寫的。按一下它開啟儀表板。(舊版本把模型數放在項目的文字裡; 現在它在工具提示裡, 讓狀態列保持安靜。)
- **用量項目**顯示最差新鮮伺服器的支出百分比, 只在有可信內容時出現; 按一下它開啟[用量區段](#用量區段)。它的完整行為 - 模式、門檻、新鮮度規則 - 在[用量與預算](usage.md#狀態列)中規定。
